# سناریوهای عملی ۴: Storage Management

> پیش‌نیاز مطالعه: `theory/04-Storage-Management.md`
> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

---

## سناریو ۱ (مبتدی): ساخت یک Volume Group و Logical Volume ساده از صفر (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده مهاجرت و RAID، باید چرخه پایه LVM (PV → VG → LV → فایل‌سیستم) را با دست خودتان یک‌بار کامل انجام داده باشید.

### قدم‌به‌قدم

**۱. آماده‌سازی یک دیسک خام به‌عنوان Physical Volume**
```bash
pvcreate /dev/sdb1
```
🔍 **تحلیل دستور:** بدون سوییچ اضافه؛ `pvcreate` یک متادیتای کوچک LVM در ابتدای پارتیشن مشخص‌شده می‌نویسد تا این دستگاه «قابل‌شناسایی» توسط بقیه ابزارهای LVM شود.

**۲. ساخت یک Volume Group از این PV**
```bash
vgcreate vg_test /dev/sdb1
```
🔍 **تحلیل دستور:**
- ا `vgcreate`: ساخت یک VG جدید.
- ا `vg_test`: اولین آرگومان، نام دلخواهی که به این VG می‌دهید (باید یکتا باشد).
- ا `/dev/sdb1`: دومین آرگومان (و می‌تواند چندتایی باشد)، لیست PV هایی که باید عضو این VG شوند.

**۳. ساخت یک Logical Volume با اندازه مشخص**
```bash
lvcreate -L 5G -n lv_test vg_test
```
🔍 **تحلیل دستور:**
- ا `-L 5G`: مخفف `--size 5G` — اندازه دقیق و مطلق LV (اینجا ۵ گیگابایت)؛ حرف بزرگ `L` برای اندازه مطلق است (برخلاف `-l` کوچک که برای تعداد Extent یا درصد استفاده می‌شود).
- ا `-n lv_test`: مخفف `--name` — نام دلخواه این LV.
- ا `vg_test`: آخرین آرگومان، مشخص می‌کند این LV از کدام VG ساخته شود.

**۴. بررسی نتیجه در هر سه سطح**
```bash
pvs; vgs; lvs
```
🔍 **تحلیل دستور:** هر سه بدون سوییچ؛ سه ابزار خلاصه‌نمایی (یک خط برای هر آیتم) در سطح PV، VG، LV به‌ترتیب؛ علامت `;` در شل به‌معنای «این سه دستور را پشت‌سرهم و مستقل اجرا کن» است .

**۵. ساخت فایل‌سیستم و mount**
```bash
mkfs.ext4 /dev/vg_test/lv_test
mkdir -p /mnt/test-lv
mount /dev/vg_test/lv_test /mnt/test-lv
```
🔍 **تحلیل دستور:** دقت کنید مسیر دستگاه LV به فرمت `/dev/<VG_NAME>/<LV_NAME>` است — این یک مسیر واقعی نیست بلکه یک symlink است که LVM خودکار می‌سازد و به دستگاه واقعی device-mapper اشاره می‌کند.

**۶. تایید نهایی**
```bash
df -h /mnt/test-lv
```

### ✅ Best Practice
همیشه بعد از هر مرحله (`pvcreate`, `vgcreate`, `lvcreate`) با دستور نمایشی متناظر (`pvs`/`vgs`/`lvs`) نتیجه را تایید کنید، قبل از رفتن به مرحله بعد.

## سناریو ۲ (مبتدی): بررسی سلامت SMART یک دیسک قبل از استفاده در Production (سطح مبتدی)

### زمینه و چرایی
قبل از هر تصمیم پیچیده RAID/Migration، باید بتوانید ساده‌ترین کار را انجام دهید: بررسی این‌که آیا یک دیسک از نظر سخت‌افزاری سالم است.

### قدم‌به‌قدم

**۱. نصب ابزار در صورت نیاز**
```bash
apt install smartmontools -y
```

**۲. بررسی نتیجه کلی سلامت**
```bash
smartctl -H /dev/sda
```
🔍 **تحلیل دستور:** `-H` مخفف `--health` — فقط یک خط نتیجه نهایی (`PASSED` یا `FAILED`)، بدون جزئیات خام.

**۳. بررسی جزئیات کامل‌تر — شمارنده‌های هشداردهنده**
```bash
smartctl -a /dev/sda | grep -i "reallocated\|pending"
```
🔍 **تحلیل دستور:**
- ا `-a`: مخفف `--all` — تمام اطلاعات SMART موجود (ده‌ها خط)، برخلاف `-H` که فقط خلاصه بود.
- ا `grep -i "reallocated\|pending"`: فیلتر فقط دو شمارنده کلیدی — `Reallocated_Sector_Count` (تعداد سکتورهایی که دیسک به‌خاطر خرابی جایگزین کرده) و `Pending` (سکتورهای مشکوکی که هنوز قطعی نشده‌اند)؛ مقادیر غیرصفر و رو به افزایش در این دو، هشدار جدی هستند.

**۴. اجرای یک تست کوتاه خودآزمایی (Self-Test)**
```bash
smartctl -t short /dev/sda
```
🔍 **تحلیل دستور:**
- ا `-t short`: مخفف `--test short` — درخواست اجرای یک تست خودآزمایی کوتاه (چند دقیقه‌ای) که خودِ فرم‌ور دیسک آن را در پس‌زمینه انجام می‌دهد.

**۵. بررسی نتیجه تست بعد از چند دقیقه**
```bash
smartctl -l selftest /dev/sda
```
🔍 **تحلیل دستور:**
- ا `-l selftest`: مخفف `--log selftest` — نمایش تاریخچه/نتیجه تست‌های خودآزمایی قبلی، شامل همان تستی که در مرحله قبل درخواست دادیم.

### 📌 نکته آزمون
همیشه قبل از قرار دادن یک دیسک جدید (حتی نو) در Production، حداقل یک بررسی `-H` انجام دهید — دیسک‌های معیوب کارخانه‌ای نادر اما واقعی هستند.

## سناریو ۳: مهاجرت آنلاین داده از یک دیسک قدیمی به یک دیسک جدید بدون قطعی سرویس (سطح پیشرفته)

### قدم‌به‌قدم

**۱. تشخیص اولیه با SMART (طبق سناریو ۲)**
```bash
smartctl -a /dev/sdb | grep -E "Reallocated_Sector|Current_Pending|Offline_Uncorrectable"
```
🔍 **تحلیل دستور:** `-E` در `grep` مخفف `--extended-regexp`، فعال‌سازی regex پیشرفته که اجازه استفاده از `|` بین چند الگو را بدون escape می‌دهد.

**۲. آماده‌سازی دیسک جدید**
```bash
pvcreate /dev/sde1
vgextend vg_data /dev/sde1
```
🔍 **تحلیل دستور:**
- ا `vgextend`: اضافه کردن یک PV **جدید** به یک VG **موجود** (برخلاف `vgcreate` که VG جدید می‌سازد)؛ آرگومان اول نام VG هدف، دومی PV جدید.

**۳. انتقال زنده داده**
```bash
pvmove /dev/sdb1 /dev/sde1
```
🔍 **تحلیل دستور:**
- ا `pvmove`: دستور اختصاصی مهاجرت داده بین دو PV.
- دو آرگومان: PV مبدا (که می‌خواهیم خالی شود) و PV مقصد (که داده به آن منتقل می‌شود)؛ اگر آرگومان دوم داده نشود، LVM خودش هر PV آزاد دیگری در همان VG را انتخاب می‌کند.

**۴. نظارت بر پیشرفت در یک ترمینال دیگر**
```bash
watch -n 5 'pvs -o pv_name,pv_used,move_pv'
```
🔍 **تحلیل دستور:**
- ا `watch`: اجرای مکرر یک دستور با فاصله زمانی مشخص و نمایش زنده رفرش‌شونده.
- ا `-n 5`: مخفف فاصله زمانی — هر ۵ ثانیه یک‌بار اجرا کن.
- ا `'pvs -o pv_name,pv_used,move_pv'`: دستور داخل کوتیشن؛ `-o` در `pvs` انتخاب دقیق ستون‌های خروجی (نام PV، فضای استفاده‌شده، وضعیت Move).

**۵. حذف رسمی PV قدیمی بعد از اتمام**
```bash
vgreduce vg_data /dev/sdb1
pvremove /dev/sdb1
```
🔍 **تحلیل دستور:**
- ا `vgreduce`: عکس `vgextend` — یک PV را از VG خارج می‌کند (فقط اگر دیگر هیچ Extent فعالی روی آن نباشد).
- ا`pvremove`: پاک کردن کامل متادیتای LVM از روی دستگاه، بازگرداندن آن به حالت «خام».

### ✅ Best Practice
همیشه پیشرفت `pvmove` را با `watch` رصد کنید و همزمان (در ترمینال سوم) سلامت سرویس واقعی را با یک حلقه تست ساده تایید کنید تا مطمئن شوید واقعاً بدون قطعی است.

## سناریو ۴: بازیابی یک آرایه RAID 5 بعد از خرابی و شناسایی نادرست دیسک‌ها (سطح پیشرفته)

### قدم‌به‌قدم

**۱. بررسی وضعیت فعلی**
```bash
cat /proc/mdstat
```
🔍 **تحلیل دستور:** بدون سوییچ؛ `/proc/mdstat` یک فایل مجازی است که کرنل آن را زنده از وضعیت داخلی ماژول RAID می‌سازد.

**۲. اسکن دستی دیسک‌ها**
```bash
mdadm --examine --scan
```
🔍 **تحلیل دستور:**
- ا `--examine`: بررسی مستقیم متادیتای RAID که هر دیسک عضو، خودش در ابتدا/انتهای خودش ذخیره کرده — کار بدون نیاز به `mdadm.conf`.
- ا `--scan`: به‌جای نیاز به دادن نام هر دیسک جداگانه، تمام دیسک‌های سیستم را خودکار اسکن می‌کند و خروجی را در فرمت آماده برای `mdadm.conf` چاپ می‌کند.

**۳. بررسی جزئیات یک دیسک خاص**
```bash
mdadm --examine /dev/sdb1
```
🔍 **تحلیل دستور:** همان `--examine`، این‌بار با یک آرگومان مسیر مشخص به‌جای `--scan` — جزئیات کامل این یک دیسک خاص (Array UUID، نقش آن در آرایه) را نشان می‌دهد.

**۴. بازسازی امن آرایه موجود**
```bash
mdadm --assemble /dev/md0 /dev/sdb1 /dev/sdc1 /dev/sdd1
```
🔍 **تحلیل دستور:**
- ا `--assemble`: تلاش برای کنار هم گذاشتن یک آرایه **موجود** از دیسک‌هایی که متادیتای سازگار دارند — این عملیات ایمن است و داده را از بین نمی‌برد.
- اولین آرگومان بعد از `--assemble` نام دستگاه هدف (`/dev/md0`) است؛ بقیه آرگومان‌ها لیست دیسک‌های عضو.

⚠️ هرگز به‌جای `--assemble` از `--create` روی دیسک‌های حاوی داده استفاده نکنید — `--create` متادیتا را از صفر می‌نویسد و می‌تواند داده موجود را عملاً غیرقابل‌بازیابی کند.

**۵. جایگزینی یک دیسک خراب**
```bash
mdadm /dev/md0 --add /dev/sde1
```
🔍 **تحلیل دستور:**
- بدون پیشوند `--` قبل از نام دستگاه (`/dev/md0`) — این یک استثنای syntax `mdadm` است: نام آرایه هدف اول می‌آید، سپس عملیات (`--add`) و آرگومان آن.
- ا `--add`: اضافه کردن یک دیسک جدید به آرایه موجود، که بلافاصله فرآیند rebuild خودکار (بازسازی داده روی دیسک جدید بر اساس Parity) را شروع می‌کند.

**۶. بازنویسی mdadm.conf**
```bash
mdadm --detail --scan > /etc/mdadm/mdadm.conf.new
```
🔍 **تحلیل دستور:**
- ا `--detail --scan`: ترکیب دو سوییچ — نمایش اطلاعات دقیق تمام آرایه‌های **فعال** فعلی (برخلاف `--examine --scan` که دیسک‌های خام را می‌خواند) در فرمت آماده برای فایل تنظیمات.
- `>`: نوشتن در یک فایل **جدید** (`.new`) به‌جای بازنویسی مستقیم فایل اصلی — یک قدم احتیاطی برای بررسی محتوا قبل از جایگزینی نهایی.

### 📌 نکته آزمون
تفاوت `--assemble` (بازسازی امن) و `--create` (بالقوه مخرب اگر روی داده موجود اشتباه اجرا شود).

## سناریو ۵: طراحی معماری کامل RAID + LUKS + LVM برای سرور دیتابیس حساس (سطح پیشرفته)

### قدم‌به‌قدم

**۱. ساخت آرایه RAID 6**
```bash
mdadm --create /dev/md0 --level=6 --raid-devices=4 /dev/sdb /dev/sdc /dev/sdd /dev/sde
```
🔍 **تحلیل دستور:**
- `--create`: اینجا (برخلاف سناریوی قبل) کاملاً صحیح است چون دیسک‌ها **کاملاً خام** هستند، نه بازسازی یک آرایه موجود.
- `--level=6`: نوع RAID (دو Parity مستقل، تحمل خرابی دو دیسک هم‌زمان).
- `--raid-devices=4`: تعداد دیسک‌های عضو فعال.

**۲. رمزنگاری کل دستگاه RAID**
```bash
cryptsetup luksFormat /dev/md0
```
🔍 **تحلیل دستور:**
- ا `luksFormat`: زیردستور `cryptsetup` برای فرمت اولیه رمزنگاری LUKS؛ آرگومان دستگاه هدف است — دقت کنید که این روی `/dev/md0` (دستگاه RAID) اجرا می‌شود، نه روی هر دیسک خام جداگانه.

**۳. باز کردن دستگاه رمزنگاری‌شده**
```bash
cryptsetup luksOpen /dev/md0 secure_db
```
🔍 **تحلیل دستور:**
- ا `luksOpen`: زیردستور باز کردن (رمزگشایی) یک دستگاه LUKS.
- دو آرگومان: دستگاه رمزنگاری‌شده مبدا، و یک **نام دلخواه** برای mapping جدید — این نام در `/dev/mapper/secure_db` ظاهر می‌شود.

**۴. اضافه کردن یک passphrase دوم**
```bash
cryptsetup luksAddKey /dev/md0
```
🔍 **تحلیل دستور:**
- ا `luksAddKey`: اضافه کردن یک passphrase جدید در یک Key Slot خالی؛ از شما یک passphrase **موجود** (برای اثبات مجاز بودن) و سپس passphrase **جدید** پرسیده می‌شود.

**۵. ساخت LVM روی دستگاه رمزگشایی‌شده**
```bash
pvcreate /dev/mapper/secure_db
vgcreate vg_dbdata /dev/mapper/secure_db
lvcreate -L 500G -n lv_postgres vg_dbdata
```
🔍 **تحلیل دستور:** همان الگوی سناریو ۱، این‌بار روی مسیر `/dev/mapper/secure_db` به‌جای یک پارتیشن مستقیم — از دید LVM هیچ فرقی نمی‌کند، چون این هم یک دستگاه بلاکی معتبر است.

**۶. پیکربندی crypttab برای بوت**
```bash
blkid /dev/md0
```
🔍 **تحلیل دستور:** همان `blkid` که در سناریو ۲ فایل ۳ دیدیم؛ اینجا برای گرفتن UUID دستگاه RAID (نه دستگاه رمزگشایی‌شده) که باید در `/etc/crypttab` استفاده شود.

### ✅ Best Practice
رمزنگاری روی دستگاه RAID (نه هر دیسک خام جداگانه) قرار می‌گیرد چون کارآمدتر است — فقط یک لایه رمزنگاری، نه چهار لایه جدا.

## سناریو ۶: تشخیص و رفع Thin Pool پر شده که باعث توقف نوشتن دیتابیس شده (سطح پیشرفته)

### قدم‌به‌قدم

**۱. بررسی گمراه‌کننده df**
```bash
df -h /var/lib/postgresql/data
```
🔍 **تحلیل دستور:** ممکن است فضای «آزاد» زیادی نشان دهد — چون `df` فضای **مجازی** اعلامی LV را می‌بیند، نه ظرفیت واقعی استخر Thin زیرین.

**۲. بررسی وضعیت واقعی استخر**
```bash
lvs -a vg_dbdata
```
🔍 **تحلیل دستور:**
- ا `-a`: مخفف `--all` روی `lvs` — بدون این سوییچ، برخی LV های داخلی (مثل خود `thinpool`) که با نقطه شروع می‌شوند در خروجی پیش‌فرض مخفی هستند؛ `-a` همه را نشان می‌دهد، شامل ستون `Data%` که درصد واقعی مصرف فیزیکی استخر است.

**۳. افزایش فوری ظرفیت استخر**
```bash
lvextend -L +100G vg_dbdata/thinpool
```
🔍 **تحلیل دستور:**
- ا `-L +100G`: علامت `+` قبل از عدد یعنی «۱۰۰ گیگابایت **اضافه کن** به اندازه فعلی»، نه «اندازه نهایی را ۱۰۰ گیگابایت کن» — تفاوت مهم؛ بدون `+`، عدد به‌عنوان اندازه **مطلق** جدید تفسیر می‌شود.
- ا `vg_dbdata/thinpool`: syntax مسیر LV به فرمت `VG/LV`، معادل `/dev/vg_dbdata/thinpool`.

**۴. راه‌اندازی مانیتورینگ خودکار**
```bash
USAGE=$(lvs --noheadings -o data_percent vg_dbdata/thinpool | tr -d ' %')
```
🔍 **تحلیل دستور:**
- ا `--noheadings`: حذف خط سرتیتر ستون از خروجی — ضروری برای استفاده در اسکریپت، چون نمی‌خواهیم متن سرتیتر جزو مقدار عددی محسوب شود.
- ا `-o data_percent`: انتخاب فقط همان یک ستون درصد مصرف.
- ا `tr -d ' %'`: حذف هم فاصله و هم علامت `%` از خروجی، تا یک عدد خام (مثل `85`) باقی بماند که بتوان آن را در شرط مقایسه عددی استفاده کرد.

### ⚠️ نکته امنیتی/عملیاتی حیاتی
ا Thin Provisioning بدون مانیتورینگ فعال بسیار خطرناک است — رسیدن به ظرفیت کامل می‌تواند باعث خرابی داده شود، نه فقط توقف نوشتن.

## جمع‌بندی مهارت‌های این بخش

- چرخه کامل و پایه ساخت LVM از صفر (PV → VG → LV → فایل‌سیستم)
- بررسی سلامت فیزیکی دیسک با SMART قبل از هر تصمیم پیچیده‌تر
- مهاجرت زنده داده با `pvmove` و نظارت با `watch`
