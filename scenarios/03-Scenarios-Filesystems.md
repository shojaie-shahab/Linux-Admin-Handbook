# سناریوهای عملی ۳: Filesystems

> پیش‌نیاز مطالعه: `theory/03-Filesystems.md`
> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

---

## سناریو ۱ (مبتدی): مشاهده Inode یک فایل و تفاوت آن با نامش (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده‌تر lsof/fsck، باید مفهوم پایه‌ای Inode را با چشم خودتان ببینید — این‌که نام فایل صرفاً یک برچسب است، نه خود فایل.

### قدم‌به‌قدم

**۱. ساخت یک فایل تست ساده**
```bash
echo "hello world" > /tmp/testfile.txt
```
🔍 **تحلیل دستور:**
- ا `echo`: چاپ یک رشته متنی.
- ا `<`: عملگر تغییر مسیر خروجی (Redirection) — به‌جای چاپ روی صفحه، خروجی `echo` مستقیماً در فایل مشخص‌شده نوشته می‌شود؛ اگر فایل وجود نداشته باشد ساخته می‌شود، اگر وجود داشته باشد بازنویسی می‌شود.

**۲. مشاهده شماره Inode این فایل**
```bash
ls -i /tmp/testfile.txt
```
🔍 **تحلیل دستور:**
- ا `-i`: مخفف `--inode` — به‌جای فقط نام فایل، شماره Inode آن را هم در ابتدای خط نمایش می‌دهد.

**۳. ساخت یک Hard Link (نام دوم برای همان Inode)**
```bash
ln /tmp/testfile.txt /tmp/testfile-link.txt
```
🔍 **تحلیل دستور:**
- ا `ln`: دستور ساخت لینک؛ بدون هیچ سوییچ، حالت پیش‌فرض آن **Hard Link** است (نه Symbolic Link که نیازمند سوییچ `-s` است).
- دو آرگومان: فایل مبدا (که Inode واقعی دارد) و نام جدید (مقصد) که به همان Inode اشاره خواهد کرد.

**۴. تایید این‌که هر دو نام همان Inode را دارند**
```bash
ls -i /tmp/testfile.txt /tmp/testfile-link.txt
```
🔍 **تحلیل دستور:** همان `-i` قبلی، این‌بار با دو آرگومان مسیر هم‌زمان؛ `ls` می‌تواند چند فایل را در یک اجرا بررسی کند — باید ببینید هر دو دقیقاً همان عدد Inode را نشان می‌دهند.

**۵. حذف نام اول و تایید این‌که داده هنوز از طریق نام دوم در دسترس است**
```bash
rm /tmp/testfile.txt
cat /tmp/testfile-link.txt
```
🔍 **تحلیل دستور:**
- ا `rm`: حذف یک نام از پوشه (نه لزوماً حذف داده واقعی، اگر نام دیگری هم به همان Inode اشاره کند).
- ا `cat`: نمایش محتوای فایل؛ همچنان باید متن `hello world` را نشان دهد — چون Inode هنوز زنده است، فقط یکی از دو نامش حذف شده.

### ✅ Best Practice
این تمرین ساده دقیقاً نشان می‌دهد چرا `rm` یک فایل همیشه به‌معنای «حذف واقعی داده» نیست — این پایه سناریوی پیچیده‌تر «فضای گمشده دیسک» در ادامه همین فایل است.

## سناریو ۲ (مبتدی): mount کردن دستی یک USB/دیسک اضافی و بررسی نوع فایل‌سیستم آن (سطح مبتدی)

### زمینه و چرایی
ساده‌ترین کار عملی روزمره یک مدیر سیستم: یک دستگاه ذخیره‌سازی جدید وصل شده، باید فهمید چیست و آن را در دسترس قرار داد.

### قدم‌به‌قدم

**۱. شناسایی دستگاه‌های بلاکی متصل به سیستم**
```bash
lsblk
```
🔍 **تحلیل دستور:** بدون سوییچ؛ نمایش درختی تمام دیسک‌ها و پارتیشن‌های شناسایی‌شده توسط کرنل، همراه با اندازه و mount point فعلی (اگر از قبل mount شده باشند).

**۲. بررسی نوع فایل‌سیستم و UUID دستگاه جدید**
```bash
blkid /dev/sdb1
```
🔍 **تحلیل دستور:**
- ا `blkid`: ابزار خواندن متادیتای فایل‌سیستم مستقیماً از دیسک (بدون نیاز به mount کردن).
- ا `/dev/sdb1`: آرگومان مشخص‌کننده دقیقاً کدام دستگاه بررسی شود؛ بدون آرگومان، `blkid` تمام دستگاه‌های شناخته‌شده را لیست می‌کند.

**۳. ساخت یک نقطه mount**
```bash
mkdir -p /mnt/usb-drive
```
🔍 **تحلیل دستور:**
- ا `mkdir`: ساخت پوشه.
- ا `-p`: مخفف `--parents` — اگر پوشه‌های والد (`/mnt`) از قبل وجود نداشته باشند، آن‌ها را هم خودکار می‌سازد؛ همچنین اگر پوشه مقصد از قبل وجود داشته باشد، برخلاف حالت پیش‌فرض `mkdir`، خطا نمی‌دهد.

**۴.انجام  mount دستی**
```bash
mount /dev/sdb1 /mnt/usb-drive
```
🔍 **تحلیل دستور:** بدون سوییچ اضافه؛ `mount` نوع فایل‌سیستم را خودش خودکار تشخیص می‌دهد (از روی متادیتای دیسک، همان چیزی که `blkid` در مرحله ۲ نشان داد) و آن را به نقطه مشخص‌شده متصل می‌کند.

**۵. تایید محتوا و فضای موجود**
```bash
df -h /mnt/usb-drive
```
🔍 **تحلیل دستور:**
- ا `df`: نمایش فضای فایل‌سیستم‌ها.
- ا `-h`: مخفف `--human-readable` — اعداد را به‌جای بایت خام، با واحدهای خوانا (K, M, G) نمایش می‌دهد.

**۶. انجام unmount ایمن قبل از جدا کردن فیزیکی دستگاه**
```bash
umount /mnt/usb-drive
```
🔍 **تحلیل دستور:** بدون سوییچ؛ اتصال را قطع می‌کند — این مرحله همیشه باید **قبل** از جدا کردن فیزیکی دستگاه انجام شود، وگرنه داده‌های در بافر نوشته‌نشده ممکن است از دست بروند.

### 📌 نکته آزمون
دقت کنید دستور `umount` است، **نه** `unmount` — یک اشتباه تایپی بسیار رایج در بین مبتدیان.

## سناریو ۳: بازیابی فضای دیسک اشغال‌شده توسط یک فایل حذف‌شده اما هنوز باز (سطح متوسط تا پیشرفته)

### زمینه و چرایی
ا `df -h` نشان می‌دهد `/var` تقریباً پر است، اما `du -sh /var/*` مطابقت ندارد — نشانه کلاسیک فایل حذف‌شده اما هنوز باز.

### قدم‌به‌قدم

**۱. مشاهده تناقض بین df و du**
```bash
du -sh /var/* 2>/dev/null | sort -rh | head -10
```
🔍 **تحلیل دستور:**
- ا `du -sh`: `-s` مخفف `--summarize` (فقط یک عدد کل برای هر آرگومان، نه هر زیرپوشه جداگانه)، `-h` خوانا.
- ا `2>/dev/null`: File Descriptor شماره ۲ (خروجی خطا) را به `/dev/null` هدایت می‌کند — پوشه‌هایی که مجوز خواندن ندارید، خطای مزاحم روی صفحه چاپ نمی‌کنند.
- ا `sort -rh`: `-r` معکوس (نزولی)، `-h` مرتب‌سازی بر اساس مقادیر خوانای انسانی (یعنی `sort` می‌فهمد `1.2G` از `800M` بزرگ‌تر است، برخلاف مرتب‌سازی متنی معمولی).
- ا `head -10`: فقط ۱۰ خط اول (۱۰ بزرگ‌ترین پوشه).

**۲. یافتن فایل‌های حذف‌شده اما هنوز باز**
```bash
lsof +L1
```
🔍 **تحلیل دستور:**
- ا `lsof`: مخفف List Open Files.
- ا `+L1`: یک سوییچ ترکیبی — `+L` فعال‌سازی فیلتر بر اساس Link Count، و عدد `1` یعنی «کمتر از ۱»، یعنی دقیقاً صفر — این فایل‌هایی را نشان می‌دهد که Link Count آن‌ها صفر است (از هر پوشه‌ای حذف شده‌اند) اما هنوز حداقل یک پردازش آن‌ها را باز نگه داشته.

**۳. بستن مجدد فایل توسط خود سرویس**
```bash
systemctl kill -s HUP rsyslogd
```
🔍 **تحلیل دستور:**
- ا `systemctl kill`: زیردستوری که به‌جای `kill` مستقیم روی PID، یک سیگنال به یک **سرویس** (بر اساس نام Unit) می‌فرستد — systemd خودش PID صحیح را پیدا می‌کند.
- ا `-s HUP`: مخفف `--signal HUP` — نام سیگنال؛ SIGHUP معمولاً به معنای «تنظیمات/فایل‌های باز را دوباره بخوان» تفسیر می‌شود.

**۴. تایید آزاد شدن فضا**
```bash
df -h /var
```
🔍 **تحلیل دستور:** همان `df -h` که در سناریو ۲ دیدیم؛ این‌بار برای بررسی این‌که فضای اشغال‌شده فوراً کاهش یافته.

**۵. راه‌حل جایگزین — ری‌استارت کامل سرویس**
```bash
systemctl restart rsyslog
```
🔍 **تحلیل دستور:** بدون سوییچ؛ ری‌استارت کامل تضمین می‌کند تمام file descriptor های قدیمی (حتی اگر SIGHUP کارساز نبود) بسته شوند.

### 📌 نکته آزمون
تفاوت «نام فایل در `ls`» و «Inode واقعی روی دیسک» — مفهومی پرتکرار در آزمون.

## سناریو ۴: تعمیر یک فایل‌سیستم خراب‌شده بعد از قطعی برق ناگهانی (سطح متوسط)

### قدم‌به‌قدم

**۱. بررسی پیام خطا در لاگ بوت**
```bash
journalctl -xb | grep -i "/data\|fsck\|ext4"
```
🔍 **تحلیل دستور:**
- ا `-xb`: ترکیب دو سوییچ تک‌حرفی — `-x` مخفف `--catalog` (اضافه کردن توضیحات تکمیلی از دیتابیس داخلی systemd برای برخی پیام‌های شناخته‌شده)، `-b` یعنی فقط بوت فعلی.
- ا `grep -i "الگو1\|الگو2\|الگو3"`: `-i` نادیده گرفتن بزرگ/کوچکی حروف؛ `\|` در grep پایه (بدون `-E`) عملگر «یا» بین چند الگو است.

**۲. اطمینان از unmount بودن**
```bash
umount /dev/sdb1 2>/dev/null
```
🔍 **تحلیل دستور:** `2>/dev/null` مخفی کردن خطای احتمالی «already not mounted» که در این حالت بی‌ضرر است.

**۳. بررسی و تعمیر اجباری**
```bash
e2fsck -f /dev/sdb1
```
🔍 **تحلیل دستور:**
- ا `e2fsck`: ابزار تخصصی بررسی/تعمیر فایل‌سیستم‌های خانواده ext.
- ا `-f`: مخفف `--force` — اجبار به بررسی کامل حتی اگر فایل‌سیستم قبلاً «تمیز» علامت خورده باشد؛ بدون این سوییچ، `e2fsck` معمولاً بررسی را رد می‌کند اگر فلگ کثیف فعال نباشد.

**۴. پاسخ خودکار به سوالات تعمیر**
```bash
e2fsck -y /dev/sdb1
```
🔍 **تحلیل دستور:**
- ا `-y`: مخفف `--yes` — به‌جای توقف و پرسیدن تک‌تک سوالات تعمیر از کاربر، به‌طور خودکار `yes` پاسخ می‌دهد؛ برای اجرای بدون نظارت (مثل یک اسکریپت) استفاده می‌شود.

**۵. بررسی محتوای lost+found**
```bash
ls -la /data/lost+found/
```
🔍 **تحلیل دستور:** همان `-l` (جزئیات) و `-a` (فایل مخفی) که قبلاً دیدیم؛ فایل‌های بازیابی‌شده اینجا نام Inode Number را به‌عنوان نام فایل دارند، نه نام اصلی‌شان.

**۶. شناسایی نوع محتوای فایل‌های بی‌نام**
```bash
file /data/lost+found/*
```
🔍 **تحلیل دستور:**
- ا `file`: ابزاری که با بررسی محتوای واقعی فایل (نه پسوند نام آن) نوع آن را حدس می‌زند (متن، تصویر، آرشیو و...).
- ا `*`: کاراکتر جایگزین (Wildcard) شل — قبل از اجرای `file`، شل خودش این ستاره را با **لیست تمام فایل‌های** داخل آن پوشه جایگزین می‌کند؛ یعنی `file` همه فایل‌ها را هم‌زمان به‌عنوان آرگومان‌های جداگانه دریافت می‌کند.

**۷. بررسی سلامت فیزیکی دیسک**
```bash
smartctl -H /dev/sdb
```
🔍 **تحلیل دستور:**
- ا `smartctl`: ابزار خواندن اطلاعات SMART (سلامت داخلی) دیسک.
- ا `-H`: مخفف `--health` — فقط نتیجه کلی سلامت (PASSED/FAILED) را نشان می‌دهد، نه تمام جزئیات خام SMART.

### ⚠️ نکته امنیتی/عملیاتی
فایل‌های بازیابی‌شده در `lost+found` ممکن است داده حساس داشته باشند — با احتیاط مدیریت شوند.

## سناریو ۵: راه‌اندازی Bind Mount برای اشتراک امن داده بین دو مسیر (سطح متوسط)

### قدم‌به‌قدم

**۱. ساخت پوشه مقصد**
```bash
mkdir -p /srv/jail/image-processor/uploads
```

**۲. برقراری Bind Mount**
```bash
mount --bind /srv/app/uploads /srv/jail/image-processor/uploads
```
🔍 **تحلیل دستور:**
- `--bind`: سوییچ ویژه‌ای که رفتار `mount` را کاملاً تغییر می‌دهد — به‌جای اتصال یک دستگاه/فایل‌سیستم، محتوای یک **پوشه موجود** را در مسیر دوم هم در دسترس قرار می‌دهد؛ هر دو مسیر به همان بلاک‌های فیزیکی دیسک اشاره می‌کنند، بدون کپی.

**۳. تست هم‌زمانی**
```bash
echo "test" > /srv/app/uploads/test.jpg
cat /srv/jail/image-processor/uploads/test.jpg
```
🔍 **تحلیل دستور:** همان الگوی `echo >` و `cat` که در سناریو ۱ دیدیم؛ این‌بار برای اثبات این‌که تغییر در یک مسیر، بلافاصله در مسیر دیگر هم دیده می‌شود.

**۴. تبدیل به فقط‌خواندنی با remount**
```bash
mount -o remount,bind,ro /srv/jail/image-processor/uploads
```
🔍 **تحلیل دستور:**
- `-o remount,bind,ro`: سه گزینه با کاما جدا شده در یک سوییچ `-o` — `remount` یعنی mount موجود را دوباره با گزینه‌های جدید اعمال کن (بدون unmount کامل)، `bind` یادآوری این‌که این هنوز یک Bind Mount است، و `ro` (read-only) محدودیت نوشتن جدید.

**۵. تایید محدودیت**
```bash
echo "should fail" > /srv/jail/image-processor/uploads/hacker-attempt.txt
```
🔍 **تحلیل دستور:** همان `echo >`؛ این‌بار باید با خطای سیستم‌عامل «Read-only file system» مواجه شود، نه یک خطای دستوری.

### ✅ Best Practice
Bind Mount با `ro` برای اشتراک امن داده با یک محیط کم‌اعتماد، بدون ریسک نوشتن یا کپی داده.

## سناریو ۶: انتخاب و مقایسه عملی ext4 در برابر XFS برای یک بار کاری مشخص (سطح پیشرفته)

### قدم‌به‌قدم

**۱. ساخت دو فایل‌سیستم برای مقایسه**
```bash
mkfs.ext4 /dev/sdb1
mkfs.xfs /dev/sdc1
```
🔍 **تحلیل دستور:** هرکدام بدون سوییچ اضافه؛ `mkfs.<type>` یک الگوی نام‌گذاری استاندارد است — پسوند نام دستور خودش نوع فایل‌سیستم را مشخص می‌کند (معادل `mkfs -t ext4` هم هست، اما فرم `mkfs.ext4` رایج‌تر است).

**۲. تست نوشتن فایل بزرگ متوالی**
```bash
dd if=/dev/zero of=/mnt/test-ext4/bigfile.bin bs=1M count=5000 conv=fdatasync status=progress
```
🔍 **تحلیل دستور:**
- ا `if=/dev/zero`: مخفف Input File — منبع داده، اینجا `/dev/zero` که یک جریان بی‌نهایت از بایت صفر تولید می‌کند (مناسب تست کارایی، چون خود محتوا اهمیتی ندارد).
- ا `of=...`: مخفف Output File — مقصد نوشتن.
- ا `bs=1M`: مخفف Block Size — اندازه هر بلاک خواندن/نوشتن؛ بلاک‌های بزرگ‌تر معمولاً کارایی بهتری در تست‌های Sequential دارند.
- ا `count=5000`: تعداد بلاک‌ها؛ با `bs=1M`، مجموع = ۵۰۰۰ مگابایت = تقریباً ۵ گیگابایت.
- ا `conv=fdatasync`: مخفف Conversion — قبل از پایان دستور، اطمینان حاصل می‌کند داده واقعاً روی دیسک نوشته شده (نه فقط در کش حافظه)، تا زمان‌سنجی واقعی باشد.
- ا `status=progress`: نمایش زنده پیشرفت (سرعت و درصد) در حین اجرا؛ بدون این سوییچ، `dd` هیچ خروجی‌ای تا پایان کامل نشان نمی‌دهد.

**۳. پاک کردن کش قبل از تست خواندن**
```bash
echo 3 > /proc/sys/vm/drop_caches
```
🔍 **تحلیل دستور:** نوشتن مستقیم در یک فایل مجازی kernel (همان الگوی `/proc/sys` که در بخش ۲ دیدیم)؛ مقدار `3` یعنی «هم کش صفحات، هم dentries و inode ها را پاک کن» — بدون این، تست خواندن بعدی ممکن است سرعت RAM را اندازه بگیرد، نه سرعت واقعی دیسک.

**۴. تست ساخت فایل‌های کوچک زیاد**
```bash
time (for i in {1..10000}; do touch /mnt/test-ext4/file_$i.txt; done)
```
🔍 **تحلیل دستور:**
- ا `time (...)`: پیشوند اندازه‌گیری زمان اجرای کل دستور داخل پرانتز؛ پرانتز یک **subshell** می‌سازد که کل حلقه داخل آن یک واحد واحد برای اندازه‌گیری محسوب شود.
- ا `for i in {1..10000}; do ... done`: حلقه شل با Brace Expansion — `{1..10000}` به شل می‌گوید این را به دنباله اعداد ۱ تا ۱۰۰۰۰ باز کن؛ برای هر عدد، متغیر `i` مقداردهی و بدنه حلقه اجرا می‌شود.
- ا `touch /mnt/.../file_$i.txt`: `$i` مقدار متغیر حلقه را در نام فایل جایگذاری می‌کند، پس هر تکرار یک فایل با نام متفاوت می‌سازد.

**۵. رشد آنلاین XFS**
```bash
xfs_growfs /mnt/test-xfs
```
🔍 **تحلیل دستور:** بدون سوییچ اضافه؛ نکته مهم syntax — آرگومان این دستور **mount point** است (`/mnt/test-xfs`)، نه نام دستگاه؛ چون XFS برای رشد نیازمند فعال و mount بودن فایل‌سیستم است.

### 📌 نکته آزمون
ا `resize2fs` مسیر دستگاه می‌گیرد، `xfs_growfs` مسیر mount point می‌گیرد — تفاوت syntax رایج‌ترین اشتباه مبتدیان.

## جمع‌بندی مهارت‌های این بخش

- درک عملی و دیداری تفاوت نام فایل و Inode با `ls -i` و Hard Link
- ا mount/unmount دستی پایه یک دستگاه ذخیره‌سازی جدید
- تشخیص و رفع «فضای گمشده دیسک» با `lsof +L1` و تحلیل دقیق این سوییچ
- تعمیر فایل‌سیستم خراب با `e2fsck -f`/`-y` و کار با `lost+found`
- ا Bind Mount امن با `mount --bind` و تبدیل به فقط‌خواندنی با `remount`
- مقایسه عملی و مبتنی‌بر داده ext4/XFS با تحلیل کامل هر سوییچ `dd`
