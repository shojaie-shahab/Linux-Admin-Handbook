# سناریوهای عملی ۲: Linux Kernel

> پیش‌نیاز مطالعه: `theory/02-Linux-Kernel.md`
> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

---

## سناریو ۱ (مبتدی): مشاهده و شمارش پردازش‌های در حال اجرا با ps و مقایسه با top (سطح مبتدی)

### زمینه و چرایی
قبل از سراغ رفتن به سناریوهای پیچیده کشتن/تشخیص پردازش، باید با ابزار پایه `ps` (که یک عکس لحظه‌ای می‌گیرد) و تفاوتش با `top` (که زنده و پیوسته است) راحت باشید.

### قدم‌به‌قدم

**۱. لیست ساده تمام پردازش‌های سیستم**
```bash
ps aux
```
🔍 **تحلیل دستور:**
- ا `ps`: ابزار اصلی نمایش وضعیت پردازش‌ها (Process Status).
- ا `aux`: سه حرف که **بدون خط تیره** نوشته می‌شوند (یک قرارداد تاریخی BSD-style) — `a` یعنی نمایش پردازش‌های همه کاربران، `u` یعنی فرمت خروجی شامل اطلاعات کاربر مالک و مصرف منابع باشد، `x` یعنی پردازش‌هایی که به یک ترمینال متصل نیستند هم نمایش داده شوند.

**۲. شمارش کل پردازش‌های سیستم**
```bash
ps aux | wc -l
```
🔍 **تحلیل دستور:**
-  ا `wc`: مخفف Word Count.
- ا `-l`: مخفف `--lines` — به‌جای شمارش کلمات، فقط تعداد خطوط ورودی را می‌شمارد؛ چون هر پردازش دقیقاً یک خط در خروجی `ps aux` است، این عدد تقریباً معادل «چند پردازش در حال اجراست».

**۳. مشاهده فقط ۵ پردازش پرمصرف‌ترین از نظر CPU**
```bash
ps aux --sort=-%cpu | head -6
```
🔍 **تحلیل دستور:**
- ا `--sort=-%cpu`: سوییچ مرتب‌سازی؛ نام ستون بعد از `=` می‌آید، و علامت `-` قبل از نام ستون یعنی ترتیب **نزولی** (بیشترین اول).
- ا `head -6`: نمایش فقط ۶ خط اول؛ عدد ۶ چون خط اول همیشه سرتیتر ستون‌هاست، نه یک پردازش واقعی.

**۴. مقایسه با نمای زنده top در حالت غیرتعاملی**
```bash
top -n 1 -b
```
🔍 **تحلیل دستور:**
- ا `-n 1`: مخفف `--iterations 1` — به‌جای رفرش بی‌نهایت، فقط یک‌بار داده می‌گیرد و خارج می‌شود.
- ا `-b`: مخفف `--batch` — خروجی متنی ساده (مناسب اجرا کردن یک دستوراتی روی ان مثلا cut , grep و ... )، نه رابط تعاملی رفرش‌شونده.

### ✅ Best Practice
 ا `ps aux --sort=-%cpu` برای اسکریپت‌ها مناسب‌تر از `top` تعاملی است، چون خروجی ثابت (نه زنده) تولید می‌کند.

## سناریو ۲ (مبتدی): بارگذاری و بررسی یک ماژول کرنل ساده بدون تغییر دائمی (سطح مبتدی)

### زمینه و چرایی
این سناریو ساده‌ترین چرخه کامل کار با یک ماژول کرنل را نشان می‌دهد: بررسی، بارگذاری، تایید، تخلیه.

### قدم‌به‌قدم

**۱. بررسی اطلاعات یک ماژول بی‌خطر (dummy، یک اینترفیس شبکه آزمایشی)**
```bash
modinfo dummy
```
🔍 **تحلیل دستور:**
- ا `modinfo`: نمایش اطلاعات یک ماژول **بدون بارگذاری آن** — کاملاً بی‌خطر، فقط خواندن متادیتا.
- ا `dummy`: نام ماژول؛ بدون مسیر کامل، چون `modinfo` خودش در مسیرهای استاندارد جستجو می‌کند.

**۲. بررسی این‌که آیا از قبل بارگذاری شده**
```bash
lsmod | grep dummy
```
🔍 **تحلیل دستور:** `lsmod` بدون سوییچ، لیست کامل ماژول‌های بارگذاری‌شده را چاپ می‌کند؛ `grep dummy` این لیست را فقط به خطوط شامل کلمه `dummy` فیلتر می‌کند.

**۳. بارگذاری ماژول**
```bash
modprobe dummy
```
🔍 **تحلیل دستور:** `modprobe` بدون سوییچ، نام ماژول را می‌گیرد و آن را همراه با تمام وابستگی‌هایش بارگذاری می‌کند.

**۴. تایید بارگذاری موفق**
```bash
ip link show | grep dummy
```
🔍 **تحلیل دستور:** بررسی این‌که این ماژول (که یک اینترفیس شبکه مجازی می‌سازد) اثر قابل‌مشاهده‌ای هم روی سیستم گذاشته.

**۵. تخلیه ماژول (پاک‌سازی)**
```bash
modprobe -r dummy
```
🔍 **تحلیل دستور:** `-r` مخفف `--remove` — به‌جای بارگذاری، ماژول را تخلیه می‌کند؛ فقط اگر هیچ ماژول دیگری به آن وابسته نباشد موفق می‌شود.

### 📌 نکته آزمون
تفاوت `modprobe` (حل خودکار وابستگی) با `insmod`/`rmmod` (مستقیم، بدون حل وابستگی) را دقیق بدانید.

## سناریو ۳: شناسایی و کشتن یک پردازش سرکش با مصرف غیرعادی CPU (سطح متوسط)

### قدم‌به‌قدم

**۱. بررسی بار کلی سیستم**
```bash
uptime
```
🔍 **تحلیل دستور:** بدون سوییچ؛ سه عدد Load Average (میانگین ۱، ۵، ۱۵ دقیقه اخیر) که باید با `nproc` مقایسه شود.

**۲. شناسایی پردازش پرمصرف**
```bash
top -o %CPU
```
🔍 **تحلیل دستور:** `-o %CPU` پردازش‌ها را بر اساس ستون `%CPU` نزولی مرتب می‌کند.

**۳. بررسی دقیق پردازش خاص**
```bash
ps -p 4521 -o pid,ppid,ni,stat,cmd
```
🔍 **تحلیل دستور:**
- ا  `-p 4521`: مخفف `--pid` — فقط این PID خاص.
- ا `-o pid,ppid,ni,stat,cmd`: انتخاب دقیق ستون‌ها؛ `ni` (niceness) و `stat` (وضعیت مثل R/S/D/Z) دو ستون کلیدی تشخیصی هستند.

**۴. بررسی System Call ها**
```bash
strace -c -p 4521
```
🔍 **تحلیل دستور:**
- ا `-c`: مخفف `--summary-only` — به‌جای چاپ زنده هر فراخوانی، فقط جدول خلاصه آماری در پایان (بعد از Ctrl+C).
- ا `-p 4521`: اتصال به یک پردازش از قبل در حال اجرا.

**۵. خاتمه مودبانه**
```bash
kill -TERM 4521
```
🔍 **تحلیل دستور:** `kill` صرفاً یک سیگنال می‌فرستد؛ `-TERM` (معادل `-15`) درخواست مودبانه خاتمه با فرصت پاکسازی.

**۶. در صورت عدم پاسخ، اجباری**
```bash
kill -KILL 4521
```
🔍 **تحلیل دستور:** `-KILL` (معادل `-9`) هرگز به خود پردازش نمی‌رسد؛ مستقیماً توسط کرنل، بدون فرصت پاکسازی، حذف می‌شود.

### ⚠️ نکته مهم
همیشه ابتدا SIGTERM، فقط در صورت شکست SIGKILL.

## سناریو ۴: پاک‌سازی Zombie Process های انباشته‌شده (سطح پیشرفته)

### قدم‌به‌قدم

**۱. شناسایی Zombie ها**
```bash
ps aux | awk '$8 ~ /Z/ {print}'
```
🔍 **تحلیل دستور:**
- ا  `awk`: زبان پردازش متن ستونی.
-  ا `'$8 ~ /Z/ {print}'`: `$8` یعنی ستون هشتم (STAT در خروجی `ps aux`)، `~` عملگر تطبیق الگو، `/Z/` الگوی جستجو، `{print}` یعنی چاپ کل خط در صورت تطبیق.

**۲. شمارش**
```bash
ps aux | awk '$8 ~ /Z/ {print}' | wc -l
```
🔍 **تحلیل دستور:** همان دستور بالا، لوله‌کشی به `wc -l` برای تبدیل به یک عدد.

**۳. یافتن پردازش‌های پدر**
```bash
ps aux | awk '$8 ~ /Z/ {print $2}' | while read pid; do
    ppid=$(ps -o ppid= -p $pid 2>/dev/null | tr -d ' ')
    echo "Zombie PID=$pid has Parent PID=$ppid"
done
```
🔍 **تحلیل دستور:**
- `{print $2}`: 

این‌بار فقط ستون دوم (PID) چاپ می‌شود، نه کل خط.
- `while read pid; do ... done`: 

حلقه شل — برای هر خط ورودی، متغیر `pid` مقداردهی می‌شود.
- `ps -o ppid= -p $pid`:

 علامت `=` بعد از `ppid` سرتیتر ستون را حذف می‌کند، فقط مقدار خام چاپ می‌شود — ضروری برای استفاده در اسکریپت.
- `2>/dev/null`:

 تغییر مسیر خروجی خطا (File Descriptor ۲) به `/dev/null`؛ اگر پردازش دیگر وجود نداشت، آن خطا نادیده گرفته می‌شود.
- `tr -d ' '`:

 حذف کاراکترهای فاصله اضافه که `ps -o ppid=` معمولاً قبل از عدد می‌گذارد.

**۴. ارسال SIGCHLD به پدر**
```bash
kill -CHLD 890
```
🔍 **تحلیل دستور:** `-CHLD` نام سیگنال؛ به پردازش پدر اطلاع می‌دهد وضعیت فرزندش تغییر کرده، که ممکن است باعث فراخوانی `wait()` شود.

**۵. ری‌استارت کنترل‌شده پدر**
```bash
systemctl restart myapp
```
🔍 **تحلیل دستور:** بدون سوییچ اضافه؛ ری‌استارت باعث Reparenting Zombie ها به PID 1 و پاک‌سازی می‌شود.

### 📌 نکته آزمون
ا Zombie را مستقیماً نمی‌توان kill کرد؛ باید سراغ پدر رفت.

## سناریو ۵: تنظیم اولویت CPU برای اجرای هم‌زمان Backup سنگین (سطح متوسط)

### قدم‌به‌قدم

**۱. بررسی اولویت فعلی**
```bash
ps -eo pid,ni,cmd | grep -E "api-server|postgres"
```
🔍 **تحلیل دستور:**
- ا `-e`: همه پردازش‌ها (بدون محدودیت به یک PID خاص).
- ا `-E` در `grep`: مخفف `--extended-regexp` — فعال‌سازی regex پیشرفته که `|` (به‌معنای «یا») را بدون escape قبول می‌کند.

**۲. اجرا با اولویت پایین**
```bash
nice -n 15 /usr/local/bin/backup-database.sh
```
🔍 **تحلیل دستور:**
- ا `nice`: اجرای یک برنامه جدید با niceness مشخص.
- ا `-n 15`: مخفف `--adjustment 15` — عدد مثبت یعنی اولویت پایین.

**۳. ترکیب با محدودیت I/O**
```bash
ionice -c 3 nice -n 15 /usr/local/bin/backup-database.sh
```
🔍 **تحلیل دستور:**
- ا `ionice`: کنترل اولویت I/O دیسک، جداگانه از CPU.
- ا `-c 3`: مخفف `--class 3` — کلاس `idle`، دسترسی به دیسک فقط وقتی هیچ پردازش دیگری I/O نمی‌خواهد.
- این دستور تودرتوست: `ionice` خودش `nice` را اجرا می‌کند، و `nice` خودش اسکریپت را — هر دو محدودیت هم‌زمان روی پردازش نهایی اعمال می‌شوند.

**۴. تغییر اولویت پردازش در حال اجرا**
```bash
renice -n 19 -p 5678
```
🔍 **تحلیل دستور:**
- ا `renice`: برخلاف `nice` (فقط هنگام شروع)، روی پردازش **از قبل در حال اجرا** عمل می‌کند.
- ا `-p 5678`: مشخص می‌کند تغییر روی کدام PID اعمال شود.

### ✅ Best Practice
ترکیب `nice`+`ionice` (یا معادل systemd) برای هر کار پس‌زمینه سنگین.

## سناریو ۶: عیب‌یابی عدم شناسایی سخت‌افزار جدید (کارت شبکه) (سطح پیشرفته)

### قدم‌به‌قدم

**۱. بررسی شناسایی در سطح PCI**
```bash
lspci | grep -i network
```
🔍 **تحلیل دستور:** `-i` در `grep` نادیده گرفتن بزرگ/کوچک بودن حروف.

**۲. جزئیات شامل درایور فعلی**
```bash
lspci -v | grep -A 10 -i ethernet
```
🔍 **تحلیل دستور:**
- ا `-v`: مخفف `--verbose` روی `lspci` — چندین خط جزئیات شامل `Kernel driver in use:`.
- ا `-A 10` در `grep`: مخفف `--after-context=10` — ۱۰ خط بعد از خط مطابق را هم نمایش می‌دهد، چون جزئیات verbose در چند خط زیر می‌آید.

**۳. شناسه دقیق Vendor:Device**
```bash
lspci -nn | grep -i ethernet
```
🔍 **تحلیل دستور:** `-nn` نمایش شناسه‌های عددی استاندارد (مثل `8086:15b7`) در کنار نام خوانا.

**۴. بررسی وجود ماژول**
```bash
modinfo e1000e
```

**۵. بارگذاری و تایید موفقیت**
```bash
modprobe e1000e
echo $?
```
🔍 **تحلیل دستور:** `echo $?` چاپ کد خروجی آخرین دستور — `$?` متغیر ویژه شل که همیشه نتیجه موفقیت (۰) یا شکست (غیرصفر) را نگه می‌دارد.

**۶. بررسی لاگ کرنل**
```bash
dmesg | tail -30
```
🔍 **تحلیل دستور:** `tail -30` فقط ۳۰ خط آخر؛ چون پیام‌های جدید همیشه در پایین `dmesg` اضافه می‌شوند.

**۷. دائمی‌سازی**
```bash
echo "e1000e" > /etc/modules-load.d/e1000e.conf
```
🔍 **تحلیل دستور:** `>` (نه `>>`) چون این یک فایل جدید است که باید دقیقاً همین یک خط را داشته باشد.

### 📌 نکته آزمون
مسیر کامل: شناسایی فیزیکی (`lspci`) → درایور (`modinfo`) → بارگذاری (`modprobe`) → تایید (`dmesg`+`lsmod`) → دائمی‌سازی (`modules-load.d`).

## جمع‌بندی مهارت‌های این بخش

- کار پایه با `ps`/`top` و مرتب‌سازی/فیلتر خروجی برای اسکریپت‌نویسی
- چرخه کامل بارگذاری/تخلیه یک ماژول کرنل با `modprobe`
- تشخیص و خاتمه صحیح پردازش سرکش با تحلیل دقیق سوییچ‌های `ps`/`strace`
- رفع Zombie از طریق پردازش پدر با اسکریپت‌نویسی awk/while ترکیبی
- اولویت‌بندی دقیق CPU/I/O با `nice`/`ionice`/`renice`
- مسیر کامل عیب‌یابی سخت‌افزار جدید با تحلیل هر سوییچ `lspci`/`modinfo`/`modprobe`
