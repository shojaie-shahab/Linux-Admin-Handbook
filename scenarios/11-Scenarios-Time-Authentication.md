# سناریوهای عملی ۱۱: Time & Authentication

> پیش‌نیاز مطالعه: `theory/11-Time-Authentication.md`
> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

---

## سناریو ۱ (مبتدی): بررسی و همگام‌سازی دستی زمان سیستم با Chrony (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده Kerberos، باید ساده‌ترین کار — بررسی این‌که آیا ساعت سیستم درست است — را مسلط باشید.

### قدم‌به‌قدم

**۱. بررسی وضعیت کلی زمان**
```bash
timedatectl
```
🔍 **تحلیل دستور:** بدون سوییچ؛ نمایش زمان محلی، UTC، منطقه زمانی، و وضعیت فعال بودن همگام‌سازی NTP.

**۲. بررسی جزئیات دقیق همگام‌سازی Chrony**
```bash
chronyc tracking
```
🔍 **تحلیل دستور:** `chronyc`: کلاینت خط‌فرمان برای ارتباط با سرویس `chronyd`؛ `tracking`: زیردستوری که وضعیت فعلی synchronization (Stratum، میزان اختلاف) را نشان می‌دهد.

**۳. لیست منابع زمان فعلی**
```bash
chronyc sources -v
```
🔍 **تحلیل دستور:** `-v`: مخفف `--verbose` — علاوه بر لیست سرورهای NTP، توضیح ستون‌ها (نماد `*` برای منبع اصلی انتخاب‌شده) را هم نمایش می‌دهد.

**۴. اجبار به تنظیم فوری (نه تدریجی)**
```bash
chronyc makestep
```
🔍 **تحلیل دستور:** بدون سوییچ اضافه؛ اگر اختلاف بزرگ باشد، به‌جای تنظیم آرام (Slewing)، فوراً یک جهش (Step) انجام می‌دهد.

### ✅ Best Practice
همیشه `chronyc tracking` را قبل از هر عیب‌یابی مرتبط با احراز هویت (که به زمان حساس است) بررسی کنید.

## سناریو ۲ (مبتدی): ساخت یک قانون ساده sudo برای یک کاربر خاص (سطح مبتدی)

### زمینه و چرایی
قبل از طراحی سیاست‌های پیچیده چندسطحی، باید ساده‌ترین حالت — یک کاربر، یک دستور مجاز — را تجربه کنید.

### قدم‌به‌قدم

**۱. باز کردن ویرایشگر امن sudoers**
```bash
visudo
```
🔍 **تحلیل دستور:** بدون سوییچ؛ هرگز فایل `/etc/sudoers` را مستقیم با یک ویرایشگر معمولی باز نکنید — `visudo` قبل از ذخیره، صحت syntax را بررسی می‌کند.

**۲. اضافه کردن یک قانون ساده در ویرایشگر باز شده**
```
alice ALL=(root) /usr/bin/systemctl restart nginx
```
🔍 **تحلیل خط:** `alice`: کاربر هدف؛ `ALL=`: از هر ترمینالی؛ `(root)`: به‌عنوان کدام کاربر اجرا شود؛ آخرین بخش: دقیقاً کدام یک دستور (با مسیر کامل) مجاز است — نه هیچ دستور دیگری.

**۳. تست از سمت کاربر alice**
```bash
sudo -l
```
🔍 **تحلیل دستور:** `-l`: مخفف `--list` — نمایش این‌که کاربر فعلی چه دستوراتی اجازه اجرای آن‌ها با sudo را دارد.

**۴. اجرای عملی مجاز**
```bash
sudo systemctl restart nginx
```

**۵. تست دستور غیرمجاز (باید رد شود)**
```bash
sudo systemctl restart mysql
```
🔍 **تحلیل دستور:** باید با پیام `alice is not allowed to run ...` مواجه شود چون قانون فقط `nginx` را مجاز کرده بود.

### 📌 نکته آزمون
ا sudo همیشه دقیقاً همان مسیر کامل دستور تعریف‌شده را چک می‌کند — نه فقط نام برنامه.

## سناریو ۳: تشخیص و رفع شکست Kerberos ناشی از عدم همگام‌سازی زمان (سطح متوسط تا پیشرفته)

### قدم‌به‌قدم

**۱. بازتولید مشکل**
```bash
kinit alice@CORP.EXAMPLE.COM
```
🔍 **تحلیل دستور:** `kinit`: درخواست اولین بلیط (TGT) با احراز هویت رمز عبور؛ آرگومان شامل نام کاربری و Realm (با حروف بزرگ، طبق قرارداد Kerberos).

**۲. مقایسه زمان با سرور KDC**
```bash
ntpdate -q dc01.corp.example.com
```
🔍 **تحلیل دستور:** `-q`: مخفف `--query-only` — فقط اختلاف زمانی را نمایش می‌دهد، بدون واقعاً تنظیم کردن ساعت سیستم.

**۳. بررسی سرویس Chrony**
```bash
systemctl status chronyd
```

**۴. راه‌اندازی و تنظیم فوری**
```bash
systemctl enable --now chronyd
chronyc makestep
```

**۵. تست مجدد Kerberos**
```bash
kinit alice@CORP.EXAMPLE.COM
klist
```
🔍 **تحلیل دستور:** `klist` بدون سوییچ؛ نمایش تمام بلیط‌های فعلی (TGT و Service Tickets) همراه با زمان انقضای هرکدام.

### 📌 نکته آزمون
پیام خطای `Clock skew too great` همیشه یعنی مشکل زمان، نه یک مشکل واقعی در اعتبار کاربر.

## سناریو ۴: طراحی زنجیره PAM دومرحله‌ای با TOTP (سطح پیشرفته)

### قدم‌به‌قدم

**۱. راه‌اندازی TOTP برای کاربر**
```bash
google-authenticator
```
🔍 **تحلیل دستور:** بدون سوییچ اجباری؛ به‌صورت تعاملی سوالاتی می‌پرسد (مثل «آیا کد باید فقط یک‌بار قابل‌استفاده باشد») و در نهایت یک کلید مخفی و QR Code تولید می‌کند.

**۲. اضافه کردن الزام TOTP به زنجیره PAM**
```bash
echo "auth required pam_google_authenticator.so" >> /etc/pam.d/sshd
```
🔍 **تحلیل دستور:** append کردن این خط **بعد** از خط موجود `pam_unix.so` (که خودش `required` است)؛ چون هر دو `required` هستند، هر دو باید موفق شوند — نه فقط یکی.

**۳. فعال‌سازی پرسش تعاملی در SSH**
```bash
grep -E "ChallengeResponseAuthentication|UsePAM" /etc/ssh/sshd_config
```
🔍 **تحلیل دستور:** `-E` در `grep` فعال‌سازی regex پیشرفته برای جستجوی هم‌زمان دو الگو با `|`.

**۴. بررسی صحت و راه‌اندازی**
```bash
sshd -t
systemctl restart sshd
```

**۵. تست کامل با نشست موازی باز**
```bash
ssh alice@server
```

### ⚠️ نکته امنیتی حیاتی
همیشه یک نشست SSH فعال دیگر باز نگه دارید قبل از تغییر تنظیمات احراز هویت.

## سناریو ۵: یکپارچه‌سازی سرور با LDAP از طریق SSSD (سطح پیشرفته)

### قدم‌به‌قدم

**۱. تست مستقیم اتصال LDAP (قبل از SSSD)**
```bash
ldapsearch -x -H ldap://ldap.corp.example.com -b "dc=corp,dc=example,dc=com" "(uid=alice)"
```
🔍 **تحلیل دستور:**
- `-x`: احراز هویت ساده (نه SASL).
- `-H`: مخفف `--URI` — آدرس کامل سرور LDAP.
- `-b`: مخفف `--baseDN` — نقطه شروع جستجو در درخت.
- `"(uid=alice)"`: فیلتر جستجو — فقط ورودی‌هایی که `uid` آن‌ها دقیقاً `alice` است.

**۲. پیکربندی SSSD**
```bash
chmod 600 /etc/sssd/sssd.conf
```
🔍 **تحلیل دستور:** مجوز `600` (فقط مالک می‌تواند بخواند/بنویسد) اجباری است — SSSD بدون این مجوز دقیق اصلاً راه‌اندازی نمی‌شود، به‌عنوان یک اقدام امنیتی داخلی.

**۳. راه‌اندازی و تست زنجیره کامل**
```bash
systemctl enable --now sssd
getent passwd alice
```
🔍 **تحلیل دستور:** `getent` مسیر واقعی NSS→SSSD→LDAP را طی می‌کند، نه فقط ارتباط مستقیم LDAP.

**۴. تست تحمل خطا (قطعی موقت شبکه)**
```bash
iptables -A OUTPUT -d 192.168.1.10 -j DROP
ssh alice@thisserver
iptables -D OUTPUT -d 192.168.1.10 -j DROP
```
🔍 **تحلیل دستور:** `-A` افزودن قانون، `-D` حذف همان قانون (باید دقیقاً همان مشخصات را داشته باشد که با `-A` اضافه شد)؛ اگر `cache_credentials=true` باشد، لاگین باید حتی با این قطعی موفق شود.

### ✅ Best Practice
همیشه `cache_credentials = true` را در Production فعال نگه دارید.

## سناریو ۶: طراحی سیاست چندسطحی sudo با Cmnd_Alias (سطح متوسط تا پیشرفته)

### قدم‌به‌قدم

**۱. ساخت گروه‌های سیستمی**
```bash
groupadd junior-ops
usermod -aG junior-ops charlie
```
🔍 **تحلیل دستور:** `-aG`: ترکیب دو سوییچ — `-a` مخفف `--append` (اضافه به گروه‌های موجود، نه جایگزینی کامل)، `-G` مخفف `--groups` (لیست گروه‌های ثانویه)؛ بدون `-a`، این دستور کاربر را از تمام گروه‌های دیگرش خارج می‌کرد.

**۲. تعریف Alias دستوری در visudo**
```
Cmnd_Alias SERVICE_RESTART = /usr/bin/systemctl restart nginx, /usr/bin/systemctl restart php-fpm
```
🔍 **تحلیل خط:** `Cmnd_Alias`: کلمه‌کلیدی تعریف یک نام دلخواه برای گروهی از دستورات؛ نام (`SERVICE_RESTART`) با حروف بزرگ (قرارداد رایج، نه اجباری)، سپس لیست دستورات با کاما جدا.

**۳. اعمال سیاست با استفاده از Alias**
```
%junior-ops ALL = (root) SERVICE_RESTART
```
🔍 **تحلیل خط:** `%junior-ops`: علامت `%` قبل از نام یعنی این یک **گروه** است، نه یک کاربر تکی.

**۴. تست از دید کاربر**
```bash
sudo -l
```

**۵. تست شکست عمدی خارج از دسترسی مجاز**
```bash
sudo vim /etc/nginx/nginx.conf
```

### ✅ Best Practice
استفاده از `Cmnd_Alias` نگهداری بلندمدت سیاست‌های دسترسی را بسیار ساده‌تر می‌کند.

## جمع‌بندی مهارت‌های این بخش

- بررسی و همگام‌سازی پایه زمان با `timedatectl`/`chronyc`
- ساخت یک قانون ساده sudo تک‌کاربره
- تشخیص و رفع شکست Kerberos ناشی از عدم تطابق زمان
- زنجیره PAM دومرحله‌ای با TOTP و تحلیل `required` در برابر `sufficient`
- یکپارچه‌سازی LDAP از طریق SSSD با تست تحمل خطا
- سیاست چندسطحی sudo با `Cmnd_Alias` و گروه‌های سیستمی
