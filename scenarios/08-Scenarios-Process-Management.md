# سناریوهای عملی ۸: Process Management

> پیش‌نیاز مطالعه: `theory/08-Process-Management.md`
> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

## سناریو ۱ (مبتدی): مشاهده Process Group و Session یک دستور پایپی ساده (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده Namespace، باید مفهوم پایه Process Group را با یک مثال بسیار ساده لمس کنید.

### قدم‌به‌قدم

**۱. اجرای یک pipeline ساده در پس‌زمینه**
```bash
sleep 100 | sleep 100 &
```
🔍 **تحلیل دستور:** `&` در انتهای دستور، آن را در پس‌زمینه اجرا می‌کند (شل بلافاصله کنترل ترمینال را پس می‌گیرد، بدون منتظر ماندن)؛ دو `sleep` با `|` (که معمولاً برای انتقال داده استفاده می‌شود، هرچند اینجا داده واقعی رد و بدل نمی‌شود) به هم متصل شده‌اند تا یک pipeline دو-پردازشی بسازند.

**۲. مشاهده Process Group مشترک**
```bash
ps -eo pid,ppid,pgid,cmd | grep sleep
```
🔍 **تحلیل دستور:** `-eo pid,ppid,pgid,cmd`: `-e` همه پردازش‌ها، `-o` انتخاب دقیق ستون‌ها شامل `pgid` (Process Group ID) — باید ببینید هر دو پردازش `sleep` دقیقاً همان مقدار PGID را دارند.

**۳. ارسال سیگنال به کل گروه (نه فقط یک پردازش)**
```bash
kill -TERM -$(jobs -p %1)
```
🔍 **تحلیل دستور:**
- ا `jobs -p`: مخفف `--pid` روی دستور داخلی `jobs` — به‌جای فرمت کامل خروجی، فقط شماره PID هر job پس‌زمینه را چاپ می‌کند.
- ا `%1`: نمادگذاری شل برای «job شماره ۱» (اولین کار پس‌زمینه‌ای که با `&` شروع کردیم).
- علامت `-` قبل از `$(...)`: این نکته حیاتی است — وقتی به `kill` یک عدد **منفی** (یا اینجا، یک PID با پیشوند `-`) داده شود، به‌جای «این یک پردازش»، به‌معنای «این یک **Process Group**» تفسیر می‌شود؛ یعنی سیگنال به **همه** پردازش‌های آن گروه فرستاده می‌شود، نه فقط یکی.

### ✅ Best Practice
این علامت `-` قبل از PID، دقیقاً همان مکانیزمی است که Ctrl+C در ترمینال برای متوقف کردن کل یک pipeline (نه فقط یک فرمان) استفاده می‌کند.

## سناریو ۲ (مبتدی): مقایسه نتیجه nice پیش‌فرض با یک nice دستی ساده (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوی پیچیده اولویت Real-time، باید تفاوت niceness پیش‌فرض و دستی را با چشم خودتان ببینید.

### قدم‌به‌قدم

**۱. اجرای یک پردازش با niceness پیش‌فرض**
```bash
sleep 300 &
```

**۲. بررسی niceness آن**
```bash
ps -o pid,ni,cmd -p $!
```
🔍 **تحلیل دستور:**
- `$!`: یک متغیر ویژه شل که همیشه PID **آخرین پردازشی که در پس‌زمینه اجرا شد** را نگه می‌دارد — بسیار مفید برای اسکریپت‌نویسی، چون نیازی به جستجوی دستی PID نیست.
- خروجی ستون `NI` باید `0` (مقدار پیش‌فرض) باشد.

**۳. اجرای یک پردازش دیگر با اولویت پایین**
```bash
nice -n 10 sleep 300 &
```

**۴. مقایسه**
```bash
ps -o pid,ni,cmd -p $!
```
🔍 **تحلیل دستور:** همان دستور مرحله ۲، این‌بار `$!` به PID پردازش **جدیدترین** (که همین الان با `nice` اجرا شد) اشاره می‌کند؛ ستون `NI` باید `10` را نشان دهد.

**۵. تغییر niceness یک پردازش در حال اجرا**
```bash
renice -n 5 -p $!
```
🔍 **تحلیل دستور:** `-n 5`: مقدار جدید niceness؛ `-p $!`: همان پردازش قبلی، این‌بار با `renice` (نه `nice`) چون از قبل در حال اجراست.

### 📌 نکته آزمون
ا `nice` فقط برای **شروع** یک پردازش استفاده می‌شود؛ `renice` برای پردازش **از قبل در حال اجرا**.

## سناریو ۳: عیب‌یابی توقف اسکریپت پس‌زمینه بعد از قطع SSH (سطح متوسط)

### قدم‌به‌قدم

**۱. اجرای بدون محافظت (بازتولید مشکل)**
```bash
long-process.sh &
ps -eo pid,ppid,pgid,sid,cmd | grep long-process
```
🔍 **تحلیل دستور:** ستون `sid` (Session ID) نشان می‌دهد این پردازش عضو کدام Session است — باید همان SID نشست SSH فعلی باشد.

**۲. راه‌حل صحیح با nohup**
```bash
nohup long-process.sh > /var/log/long-process.log 2>&1 &
```
🔍 **تحلیل دستور:**
- ا `nohup`: اجرای برنامه طوری که سیگنال SIGHUP (که با بسته شدن نشست فرستاده می‌شود) نادیده گرفته شود.
- ا `> /var/log/long-process.log`: تغییر مسیر خروجی استاندارد (stdout، File Descriptor ۱) به یک فایل.
- ا `2>&1`: تغییر مسیر خروجی خطا (File Descriptor ۲) به **همان مقصدی که File Descriptor ۱ می‌رود** (یعنی همان فایل لاگ)؛ ترتیب این علامت‌ها مهم است — باید بعد از تغییر مسیر stdout بیاید.

**۳. جدا کردن کامل از لیست jobs شل**
```bash
disown
```
🔍 **تحلیل دستور:** بدون آرگومان، آخرین job پس‌زمینه را از لیست داخلی jobs شل کاملاً حذف می‌کند — حتی اگر شل بعداً بخواهد سیگنالی به «کارهای خودش» بفرستد، این پردازش دیگر جزو آن‌ها محسوب نمی‌شود.

**۴. روش جایگزین با tmux**
```bash
tmux new -s longtask
```
🔍 **تحلیل دستور:** `-s longtask`: مخفف `--session-name` — یک نام دلخواه برای این نشست tmux تا بعداً بتوان دقیقاً همین نشست را دوباره پیدا کرد.

**۵. اتصال مجدد بعد از قطع SSH**
```bash
tmux attach -t longtask
```
🔍 **تحلیل دستور:** `-t longtask`: مخفف `--target-session` — نام دقیق نشستی که می‌خواهید به آن متصل شوید (نه یک نشست جدید).

### 📌 نکته آزمون
سه راه‌حل (`nohup`, `tmux`, systemd service) سطوح متفاوتی از پایداری دارند.

## سناریو ۴: ایزوله‌سازی دستی یک پردازش با Namespace (سطح پیشرفته)

### قدم‌به‌قدم

**۱. ساخت Namespace جدید با ایزوله PID و شبکه**
```bash
unshare --pid --net --fork --mount-proc bash
```
🔍 **تحلیل دستور:**
- ا `--pid`: ساخت یک PID Namespace جدید — پردازش‌های داخل آن فقط خودشان را می‌بینند.
- ا `--net`: ساخت یک Network Namespace جدید — در ابتدا فقط `lo` (loopback) دارد، بدون دسترسی به شبکه واقعی.
- ا `--fork`: دستور بعدی (`bash`) در یک پردازش **فرزند** اجرا شود، نه مستقیم جایگزین شل فعلی.
- ا `--mount-proc`: mount کردن یک نمونه تازه از `/proc` برای این Namespace — بدون این، `ps` داخل Namespace جدید هنوز اطلاعات قدیمی/اشتباه نشان می‌دهد.

**۲. تایید ایزوله‌سازی PID**
```bash
ps aux
```
🔍 **تحلیل دستور:** همان دستور آشنا؛ اما این‌بار داخل Namespace، خروجی فقط ۱-۲ پردازش نشان می‌دهد (نه صدها پردازش واقعی سیستم) چون از دید این Namespace، بقیه پردازش‌ها اصلاً وجود ندارند.

**۳. تایید ایزوله‌سازی شبکه**
```bash
ip addr show
```
🔍 **تحلیل دستور:** باید فقط `lo` دیده شود — هیچ اینترفیس واقعی شبکه.

**۴. مشاهده از بیرون Namespace**
```bash
lsns -t pid
```
🔍 **تحلیل دستور:** `-t pid`: مخفف `--type` — فیلتر خروجی `lsns` فقط به Namespace هایی از نوع `pid` (نه mount، net، و بقیه انواع).

**۵. ورود مستقیم به یک Namespace موجود از بیرون**
```bash
nsenter --target 5678 --pid --net ps aux
```
🔍 **تحلیل دستور:**
- ا `--target 5678`: مخفف `-t` طولانی — PID پردازشی که Namespace های آن را می‌خواهیم وارد شویم.
- ا `--pid --net`: مشخص می‌کند فقط این دو نوع Namespace (نه همه انواع) وارد شوند.
- ا  `ps aux`: آخرین آرگومان، دستوری که باید **داخل** آن Namespace اجرا شود (نه در شل فعلی).

### ⚠️ نکته امنیتی
این تکنیک ایزوله‌سازی سبک است، نه جایگزین کامل ابزارهای امنیتی حرفه‌ای.

## سناریو ۵: رفع بحران کارایی ناشی از اولویت Real-time اشتباه (سطح پیشرفته)

### قدم‌به‌قدم

**۱. شناسایی پردازش‌های غیرمعمول کلاس زمان‌بندی**
```bash
ps -eLo pid,cls,rtprio,pri,cmd | grep -v " TS "
```
🔍 **تحلیل دستور:**
- ا `-eLo`: ترکیب سه سوییچ — `-e` همه پردازش‌ها، `-L` نمایش threadها هم (نه فقط پردازش اصلی)، `-o` انتخاب ستون‌های سفارشی شامل `cls` (کلاس زمان‌بندی).
- ا `grep -v " TS "`: مخفف `--invert-match` — به‌جای نمایش خطوط **مطابق**، خطوط **غیرمطابق** را نشان می‌دهد؛ یعنی همه چیز **به‌جز** کلاس معمولی `TS` (SCHED_OTHER) باقی می‌ماند.

**۲. کاهش فوری اولویت Real-time**
```bash
chrt -f -p 10 4521
```
🔍 **تحلیل دستور:**
- ا `-f`: مخفف `--fifo` — نگه‌داشتن کلاس `SCHED_FIFO`، فقط تغییر عدد اولویت.
- ا `-p 10`: اولویت جدید (۱۰، به‌جای ۵۰ قبلی)؛ عدد اول بعد از `chrt` همیشه مقدار اولویت است.
- آخرین عدد (`4521`): PID هدف.

**۳. بازگرداندن کامل به کلاس معمولی**
```bash
chrt -o -p 0 4521
```
🔍 **تحلیل دستور:** `-o`: مخفف `--other` — تغییر کلاس به `SCHED_OTHER` (معمولی)؛ اولویت Real-time برای این کلاس همیشه باید `0` باشد (نمی‌تواند مقدار دیگری داشته باشد).

**۴. اعطای اولویت بالا اما نه مطلق**
```bash
renice -n -10 -p 4521
```
🔍 **تحلیل دستور:** عدد منفی در `renice` (که در بخش ۲ دیدیم) اولویت بالاتر (نه Real-time، فقط nice پایین‌تر) می‌دهد.

**۵. تنظیم دائمی در سطح systemd**
```bash
mkdir -p /etc/systemd/system/audio-processor.service.d
cat > /etc/systemd/system/audio-processor.service.d/priority.conf << 'EOF'
[Service]
Nice=-10
CPUSchedulingPolicy=other
EOF
```
🔍 **تحلیل دستور:** `Nice=` و `CPUSchedulingPolicy=` معادل مستقیم سوییچ‌های `renice`/`chrt` هستند، اما در سطح تعریف Unit — طوری که با هر ری‌استارت سرویس، خودکار دوباره اعمال می‌شوند.

### ⚠️ نکته حیاتی
اولویت Real-time اشتباه می‌تواند حتی دسترسی SSH را مسدود کند.

## سناریو ۶: تشخیص گلوگاه دقیق (CPU/حافظه/I/O) در یک معماری چندلایه (سطح پیشرفته)

### قدم‌به‌قدم

**۱. بررسی هم‌زمان چند PID مشخص از نظر CPU**
```bash
pidstat -u -p 1001,2001,3001 1 10
```
🔍 **تحلیل دستور:**
- ا `-u`: مخفف `--util` روی `pidstat` — نمایش آمار مصرف CPU.
- ا `-p 1001,2001,3001`: چند PID با کاما جدا شده، بدون فاصله — همه هم‌زمان مانیتور می‌شوند.
- ا `1 10`: دو عدد در انتها، رفتاری مشابه `vmstat`/`iostat` — فاصله نمونه‌برداری (۱ ثانیه) و تعداد تکرار (۱۰ بار).

**۲. بررسی حافظه همان پردازش‌ها**
```bash
pidstat -r -p 1001,2001,3001 1 10
```
🔍 **تحلیل دستور:** `-r`: مخفف `--mem` — همان ساختار دستور، این‌بار ستون‌های حافظه (`RSS`, `%MEM`) به‌جای CPU.

**۳. بررسی I/O دیسک**
```bash
pidstat -d -p 1001,2001,3001 1 10
```
🔍 **تحلیل دستور:** `-d`: مخفف `--disk` — ستون‌های نرخ خواندن/نوشتن دیسک هر پردازش.

**۴. تایید زنده با iotop**
```bash
iotop -o -p 1001,2001,3001
```
🔍 **تحلیل دستور:** `-o`: مخفف `--only` — فقط پردازش‌هایی که واقعاً در همین لحظه I/O انجام می‌دهند نمایش داده شوند (نه لیست کامل idle ها).

### ✅ Best Practice
مانیتورینگ per-process (نه فقط آمار کلی سیستم) برای معماری‌های چندلایه ضروری است.

---

## جمع‌بندی مهارت‌های این بخش

- درک عملی Process Group با ارسال سیگنال به کل گروه (`kill -PGID`)
- مقایسه دستی niceness پیش‌فرض و تنظیم‌شده با `$!`
- سه راه‌حل مختلف برای پایداری پردازش پس‌زمینه در برابر قطع SSH
- ایزوله‌سازی عملی با `unshare`/`nsenter` و تحلیل دقیق هر سوییچ
- تشخیص و رفع بحران اولویت Real-time با `chrt`
- تشخیص دقیق گلوگاه چندبعدی با `pidstat`/`iotop`
