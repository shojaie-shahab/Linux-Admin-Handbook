# سناریوهای عملی ۱۳: Capacity Planning

> پیش‌نیاز مطالعه: `theory/13-Capacity-Planning.md`
> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

---

## سناریو ۱ (مبتدی): فعال‌سازی sysstat و اولین بررسی داده تاریخی (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده پیش‌بینی، باید مطمئن شوید sysstat اصلاً به‌درستی فعال است و داده جمع می‌کند.

### قدم‌به‌قدم

**۱. نصب**
```bash
apt install sysstat -y
```

**۲. فعال‌سازی جمع‌آوری خودکار**
```bash
sed -i 's/ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
```
🔍 **تحلیل دستور:** `sed -i 's/قدیم/جدید/'`: جایگزینی متن مستقیم در فایل (`-i`)؛ چون فایل پیش‌فرض معمولاً `ENABLED="false"` دارد، این دستور دقیقاً آن رشته را به `"true"` تغییر می‌دهد.

**۳. راه‌اندازی سرویس**
```bash
systemctl enable --now sysstat
```

**۴. بررسی اولین داده جمع‌آوری‌شده (بعد از چند دقیقه صبر)**
```bash
sar -u
```
🔍 **تحلیل دستور:** بدون سوییچ اضافه یا فایل مشخص؛ `sar` به‌طور پیش‌فرض داده **امروز** را از فایل روزانه فعلی می‌خواند.

**۵. بررسی مستقیم فایل داده خام**
```bash
ls -la /var/log/sysstat/
```
🔍 **تحلیل دستور:** باید فایل‌هایی با نام `saXX` (که XX روز ماه است) ببینید — این تایید می‌کند sysstat واقعاً در حال نوشتن داده است.

### ✅ Best Practice
همیشه بعد از فعال‌سازی sysstat روی یک سرور جدید، چند دقیقه صبر کنید و سپس با `sar -u` تایید کنید داده واقعاً جمع می‌شود.

## سناریو ۲ (مبتدی): مقایسه ساده Load Average با تعداد هسته‌ها (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده تفکیک CPU/I/O، باید ساده‌ترین محاسبه — «آیا سیستم واقعاً زیر فشار است؟» — را مسلط باشید.

### قدم‌به‌قدم

**۱. بررسی Load Average**
```bash
uptime
```
🔍 **تحلیل دستور:** بدون سوییچ؛ سه عدد به‌ترتیب میانگین ۱، ۵، و ۱۵ دقیقه اخیر.

**۲. بررسی تعداد هسته‌های واقعی**
```bash
nproc
```
🔍 **تحلیل دستور:** بدون سوییچ؛ عدد ساده تعداد هسته‌های منطقی (شامل Hyper-Threading اگر فعال باشد) در دسترس کرنل.

**۳. محاسبه دستی نسبت**
```bash
echo "Load per core: $(echo "scale=2; $(uptime | awk -F'load average: ' '{print $2}' | cut -d, -f1) / $(nproc)" | bc)"
```
🔍 **تحلیل دستور:**
- `awk -F'load average: '`: مخفف `--field-separator` — به‌جای جداکننده پیش‌فرض (فاصله)، این عبارت خاص را جداکننده قرار می‌دهد تا بتوان دقیقاً بعد از آن را استخراج کرد.
- `cut -d, -f1`: مخفف `--delimiter`/`--fields` — جدا کردن با کاما و گرفتن فقط فیلد اول (یعنی میانگین ۱ دقیقه).
- `bc`: ماشین‌حساب خط‌فرمان؛ `scale=2` تعداد ارقام اعشار خروجی را مشخص می‌کند.

### 📌 نکته آزمون
اگر نسبت Load به Core بیشتر از ۱ باشد به‌طور مداوم، یعنی سیستم واقعاً زیر فشار CPU (یا I/O، که در سناریوی بعد تفکیک می‌شود) است.

## سناریو ۳: پیش‌بینی روز اشباع فضای دیسک با داده تاریخی (سطح متوسط)

### قدم‌به‌قدم

**۱. ثبت روزانه اندازه واقعی**
```bash
echo "$(date +%Y-%m-%d),$(df --output=used /var/lib/mysql | tail -1 | tr -d ' ')" >> /var/log/capacity/db-disk.csv
```
🔍 **تحلیل دستور:**
- `df --output=used`: مخفف پارامتر انتخاب ستون خروجی — به‌جای فرمت کامل پیش‌فرض `df`، فقط ستون فضای استفاده‌شده (به کیلوبایت) چاپ می‌شود.
- `tail -1`: چون خط اول خروجی `df --output` سرتیتر است، `tail -1` فقط آخرین (و در این حالت تنها) خط داده را می‌گیرد.
- `tr -d ' '`: حذف فاصله‌های اضافه احتمالی در ابتدای عدد.

**۲. زمان‌بندی روزانه با Timer**
```bash
cat > /etc/systemd/system/track-db-disk.timer << 'EOF'
[Timer]
OnCalendar=daily
[Install]
WantedBy=timers.target
EOF
```
🔍 **تحلیل دستور:** `OnCalendar=daily`: یک کلمه‌کلیدی ساده معادل «هر روز در نیمه‌شب» — جایگزین فرمت پیچیده‌تر `*-*-* 00:00:00`.

**۳. بعد از ۳۰ روز، بررسی نرخ رشد**
```bash
head -1 /var/log/capacity/db-disk.csv
tail -1 /var/log/capacity/db-disk.csv
```
🔍 **تحلیل دستور:** `head -1` اولین رکورد ثبت‌شده (شروع دوره)، `tail -1` آخرین رکورد (اکنون) — مقایسه این دو نرخ رشد را می‌دهد.

**۴. محاسبه روز اشباع**
```bash
df -h /var/lib/mysql
```

**۵. ساخت گزارش**
```bash
cat > /root/capacity-report-$(date +%Y%m%d).txt << EOF
ظرفیت کل: 500GB
نرخ رشد میانگین: 1.2GB/روز
پیش‌بینی اشباع: حدود 54 روز دیگر
EOF
```
🔍 **تحلیل دستور:** `$(date +%Y%m%d)` در نام فایل — Command Substitution که تاریخ امروز را در نام فایل جاسازی می‌کند تا هر گزارش نام یکتا داشته باشد.

### ✅ Best Practice
هر گزارش Capacity Planning باید عدد فعلی، نرخ رشد، و تاریخ پیش‌بینی‌شده داشته باشد.

## سناریو ۴: تفکیک دقیق علت کندی — CPU در برابر I/O (سطح متوسط)

### قدم‌به‌قدم

**۱. بررسی اولیه**
```bash
uptime; nproc
```

**۲. تفکیک با vmstat**
```bash
vmstat 1 10
```
🔍 **تحلیل دستور:** دو عدد در انتها — فاصله نمونه‌برداری (۱ ثانیه) و تعداد تکرار (۱۰ بار)؛ ستون `r` (صف اجرای CPU) و `b` (منتظر I/O) کلید تفکیک هستند.

**۳. تست مستقیم I/O**
```bash
iostat -x 1 5
```
🔍 **تحلیل دستور:** `-x`: مخفف `--extended` — نمایش آمار گسترده‌تر شامل ستون `%util` که میزان اشباع واقعی دیسک را نشان می‌دهد.

**۴. شناسایی پردازش دقیق مسئول I/O**
```bash
pidstat -d 1 5
```
🔍 **تحلیل دستور:** `-d`: مخفف `--disk` — آمار I/O per-process، برای پیدا کردن دقیقاً کدام پردازش دیسک را اشغال کرده.

### 📌 نکته آزمون
ا Load Average بالا همیشه به‌معنای کمبود CPU نیست — پردازش‌های `D` (Uninterruptible Sleep) هم در محاسبه شرکت می‌کنند.

## سناریو ۵: راه‌اندازی یک داشبورد ساده خط‌فرمانی برای مرور روزانه ظرفیت (سطح متوسط)

### قدم‌به‌قدم

**۱. ساخت اسکریپت ترکیبی**
```bash
cat > /usr/local/bin/capacity-dashboard.sh << 'SCRIPT'

#!/bin/bash
echo "=== CPU ==="
echo "Load: $(uptime | awk -F'load average:' '{print $2}') | Cores: $(nproc)"
echo "=== Memory ==="
free -h | grep Mem
echo "=== Disk ==="
df -h --output=target,pcent | grep -v Mounted
SCRIPT


chmod +x /usr/local/bin/capacity-dashboard.sh
```
🔍 **تحلیل دستور:**
- `free -h | grep Mem`: `free -h` نمایش خوانای حافظه؛ `grep Mem` فیلتر فقط خط مربوط به RAM (نه خط Swap که جداگانه است).
- `df -h --output=target,pcent`: انتخاب فقط دو ستون (نقطه mount و درصد اشغال)، به‌جای فرمت کامل پیش‌فرض که ستون‌های اضافی دارد.
- `grep -v Mounted`: `-v` معکوس — حذف خط سرتیتر (که شامل کلمه Mounted است) از خروجی.

**۲. اجرا**
```bash
capacity-dashboard.sh
```

### ✅ Best Practice
یک اسکریپت داشبورد ساده که هر صبح مرور می‌شود، مؤثرتر از انتظار برای هشدار بحرانی است.

## سناریو ۶: پیش‌بینی نیاز به هسته CPU بیشتر بر اساس روند Load تاریخی (سطح پیشرفته)

### قدم‌به‌قدم

**۱. بررسی Load در یک بازه ساعتی خاص از یک روز گذشته**
```bash
sar -q -f /var/log/sysstat/sa15 -s 09:00:00 -e 11:00:00
```
🔍 **تحلیل دستور:**
- `-f /var/log/sysstat/sa15`: خواندن از فایل داده تاریخی روز پانزدهم (نه داده امروز).
- `-s 09:00:00`: مخفف `--start` — کران پایین بازه زمانی.
- `-e 11:00:00`: مخفف `--end` — کران بالای بازه؛ این دو با هم فقط داده بین ساعت ۹ تا ۱۱ صبح را نشان می‌دهند.

**۲. مقایسه با ظرفیت فعلی**
```bash
nproc
```

**۳. مستندسازی روند**
```bash
cat > /root/cpu-capacity-trend.txt << EOF
هسته‌های فعلی: 4
میانگین Load ساعت پیک: 3.4
توصیه: ارتقا ظرف 2 ماه آینده
EOF
```

### 📌 نکته آزمون
تفاوت بین اسپیک موقت و روند پایدار فقط با داده تاریخی چندروزه/چندهفته‌ای قابل تشخیص است.

---

## جمع‌بندی مهارت‌های این بخش

- فعال‌سازی و تایید پایه sysstat
- محاسبه دستی نسبت Load به Core با ترکیب `awk`/`cut`/`bc`
- ثبت و تحلیل روند رشد دیسک با زمان‌بندی خودکار
- تفکیک دقیق CPU در برابر I/O با `vmstat`/`iostat`/`pidstat`
- ساخت داشبورد ساده خط‌فرمانی برای مرور روزانه
- پیش‌بینی نیاز به ارتقای CPU بر اساس روند تاریخی Load در بازه‌های خاص
