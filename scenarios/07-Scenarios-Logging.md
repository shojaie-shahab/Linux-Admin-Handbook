# سناریوهای عملی ۷: Logging

> پیش‌نیاز مطالعه: `theory/07-Logging.md`
> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

---

## سناریو ۱ (مبتدی): جستجوی ساده در لاگ سیستم برای یک بازه زمانی و یک سرویس خاص (سطح مبتدی)

### زمینه و چرایی
قبل از فیلترهای پیشرفته journald، باید ساده‌ترین و پرکاربردترین حالت جستجو (بازه زمانی + یک سرویس) را با دست خودتان امتحان کرده باشید.

### قدم‌به‌قدم

**۱. مشاهده لاگ‌های همین امروز**
```bash
journalctl --since today
```
🔍 **تحلیل دستور:** `--since today`: مقدار `today` یک کلمه‌کلیدی خاص است که journald آن را به «نیمه‌شب امروز تا الان» تفسیر می‌کند — نیازی به نوشتن تاریخ کامل نیست.

**۲. محدود کردن به یک سرویس خاص**
```bash
journalctl --since today -u sshd
```
🔍 **تحلیل دستور:** `-u sshd`: مخفف `--unit` — فقط پیام‌های مربوط به این یک Unit؛ می‌توان چند بار `-u` تکرار کرد برای چند سرویس هم‌زمان.

**۳. جستجوی یک بازه زمانی دقیق**
```bash
journalctl --since "09:00" --until "11:00"
```
🔍 **تحلیل دستور:** وقتی فقط ساعت (بدون تاریخ) نوشته شود، journald آن را برای **امروز** تفسیر می‌کند؛ `--until` کران بالای بازه را مشخص می‌کند — بدون آن، جستجو تا همین الان ادامه می‌یابد.

**۴. نمایش فقط سطر‌های خطا**
```bash
journalctl -p err
```
🔍 **تحلیل دستور:** `-p err`: مخفف `--priority` — فقط پیام‌هایی با سطح `err` یا بالاتر (`crit`, `alert`, `emerg`)؛ سطوح پایین‌تر (`info`, `debug`, `warning`) فیلتر می‌شوند.

**۵. حالت زنده (دنبال کردن لاگ جدید)**
```bash
journalctl -f
```
🔍 **تحلیل دستور:** `-f`: مخفف `--follow` — به‌جای نمایش یک‌باره و خروج، صفحه باز می‌ماند و هر پیام جدید بلافاصله نمایش داده می‌شود (مثل `tail -f`).

### ✅ Best Practice
ترکیب `--since`/`--until`/`-u`/`-p` قبل از هر بررسی طولانی، حجم داده را به چیزی قابل‌مدیریت کاهش می‌دهد.

## سناریو ۲ (مبتدی): ارسال یک پیام دستی به سیستم لاگ و پیدا کردن آن (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده rsyslog، باید بفهمید چگونه یک اسکریپت ساده می‌تواند پیام خودش را وارد زنجیره لاگ کند.

### قدم‌به‌قدم

**۱. ارسال یک پیام ساده**
```bash
logger "This is a test message from training"
```
🔍 **تحلیل دستور:** `logger` بدون سوییچ، پیام را با facility/priority پیش‌فرض (`user.notice`) به سیستم لاگ می‌فرستد.

**۲. جستجوی همان پیام**
```bash
journalctl | grep "training"
```

**۳. ارسال با یک برچسب (tag) سفارشی برای شناسایی راحت‌تر**
```bash
logger -t my-test-script "Custom tagged message"
```
🔍 **تحلیل دستور:** `-t`: مخفف `--tag` — به‌جای نام پیش‌فرض (که معمولاً نام کاربر یا شل است)، یک برچسب دلخواه برای این پیام تنظیم می‌کند تا بعداً راحت‌تر فیلتر شود.

**۴. جستجو بر اساس این برچسب**
```bash
journalctl -t my-test-script
```
🔍 **تحلیل دستور:** `-t` در `journalctl` (مخفف `--identifier`) دقیقاً همان مکانیزم برچسب `logger -t` را برای فیلتر کردن استفاده می‌کند.

**۵. ارسال با یک سطح اهمیت (Priority) مشخص**
```bash
logger -p local0.warning "This is a warning-level test"
```
🔍 **تحلیل دستور:** `-p local0.warning`: مخفف `--priority` — فرمت `facility.priority`؛ اینجا `local0` (یک facility رزروشده برای استفاده سفارشی برنامه‌ها) و سطح `warning`.

### 📌 نکته آزمون
ا `logger -t` و `journalctl -t` (Identifier) دو طرف یک مکانیزم واحد برای ردیابی راحت پیام‌های خودساخته هستند.

## سناریو ۳: عیب‌یابی رویداد امنیتی گذشته با فیلترهای پیشرفته journalctl (سطح متوسط تا پیشرفته)

### قدم‌به‌قدم

**۱. محدود کردن بازه زمانی دقیق**
```bash
journalctl --since "2026-08-14 02:00:00" --until "2026-08-14 04:00:00" --no-pager | wc -l
```
🔍 **تحلیل دستور:** `--no-pager`: به‌طور پیش‌فرض `journalctl` خروجی طولانی را در یک صفحه‌بند تعاملی (مثل `less`) نمایش می‌دهد؛ این سوییچ آن را غیرفعال می‌کند تا خروجی مستقیم قابل پایپ به `wc -l` باشد.

**۲. فیلتر بر اساس UID دقیق**
```bash
journalctl --since "2026-08-14 02:00:00" --until "2026-08-14 04:00:00" _UID=1005
```
🔍 **تحلیل دستور:** `_UID=1005` (بدون خط تیره جلوی آن) یک **فیلد ساخت‌یافته** journald است، نه یک سوییچ خط‌فرمان معمولی — این‌ها فیلدهای متادیتای داخلی (مثل `_PID=`, `_COMM=`) هستند که مستقیماً به‌عنوان یک آرگومان جستجو نوشته می‌شوند.

**۳. نمایش تمام فیلدهای پنهان هر پیام**
```bash
journalctl -o verbose | grep -B5 "_COMM="
```
🔍 **تحلیل دستور:**
- `-o verbose`: مخفف `--output verbose` — به‌جای فرمت خلاصه معمول، تمام فیلدهای داخلی هر پیام (شامل مسیر فایل اجرایی، Cgroup) را نمایش می‌دهد.
- `grep -B5`: مخفف `--before-context=5` — علاوه بر خط مطابق، ۵ خط **قبل** از آن را هم نشان می‌دهد؛ چون در فرمت verbose، فیلدهای یک پیام واحد در چند خط پشت‌سرهم می‌آیند.

**۴. صادر کردن به فرمت JSON برای مستندسازی**
```bash
journalctl --since "2026-08-14 02:00:00" _UID=1005 -o json > /root/incident.json
```
🔍 **تحلیل دستور:** `-o json`: خروجی هر پیام به‌عنوان یک شیء JSON مستقل، مناسب پردازش خودکار توسط اسکریپت‌ها یا ابزارهای تحلیلی دیگر.

### 📌 نکته آزمون
فیلترهای فیلد ساخت‌یافته (`_UID=`, `_PID=`, `_COMM=`) دقیق‌تر و سریع‌تر از `grep` روی متن آزاد هستند.

## سناریو ۴: راه‌اندازی سرور Syslog مرکزی امن (سطح پیشرفته)

### قدم‌به‌قدم

**۱. فعال‌سازی دریافت TCP با Template پویا**
```bash

cat > /etc/rsyslog.d/10-remote-receiver.conf << 'EOF'
module(load="imtcp")
input(type="imtcp" port="6514")
template(name="RemoteHostLogs" type="string"
         string="/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log")
if $fromhost-ip != '127.0.0.1' then {
    action(type="omfile" dynaFile="RemoteHostLogs")
    stop
}
EOF
```
🔍 **تحلیل دستور:** `%HOSTNAME%` و `%PROGRAMNAME%` نمادهای Template پویا rsyslog — برای هر پیام دریافتی، این‌ها با مقادیر واقعی همان پیام (نام هاست فرستنده، نام برنامه) جایگزین می‌شوند، و یک مسیر فایل منحصربه‌فرد می‌سازند.

**۲. باز کردن پورت فقط برای شبکه داخلی**
```bash
firewall-cmd --permanent --zone=internal --add-port=6514/tcp
firewall-cmd --permanent --zone=internal --add-source=192.168.0.0/16
```
🔍 **تحلیل دستور:** `--zone=internal`: به‌جای zone پیش‌فرض `public`، این قانون را در zone با سطح اعتماد بالاتر تعریف می‌کند؛ `--add-source`: محدود کردن این zone فقط به ترافیک از یک رنج IP مشخص.

**۳. پیکربندی سمت کلاینت با TCP**
```bash
echo "*.*    @@central-syslog.internal.example.com:6514" >> /etc/rsyslog.d/90-forward.conf
```
🔍 **تحلیل دستور:** `@@` (دو @) صراحتاً یعنی ارسال با پروتکل **TCP**؛ یک `@` تنها یعنی UDP — این تفاوت یک کاراکتری، قابلیت‌اطمینان کل مسیر ارسال لاگ را تعیین می‌کند.

**۴. تست عملی**
```bash
logger -t test-central "Testing from $(hostname)"
```
🔍 **تحلیل دستور:** `$(hostname)`: Command Substitution — نام واقعی هاست فعلی را در پیام جایگذاری می‌کند.

### ✅ Best Practice
همیشه TCP (نه UDP) برای Centralized Logging، و همیشه محدودیت zone/source روی پورت دریافت.

## سناریو ۵: فیلترینگ پیشرفته RainerScript برای شناسایی الگوی Brute-force (سطح پیشرفته)

### قدم‌به‌قدم

**۱. طراحی قانون شرطی**
```bash
cat > /etc/rsyslog.d/50-ssh-security.conf << 'EOF'
if $programname == 'sshd' and $msg contains 'Failed password' then {
    action(type="omfile" file="/var/log/ssh-brute-force.log")
}
EOF
```
🔍 **تحلیل دستور:** `$programname` و `$msg` متغیرهای داخلی RainerScript که به فیلدهای هر پیام دریافتی اشاره می‌کنند؛ `contains` عملگر بررسی زیررشته (نه تطبیق کامل)؛ `and` ترکیب دو شرط.

**۲. تست و بررسی**
```bash
tail -10 /var/log/ssh-brute-force.log
```

**۳. اسکریپت تحلیلی شناسایی IP های مشکوک**
```bash
grep "Failed password" /var/log/ssh-brute-force.log | \
    grep -oE "from [0-9]+\.[0-9]+\.[0-9]+\.[0-9]+" | \
    awk '{print $2}' | sort | uniq -c | sort -rn | head -10
```
🔍 **تحلیل دستور:**
- ا `\`: بک‌اسلش در انتهای خط، ادامه دستور را به خط بعدی می‌برد (فقط برای خوانایی، از نظر شل یک دستور واحد است).
- ا `grep -oE "regex"`: `-o` فقط بخش مطابق، `-E` regex پیشرفته.
- ا `uniq -c`: مخفف `--count` — قبل از هر خط تکراری، تعداد تکرار آن را می‌شمارد (نیازمند این‌که ورودی از قبل با `sort` مرتب شده باشد، چون `uniq` فقط تکرارهای **متوالی** را می‌شمارد).
- ا `sort -rn`: `-r` نزولی، `-n` مرتب‌سازی عددی (نه متنی) — ضروری چون بدون `-n`، عدد ۱۰۰ قبل از ۲۰ می‌آمد (مرتب‌سازی متنی اشتباه).

### 📌 نکته آزمون
ا RainerScript می‌تواند بخشی از منطق تحلیلی امنیتی سطح پایین را بدون ابزار جداگانه انجام دهد.

## سناریو ۶: بازیابی فضای بحرانی ناشی از رشد کنترل‌نشده Journal (سطح متوسط)

### قدم‌به‌قدم

**۱. تایید علت**
```bash
journalctl --disk-usage
```
🔍 **تحلیل دستور:** بدون سوییچ اضافه؛ فقط یک خط خلاصه نشان می‌دهد journal در مجموع چقدر فضا اشغال کرده.

**۲. رفع فوری**
```bash
journalctl --vacuum-size=1G
```
🔍 **تحلیل دستور:** `--vacuum-size=1G` قدیمی‌ترین پیام‌ها را حذف می‌کند تا حجم کل به این مقدار برسد — بدون تعیین بازه زمانی، فقط بر اساس حجم کل عمل می‌کند.

**۳. تنظیم دائمی با Drop-in**
```bash
mkdir -p /etc/systemd/journald.conf.d
cat > /etc/systemd/journald.conf.d/size-limits.conf << 'EOF'
[Journal]
SystemMaxUse=2G
MaxRetentionSec=60day
EOF
```
🔍 **تحلیل دستور:** الگوی Drop-in مشابه systemd Service (که در بخش ۶ دیدیم)، اینجا برای خود پیکربندی journald.

**۴. اعمال با ری‌استارت**
```bash
systemctl restart systemd-journald
```

### ✅ Best Practice
ا `SystemMaxUse` و `MaxRetentionSec` باید بخشی از checklist راه‌اندازی هر سرور جدید باشد.

## جمع‌بندی مهارت‌های این بخش

- جستجوی پایه journalctl با بازه زمانی، unit، و priority
- ارسال و ردیابی پیام دستی با `logger -t` و `journalctl -t`
- فیلترهای پیشرفته فیلد ساخت‌یافته (`_UID=`) برای عیب‌یابی امنیتی دقیق
- راه‌اندازی Centralized Logging امن با TCP و محدودیت zone
- طراحی قوانین RainerScript برای تشخیص خودکار الگوی حمله
- مدیریت دائمی فضای journal با Drop-in Configuration
