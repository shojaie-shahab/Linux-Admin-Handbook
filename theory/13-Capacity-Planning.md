# بخش ۱۳: Capacity Planning (برنامه‌ریزی ظرفیت)

> پیش‌نیاز مفهومی: بخش ۲ (Process Monitoring در ۸.۴) و بخش ۳/۴ (Storage). این بخش آن ابزارها را در یک چارچوب تحلیلی و پیش‌بینانه قرار می‌دهد.

---

## ۱۳.۱ ا Capacity Planning چیست و چرا با «مانیتورینگ لحظه‌ای» فرق دارد؟

مانیتورینگ لحظه‌ای (مثل `top`) به سوال «همین الان چه خبر است؟» پاسخ می‌دهد. **Capacity Planning** به سوال بسیار متفاوت‌تری پاسخ می‌دهد: «با این نرخ رشد فعلی، **چه زمانی** این منبع (CPU، RAM، دیسک) تمام می‌شود، و چه اقدامی باید **از الان** انجام شود تا آن روز غافلگیرکننده نباشد؟» این نیازمند **داده تاریخی** (نه فقط لحظه‌ای) و یک روش تحلیل روند (Trend Analysis) است.

## ۱۳.۲ ا sysstat — زیرساخت جمع‌آوری داده تاریخی

بدون داده تاریخی، Capacity Planning غیرممکن است. پکیج **sysstat** شامل `sar`, `iostat`, `mpstat`, `pidstat` است و یک سرویس پس‌زمینه دارد که هر ۱۰ دقیقه (پیش‌فرض) آمار سیستم را جمع‌آوری و در `/var/log/sysstat/` (یا `/var/log/sa/`) ذخیره می‌کند.

```bash
apt install sysstat -y
sed -i 's/ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
systemctl enable --now sysstat
```

```bash
sar -u 1 5              # CPU زنده، هر ۱ ثانیه، ۵ بار
sar -u -f /var/log/sysstat/sa15    # آمار تاریخی روز پانزدهم ماه
sar -r                    # حافظه (RAM/Swap)
sar -b                     # I/O دیسک
sar -n DEV 1 5              # ترافیک شبکه
sar -q                      # Load Average تاریخی
```

📌 مهم: بدون `ENABLED="true"`، سرویس sysstat هیچ داده‌ای جمع نمی‌کند — حتی اگر نصب شده باشد. این یکی از رایج‌ترین اشتباهات است: مدیر سیستم فکر می‌کند sysstat فعال است، اما وقتی بعد از یک هفته به داده تاریخی نیاز پیدا می‌کند، هیچ‌چیز وجود ندارد.

## ۱۳.۳ روش سیستماتیک تحلیل روند رشد

### گام ۱: ثبت اندازه‌گیری‌های دوره‌ای

```bash
echo "$(date +%Y-%m-%d),$(df --output=pcent /var | tail -1 | tr -d '% ')" >> /var/log/capacity/var-usage.csv
```
یک اسکریپت ساده که هر روز (با cron/timer) درصد اشغال یک پارتیشن را در یک فایل CSV ثبت می‌کند.

### گام ۲: محاسبه نرخ رشد

```bash
tail -30 /var/log/capacity/var-usage.csv
```
با مقایسه دو نقطه (مثلاً ۳۰ روز قبل و امروز)، نرخ رشد روزانه محاسبه می‌شود: `(مقدار_امروز - مقدار_۳۰_روز_قبل) / 30`.

### گام ۳: پیش‌بینی روز اشباع

اگر پارتیشن امروز ۷۰٪ پر است و نرخ رشد ۱٪ در روز است، فضای باقی‌مانده (۳۰٪) در حدود ۳۰ روز دیگر تمام می‌شود. این محاسبه ساده، پایه هر تصمیم خرید سخت‌افزار یا برنامه‌ریزی ارتقا است.

📌 نکته آزمون و عملی: پیش‌بینی خطی (Linear) همیشه دقیق نیست — رشد داده اغلب نمایی (Exponential) است، خصوصاً برای لاگ‌ها یا داده کاربر در حال رشد. یک Capacity Planner خوب چند نقطه داده (نه فقط دو نقطه) را بررسی می‌کند تا الگوی واقعی رشد را تشخیص دهد.

## ۱۳.۴ شناسایی گلوگاه‌ها — کدام منبع اول تمام می‌شود؟

```bash
uptime; nproc                    # مقایسه Load Average با تعداد هسته‌ها
vmstat 1 5                        # ستون si/so برای swap فعال، ستون r برای صف CPU
iostat -x 1 5                      # ستون %util نزدیک ۱۰۰٪ یعنی دیسک اشباع
```

هر منبع (CPU، RAM، دیسک، شبکه) الگوی اشباع متفاوتی دارد که باید جداگانه پایش شود؛ فرض غلط رایج این است که «کندی همیشه یعنی کمبود CPU» — در عمل اغلب I/O دیسک یا کمبود RAM (که به Swapping منجر می‌شود) علت واقعی است.

## ۱۳.۵ خلاصه نکات کلیدی برای آزمون

- ا Capacity Planning نیازمند داده **تاریخی** است؛ `sar -f <file>` برای بازخوانی آمار گذشته
- ا `ENABLED="true"` در `/etc/default/sysstat` پیش‌نیاز اجباری جمع‌آوری خودکار است
- ا Load Average باید همیشه نسبت به `nproc` تفسیر شود، نه به‌تنهایی
- پیش‌بینی رشد باید بر اساس چند نقطه داده باشد، نه فقط دو نقطه (خطر خطای پیش‌بینی خطی روی رشد نمایی)
