# بخش ۶: System Services (سرویس‌های سیستمی — تعمیق systemd)

> پیش‌نیاز مفهومی: در بخش ۱ با مفهوم پایه systemd (PID 1، Target ، Boot Transaction، Dependencies) آشنا شدیم. در این بخش، انواع دیگر Unit (فراتر از Service و Target)، و ابزارهای مدیریتی پیشرفته‌تر را با جزئیات کامل می‌بینیم.

---

## ۶.۱ مرور سریع مدل Unit — و چرا انواع مختلف داریم

به یاد بیاورید در بخش ۱ گفتیم systemd حول مفهوم **Unit** (هر «چیز قابل مدیریت») می‌چرخد. تا اینجا فقط با Service (یک برنامه در حال اجرا) و Target (گروه‌بندی Unit ها) آشنا شدیم. اما یک مدیر سیستم واقعی باید بتواند چیزهای دیگری را هم به این شکل استاندارد مدیریت کند: یک mount point، یک سوکت شبکه، یک زمان‌بندی دوره‌ای، یا حتی «وقتی این فایل خاص تغییر کرد، این کار را انجام بده». systemd برای هرکدام از این‌ها یک **نوع Unit اختصاصی** طراحی کرده، اما همه از یک الگوی مشترک (بخش‌های `[Unit]`, و بخش تخصصی خودشان، و `[Install]`) پیروی می‌کنند — یادگیری یک نوع، یادگیری بقیه را بسیار آسان‌تر می‌کند.

| نوع Unit | پسوند | چه چیزی را مدیریت می‌کند |
|---|---|---|
| Service | `.service` | یک پردازش/دیمون در حال اجرا |
| Socket | `.socket` | یک سوکت شبکه یا یونیکس که یک سرویس را «فعال‌سازی بر اساس تقاضا» می‌کند |
| Timer | `.timer` | زمان‌بندی اجرای دوره‌ای یک سرویس (معادل مدرن cron) |
| Mount | `.mount` | یک نقطه mount فایل‌سیستم |
| Automount | `.automount` | mount خودکار و تنبل (فقط وقتی واقعاً به آن دسترسی پیدا شود) |
| Path | `.path` | نظارت بر یک مسیر فایل‌سیستم برای تغییرات |
| Device | `.device` | نمایانگر یک دستگاه سخت‌افزاری شناسایی‌شده توسط udev |
| Scope | `.scope` | گروه‌بندی پردازش‌هایی که از بیرون systemd ساخته شده‌اند (نه با ExecStart) |
| Slice | `.slice` | یک گروه سلسله‌مراتبی از منابع (cgroup) برای محدودسازی دسته‌ای |
| Target | `.target` | گروه‌بندی منطقی از Unit های دیگر (که در بخش ۱ دیدیم) |

## ۶.۲ ا Socket Activation — یکی از هوشمندانه‌ترین ایده‌های systemd

### مشکلی که Socket Activation حل می‌کند

فرض کنید یک سرور دارید با ۵۰ سرویس مختلف نصب‌شده، اما در هر لحظه فقط چند تای آن‌ها واقعاً مورد استفاده هستند. اگر همه این ۵۰ سرویس همیشه از ابتدای بوت در حال اجرا باشند، حافظه و منابع CPU زیادی صرف سرویس‌هایی می‌شود که شاید هفته‌ها هیچ درخواستی دریافت نکنند.

ا **Socket Activation** این مشکل را با یک ترفند هوشمندانه حل می‌کند: به‌جای این‌که خود سرویس (که ممکن است سنگین باشد) را از ابتدا اجرا کنیم، systemd فقط یک **سوکت شبکه سبک** (که خودش تقریباً هیچ منبعی مصرف نمی‌کند) را باز نگه می‌دارد و به آن گوش می‌دهد. تا زمانی که هیچ درخواستی نیاید، سرویس واقعی اصلاً اجرا نمی‌شود. فقط در همان لحظه‌ای که **اولین اتصال واقعی** به آن سوکت برسد، systemd بلافاصله سرویس واقعی را اجرا می‌کند و آن اتصال را به آن تحویل می‌دهد.

### مثال عملی Socket Activation

```ini
# /etc/systemd/system/myapp.socket
[Unit]
Description=Socket for MyApp

[Socket]
ListenStream=8080

[Install]
WantedBy=sockets.target
```

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=MyApp Service
Requires=myapp.socket

[Service]
ExecStart=/usr/local/bin/myapp
```

```bash
systemctl enable --now myapp.socket
systemctl status myapp.service     # هنوز inactive (اجرا نشده)
```

اگر الان به پورت ۸۰۸۰ متصل شوید (مثلاً با `curl http://localhost:8080`)، بلافاصله سرویس `myapp.service` به‌طور خودکار توسط systemd راه‌اندازی می‌شود تا این درخواست را مدیریت کند:

```bash
curl http://localhost:8080
systemctl status myapp.service      # اکنون active است
```

📌 این دقیقاً همان مکانیزمی است که سرویس بسیار پرکاربرد **SSH** در برخی توزیع‌ها (یا ابزارهایی مثل `xinetd` در گذشته دورتر) از آن استفاده می‌کنند — یک سوکت شبکه سبک همیشه گوش می‌دهد، و فقط با اولین اتصال واقعی، هزینه واقعی راه‌اندازی سرویس پرداخت می‌شود.

## ۶.۳ ا Path Unit — واکنش خودکار به تغییرات فایل‌سیستم

ا **Path Unit** به systemd اجازه می‌دهد یک مسیر خاص از فایل‌سیستم را نظارت کند و وقتی تغییری در آن رخ داد (فایل جدید ایجاد شد، فایل موجود تغییر کرد)، یک سرویس مرتبط را خودکار اجرا کند — این جایگزین یک روش قدیمی‌تر و ناکارآمد به نام "polling" (چک کردن دوره‌ای دستی با یک اسکریپت که هر چند ثانیه بررسی می‌کند «آیا فایل جدیدی آمده؟») است.

```ini
# /etc/systemd/system/watch-uploads.path
[Unit]
Description=Watch for new upload files

[Path]
PathExistsGlob=/srv/uploads/incoming/*.jpg

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/watch-uploads.service
[Unit]
Description=Process new uploaded images

[Service]
Type=oneshot
ExecStart=/usr/local/bin/process-uploads.sh
```

```bash
systemctl enable --now watch-uploads.path
```

هر بار که یک فایل جدید با پسوند `.jpg` در `/srv/uploads/incoming/` ظاهر شود، systemd بلافاصله (بدون هیچ تاخیر polling) سرویس `watch-uploads.service` را اجرا می‌کند — این روش هم سریع‌تر و هم کارآمدتر (از نظر مصرف منابع) از یک اسکریپت cron است که هر ۱ دقیقه چک می‌کند.

## ۶.۴ ا Automount — mount تنبل (Lazy Mount)

فرض کنید یک NFS share (که در بخش ۵ دیدیم) دارید که به‌ندرت استفاده می‌شود، اما وقتی سرور NFS در دسترس نیست، mount عادی در بوت باعث تاخیر طولانی می‌شود (چون سیستم منتظر می‌ماند). **Automount** این مشکل را حل می‌کند: در بوت، فقط یک «نقطه تعهد» ساخته می‌شود، بدون این‌که واقعاً mount انجام شود؛ فقط در همان لحظه‌ای که **اولین دسترسی واقعی** (مثلاً یک `ls` یا باز کردن یک فایل) به آن مسیر انجام شود، mount واقعی به‌صورت آنی اتفاق می‌افتد.

```ini
# /etc/systemd/system/mnt-archive.automount
[Unit]
Description=Automount for archive NFS share

[Automount]
Where=/mnt/archive

[Install]
WantedBy=multi-user.target
```

باید همراه با یک Unit `.mount` معمولی (که مشخصات واقعی device و type را دارد) استفاده شود. مزیت: بوت سیستم هرگز منتظر یک share شبکه‌ای که ممکن است کند یا در دسترس نباشد، معطل نمی‌ماند.

## ۶.۵ ا Slice — سازمان‌دهی سلسله‌مراتبی منابع با cgroups

### ا cgroups چیست؟ (پیش‌نیاز مفهومی برای Slice)

ا **cgroups (Control Groups)** یک قابلیت سطح کرنل است که اجازه می‌دهد گروهی از پردازش‌ها را با هم به‌عنوان یک واحد، از نظر مصرف منابع (CPU، حافظه، I/O) محدود، اولویت‌بندی، و اندازه‌گیری کنید. این دقیقاً همان مکانیزم زیرینی است که در بخش ۱ (سناریوی محدودسازی سرویس با `MemoryMax=` و `CPUQuota=`) از آن استفاده کردیم، بدون این‌که نامش را ببریم — اکنون وقت آن است که عمیق‌تر آن را بفهمیم.

ا systemd به‌طور خودکار هر Service، Scope، و Slice را در یک **cgroup اختصاصی** خودش قرار می‌دهد. **Slice** خودش هیچ پردازشی مستقیماً اجرا نمی‌کند — فقط یک **ظرف سازمان‌دهی سلسله‌مراتبی** است که چند Service/Scope دیگر را زیرمجموعه خودش قرار می‌دهد تا بتوان محدودیت منابع را روی کل آن گروه، به‌صورت یکجا اعمال کرد.

```ini
# /etc/systemd/system/webapps.slice
[Unit]
Description=Slice for all web application services

[Slice]
CPUQuota=200%
MemoryMax=4G
```

اگر چند Service را طوری تنظیم کنیم که همگی زیر همین Slice قرار بگیرند (با `Slice=webapps.slice` در بخش `[Service]` هرکدام)، محدودیت `CPUQuota=200%` و `MemoryMax=4G` روی **مجموع** تمام آن سرویس‌ها با هم اعمال می‌شود، نه هرکدام جداگانه — مفید برای سناریوهایی مثل «تمام سرویس‌های مربوط به بخش وب، جمعاً نباید بیش از ۴ گیگابایت رم مصرف کنند».

### ابزارهای مشاهده cgroups

```bash
systemd-cgls
```
نمایش یک درخت کامل و بصری از تمام cgroups فعال سیستم، شامل این‌که هر پردازش دقیقاً زیر کدام Slice/Service قرار دارد — این ابزار تصویر واضحی از سازمان‌دهی سلسله‌مراتبی کل سیستم می‌دهد.

```bash
systemd-cgtop
```
مشابه دستور آشنای `top`، اما به‌جای نمایش تک‌تک پردازش‌ها، مصرف منابع را **به تفکیک cgroup** (یعنی هر Service/Slice به‌عنوان یک واحد جمع‌شده) نشان می‌دهد — بسیار مفید برای فهمیدن این‌که «کدام سرویس مجموعاً بیشترین منابع را مصرف می‌کند»، بدون نیاز به جمع دستی چند پردازش فرزند مختلف.

## ۶.۶ ا Drop-in Configuration — سفارشی‌سازی بدون دستکاری فایل اصلی

### چرا نباید فایل‌های Unit اصلی (که از پکیج آمده‌اند) را مستقیماً ویرایش کنیم؟

فرض کنید می‌خواهید یک تنظیم کوچک (مثلاً افزایش `MemoryMax`) را به سرویس nginx که از پکیج توزیع نصب شده اضافه کنید. اگر مستقیماً فایل `/usr/lib/systemd/system/nginx.service` را ویرایش کنید، دو مشکل بزرگ به وجود می‌آید: اول، دفعه بعد که پکیج nginx بروزرسانی شود، این فایل با نسخه جدید **بازنویسی** می‌شود و تغییر شما از بین می‌رود؛ دوم، تشخیص این‌که «چه چیزی را من تغییر دادم» در آینده بسیار سخت می‌شود چون تغییرات سفارشی و پیش‌فرض پکیج در یک فایل قاطی شده‌اند.

ا **Drop-in Configuration** راه‌حل استاندارد این مشکل است: به‌جای ویرایش فایل اصلی، یک پوشه با نام `<unit-name>.d/` می‌سازید و داخل آن، فایل‌های کوچک `.conf` که فقط شامل تغییراتی که می‌خواهید هستند قرار می‌دهید.

```bash
mkdir -p /etc/systemd/system/nginx.service.d/
cat > /etc/systemd/system/nginx.service.d/override.conf << 'EOF'
[Service]
MemoryMax=1G
Restart=always
EOF
```
```bash
systemctl daemon-reload
systemctl restart nginx
```

ا systemd به‌طور خودکار محتوای فایل اصلی (`/usr/lib/systemd/system/nginx.service`) را با هر فایل داخل `nginx.service.d/*.conf` **ادغام (merge)** می‌کند — پارامترهایی که در drop-in تعریف شده‌اند، مقادیر اصلی را override می‌کنند، و بقیه پارامترهای فایل اصلی دست‌نخورده باقی می‌مانند.

```bash
systemctl cat nginx.service
```
این دستور بسیار مفید است: نتیجه **نهایی و ادغام‌شده** (فایل اصلی + تمام drop-in ها) را دقیقاً همان‌طور که systemd آن را می‌بیند نمایش می‌دهد — بهترین راه برای تایید این‌که override شما واقعاً اعمال شده.

```bash
systemctl edit nginx.service
```
📌 یک میان‌بر بسیار مفید: این دستور به‌طور خودکار یک فایل drop-in برای شما باز می‌کند (در ویرایشگر پیش‌فرض) و بعد از ذخیره، خودش `daemon-reload` را هم انجام می‌دهد — دیگر نیازی به ساخت دستی پوشه `.d/` نیست.

```bash
systemctl edit --full nginx.service
```
ا `--full` رفتار متفاوتی دارد: به‌جای drop-in، یک **کپی کامل** از فایل اصلی را در `/etc/systemd/system/` می‌سازد که کاملاً جایگزین فایل پکیج می‌شود — این روش کمتر توصیه می‌شود (چون تمام مزایای drop-in که در بالا گفتیم را از دست می‌دهید)، اما گاهی برای تغییرات بسیار گسترده مفید است.

## ۶.۷ ا Template Unit — یک تعریف، چندین نمونه

### مشکل: چند نمونه از یک سرویس مشابه

فرض کنید می‌خواهید ۵ نمونه مستقل از یک سرویس worker صف پیام (مثلاً برای پردازش موازی) اجرا کنید، که هرکدام فقط با یک پارامتر کوچک (مثلاً شماره worker) از هم متفاوت‌اند. نوشتن ۵ فایل Unit تقریباً یکسان (`worker1.service`, `worker2.service`, ...) بسیار تکراری و مستعد خطا است.

ا **Template Unit** این مشکل را حل می‌کند: یک فایل الگو با علامت `@` در نامش می‌سازید، و systemd به شما اجازه می‌دهد در لحظه فعال‌سازی، یک «پارامتر نمونه» (Instance) مشخص کنید که در تعریف Unit جایگذاری می‌شود.

```ini
# /etc/systemd/system/worker@.service
[Unit]
Description=Queue Worker Instance %i

[Service]
ExecStart=/usr/local/bin/queue-worker.sh --worker-id=%i
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

این `%i` نمادی است که systemd آن را با هر چیزی که بعد از `@` در لحظه فعال‌سازی قرار می‌دهید، جایگزین می‌کند:

```bash
systemctl enable --now worker@1.service
systemctl enable --now worker@2.service
systemctl enable --now worker@3.service
```

هرکدام از این‌ها یک **نمونه مستقل** با شماره worker متفاوت است، اما همگی از همان یک فایل الگوی `worker@.service` تعریف شده‌اند — تغییر منطق (مثلاً یک بروزرسانی در اسکریپت worker) فقط نیازمند ویرایش یک فایل واحد است.

```bash
systemctl status worker@2.service
systemctl list-units 'worker@*'      # نمایش تمام نمونه‌های فعال از این الگو
```

📌 یک نمونه بسیار رایج از Template Unit که احتمالاً از قبل روی سیستم شما وجود دارد: `getty@.service` که برای هر ترمینال مجازی (`tty1`, `tty2`, ...) یک نمونه مستقل صفحه لاگین راه‌اندازی می‌کند (`getty@tty1.service`).

## ۶.۸ ا systemd-tmpfiles — مدیریت خودکار فایل‌ها و پوشه‌های موقت

### مشکلی که این ابزار حل می‌کند

بسیاری از سرویس‌ها نیاز دارند در هر بوت، مطمئن شوند یک پوشه خاص (مثلاً برای PID file یا کش موقت) با مالکیت و مجوز صحیح وجود دارد. به‌جای این‌که هر سرویس جداگانه این منطق را در اسکریپت راه‌اندازی خودش بنویسد، systemd یک مکانیزم استاندارد و مرکزی برای این کار فراهم می‌کند: **systemd-tmpfiles**.

فایل‌های تنظیمات در `/etc/tmpfiles.d/*.conf` یا `/usr/lib/tmpfiles.d/*.conf` قرار دارند و با یک syntax فشرده و خوانا، رفتار مورد نیاز را تعریف می‌کنند:

```
# /etc/tmpfiles.d/myapp.conf
d /run/myapp 0750 myapp myapp -
d /var/cache/myapp 0755 myapp myapp 10d
```

هر خط شامل چند فیلد است: نوع عملیات (`d` یعنی «مطمئن شو این پوشه وجود دارد»)، مسیر، مجوز (permission)، مالک، گروه، و در آخر — مدت زمان نگهداری (`10d` یعنی فایل‌های داخل این پوشه که قدیمی‌تر از ۱۰ روز باشند به‌طور خودکار پاک‌سازی می‌شوند؛ `-` یعنی هرگز پاک‌سازی خودکار انجام نشود).

```bash
systemd-tmpfiles --create /etc/tmpfiles.d/myapp.conf     # اجرای دستی فوری (بدون نیاز به ریبوت)
systemd-tmpfiles --clean                                    # اجرای فقط بخش پاک‌سازی (بر اساس سن فایل)
systemd-tmpfiles --remove /etc/tmpfiles.d/myapp.conf         # حذف مسیرهای تعریف‌شده
```

📌 این دقیقاً همان مکانیزمی است که مسئول پاک‌سازی خودکار دوره‌ای `/tmp` در بسیاری از توزیع‌های مدرن است (به‌جای یک اسکریپت cron جداگانه که در گذشته این کار را انجام می‌داد).

## ۶.۹ ا systemd-sysusers — ساخت خودکار کاربران سیستمی

وقتی یک پکیج نرم‌افزاری (مثلاً nginx) نصب می‌شود، معمولاً به یک کاربر سیستمی اختصاصی (نه `root`، برای امنیت — دقیقاً همان اصلی که در بخش‌های قبلی درباره اجرای سرویس با کاربر غیر-root تاکید کردیم) نیاز دارد. **systemd-sysusers** یک روش استاندارد و اعلانی (declarative) برای تعریف این کاربران فراهم می‌کند، به‌جای این‌که هر پکیج اسکریپت‌های پیچیده نصب خودش برای فراخوانی `useradd` بنویسد.

```
# /usr/lib/sysusers.d/myapp.conf
u myapp - "MyApp Service User" /var/lib/myapp /sbin/nologin
```

این خط اعلام می‌کند: یک کاربر سیستمی (`u`) به نام `myapp` باید وجود داشته باشد، با توضیح مشخص، پوشه home مشخص، و بدون امکان لاگین تعاملی (`/sbin/nologin` — دقیقاً همان الگوی امنیتی که در بخش‌های Samba و systemd Service سفارشی هم دیدیم).

```bash
systemd-sysusers /usr/lib/sysusers.d/myapp.conf
```

## ۶.۱۰ ا systemd-coredump — مدیریت خودکار Core Dump

### ا Core Dump چیست؟

وقتی یک پردازش به‌طور غیرمنتظره کرش می‌کند (مثلاً یک خطای حافظه سطح پایین)، کرنل می‌تواند یک **تصویر کامل از حافظه آن پردازش در لحظه کرش** را ذخیره کند — این را **Core Dump** می‌نامند و برای توسعه‌دهندگان (با ابزارهایی مثل `gdb`) امکان تحلیل دقیق علت کرش را فراهم می‌کند.

ا **systemd-coredump** این فرآیند را مدیریت و سازمان‌دهی می‌کند: به‌جای پراکنده شدن فایل‌های Core Dump در پوشه‌های مختلف با نام‌های نامنظم، systemd-coredump آن‌ها را به‌طور متمرکز جمع‌آوری، فشرده‌سازی، و در journal (که در بخش ۱ با `journalctl` دیدیم) قابل جستجو می‌کند.

```bash
coredumpctl list
```
لیست تمام Core Dump های اخیر ثبت‌شده روی سیستم را نشان می‌دهد.

```bash
coredumpctl info <PID>
coredumpctl debug <PID>
```
ا `info` جزئیات یک Core Dump خاص (شامل پیام خطا، Stack Trace) را نشان می‌دهد؛ `debug` مستقیماً یک نشست `gdb` را با آن Core Dump بارگذاری‌شده باز می‌کند — برای تحلیل عمیق‌تر توسط یک توسعه‌دهنده.

## ۶.۱۱ جمع‌بندی گراف وابستگی — مشاهده کامل ساختار سیستم

```bash
systemctl list-dependencies nginx.service
```
نمایش درختی تمام Unit هایی که `nginx.service` به آن‌ها وابسته است (مستقیم و غیرمستقیم) — مفید برای فهمیدن این‌که چرا یک سرویس منتظر سرویس دیگری می‌ماند.

```bash
systemctl list-dependencies nginx.service --reverse
```
ا `--reverse` جهت را برعکس می‌کند: نشان می‌دهد **کدام Unit های دیگر** به `nginx.service` وابسته‌اند (یعنی اگر nginx را متوقف کنید، چه چیزهای دیگری تحت تاثیر قرار می‌گیرند).

## ۶.۱۲ خلاصه نکات کلیدی برای آزمون

- ا Socket Activation اجازه می‌دهد یک سرویس فقط با اولین اتصال واقعی راه‌اندازی شود، نه از ابتدای بوت — صرفه‌جویی در منابع
- ا Path Unit جایگزین کارآمدتر «polling دوره‌ای با cron» برای واکنش به تغییرات فایل‌سیستم است
- ا Automount از تاخیر بوت به‌خاطر mount های شبکه‌ای کند/غیرقابل‌دسترس جلوگیری می‌کند
- ا Slice یک ظرف سازمان‌دهی cgroup است که هیچ پردازشی مستقیم اجرا نمی‌کند، فقط محدودیت منابع را روی گروهی از Service ها اعمال می‌کند
- همیشه از Drop-in Configuration (`systemctl edit`) برای سفارشی‌سازی سرویس‌های پکیج‌شده استفاده کنید، نه ویرایش مستقیم فایل اصلی
- ا `systemctl cat` نتیجه نهایی ادغام‌شده (اصلی + drop-in) را نشان می‌دهد
- ا Template Unit (`name@.service` با `%i`) از تکرار فایل‌های تقریباً یکسان جلوگیری می‌کند
- تفاوت `systemd-cgls` (نمایش درختی ساختار) و `systemd-cgtop` (نمایش زنده مصرف منابع، شبیه top) را بدانید
- ا systemd-tmpfiles و systemd-sysusers، مدیریت اعلانی (نه اسکریپتی) پوشه‌های موقت و کاربران سیستمی را استاندارد می‌کنند
