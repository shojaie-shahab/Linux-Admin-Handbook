# بخش ۱۱: Time & Authentication (زمان‌ و احراز هویت)

> پیش‌نیاز مفهومی: این بخش دو موضوع به‌ظاهر نامرتبط اما هر دو زیرساختی را پوشش می‌دهد: همگام‌سازی دقیق زمان (که پایه بسیاری از پروتکل‌های امنیتی مثل Kerberos است) و لایه‌های مختلف احراز هویت کاربر در لینوکس.

---

## ۱۱.۱ چرا زمان دقیق سیستم این‌قدر اهمیت دارد؟

### فراتر از «ساعت درست را نشان بده»

ممکن است فکر کنید دقت زمان سیستم فقط برای این است که timestamp لاگ‌ها درست باشد — این درست است، اما فقط بخش کوچکی از ماجراست. دلایل عمیق‌تر و حیاتی‌تر:

**همبستگی لاگ‌ها بین چند سرور**: اگر می‌خواهید بفهمید یک رویداد که چند سرور را درگیر کرده (مثلاً یک درخواست که از یک وب‌سرور به یک سرور دیتابیس رفته) دقیقاً در چه ترتیبی رخ داده، ساعت هر دو سرور باید همگام باشد — در غیر این‌صورت، ترتیب واقعی رویدادها در تحلیل لاگ (که در بخش ۷ دیدیم) کاملاً گمراه‌کننده می‌شود.

**پروتکل‌های رمزنگاری زمان‌محور**: بسیاری از مکانیزم‌های امنیتی (که در ادامه همین بخش با Kerberos می‌بینیم، و همچنین گواهی‌های TLS/SSL) به‌شدت به زمان دقیق وابسته‌اند. یک بلیط Kerberos (Ticket) معمولاً فقط برای چند دقیقه معتبر است؛ اگر ساعت کلاینت و سرور بیش از چند دقیقه اختلاف داشته باشند، کل فرآیند احراز هویت شکست می‌خورد — نه به‌خاطر یک خطای امنیتی واقعی، بلکه صرفاً به‌خاطر عدم تطابق زمانی.

**فایل‌سیستم‌های توزیع‌شده و سیستم‌های کنترل نسخه**: ابزارهایی که بر اساس timestamp تصمیم می‌گیرند کدام نسخه از یک فایل «جدیدتر» است (مثل `make` که در بخش ۲ دیدیم، یا سیستم‌های sync فایل)، اگر ساعت سیستم اشتباه باشد، می‌توانند تصمیمات کاملاً غلط بگیرند.

### ا RTC در برابر System Clock — دو ساعت مجزا در هر کامپیوتر

هر کامپیوتر در واقع **دو ساعت مجزا** دارد:

ا **RTC (Real-Time Clock)**: یک تراشه سخت‌افزاری کوچک روی مادربرد که با یک باتری کوچک (حتی وقتی کامپیوتر کاملاً خاموش است) کار می‌کند و زمان را نگه می‌دارد — این همان چیزی است که باعث می‌شود کامپیوتر شما بعد از خاموش کردن کامل، هنوز زمان تقریباً درستی داشته باشد.

ا **System Clock**: ساعتی که خود کرنل لینوکس، بعد از بوت، در حافظه نگه می‌دارد و مدام (بر اساس تیک‌های داخلی CPU) به‌روزرسانی می‌کند — این ساعتی است که تمام برنامه‌ها و سیستم‌عامل واقعاً از آن استفاده می‌کنند.

در ابتدای بوت، System Clock از RTC خوانده می‌شود تا یک نقطه شروع داشته باشد؛ اما از آن لحظه به بعد، System Clock مستقل کار می‌کند — و می‌تواند به‌مرور کمی «رانده» (Drift) شود (چون ساعت‌های کریستالی داخلی هرگز کاملاً بی‌نقص نیستند).

```bash
timedatectl
```
نمایش وضعیت کامل هر دو ساعت: زمان محلی، زمان UTC، منطقه زمانی، و این‌که آیا NTP همگام‌سازی فعال است.

```bash
hwclock --show      # نمایش مستقیم RTC (بدون واسطه سیستم‌عامل)
hwclock --systohc     # کپی زمان فعلی System Clock به RTC (ذخیره برای بعد از خاموشی)
hwclock --hctosys      # کپی زمان RTC به System Clock (معمولاً فقط در بوت انجام می‌شود)
```

## ا ۱۱.۲ NTP و Chrony — همگام‌سازی خودکار و دقیق زمان

### چرا نمی‌توانیم فقط دستی زمان را تنظیم کنیم؟

حتی اگر یک‌بار زمان سیستم را کاملاً دقیق تنظیم کنید، به‌خاطر Drift که در بالا توضیح دادیم، این دقت به‌مرور از بین می‌رود — بعد از چند هفته، ممکن است چند ثانیه یا حتی بیشتر اختلاف پیدا شود. **NTP (Network Time Protocol)** یک پروتکل استاندارد است که به‌طور مداوم و خودکار، ساعت سیستم را با یک یا چند سرور زمان مرجع (که خودشان نهایتاً به ساعت‌های اتمی بسیار دقیق متصل‌اند) همگام نگه می‌دارد.

### ا Stratum — سلسله‌مراتب منابع زمان

ا NTP از یک مفهوم سلسله‌مراتبی به نام **Stratum** استفاده می‌کند: **Stratum 0** منابع زمان بسیار دقیق فیزیکی هستند (ساعت اتمی، گیرنده GPS) که خودشان مستقیماً به شبکه متصل نیستند؛ **Stratum 1** سرورهایی هستند که مستقیماً به یک منبع Stratum 0 متصل‌اند؛ **Stratum 2** سرورهایی هستند که زمان خود را از سرورهای Stratum 1 می‌گیرند، و الی‌آخر — هرچه عدد Stratum بزرگ‌تر، فاصله (و بالقوه خطای انباشته‌شده) از منبع اصلی بیشتر است.

### ا Chrony — پیاده‌سازی مدرن NTP

ا **Chrony** جانشین مدرن پیاده‌سازی قدیمی‌تر `ntpd` است و در اکثر توزیع‌های امروزی پیش‌فرض است — طراحی آن برای شرایط واقعی (اتصال اینترنت متناوب، سیستم‌هایی که گاهی برای مدت طولانی خاموش/معلق می‌شوند، مثل لپ‌تاپ‌ها) بهینه‌تر است و سریع‌تر به دقت بالا می‌رسد.

```bash
apt install chrony -y
```

فایل تنظیمات: `/etc/chrony/chrony.conf`
```
pool 2.debian.pool.ntp.org iburst
```
ا `pool` به مجموعه‌ای از سرورهای NTP عمومی اشاره می‌کند (نه یک سرور واحد، برای افزونگی و توزیع بار)؛ `iburst` به Chrony می‌گوید در ابتدای راه‌اندازی، چندین درخواست سریع پشت‌سرهم بفرستد تا هرچه سریع‌تر (به‌جای منتظر ماندن طولانی) به یک تخمین اولیه دقیق برسد.

```bash
chronyc tracking
```
نمایش وضعیت دقیق همگام‌سازی فعلی: Stratum فعلی سیستم، میزان اختلاف تخمینی از زمان واقعی (Offset)، و نرخ Drift تخمینی.

```bash
chronyc sources -v
```
لیست تمام سرورهای NTP که سیستم در حال حاضر با آن‌ها در ارتباط است، همراه با کیفیت هرکدام — ستون‌هایی که نشان می‌دهند کدام سرور به‌عنوان منبع اصلی انتخاب شده (`*`) و کدام‌ها به‌عنوان پشتیبان یا رد‌شده هستند.

```bash
chronyc makestep
```
اگر اختلاف زمانی بسیار بزرگ باشد (مثلاً چند دقیقه، که می‌تواند بعد از یک خاموشی طولانی رخ دهد)، Chrony به‌طور پیش‌فرض به‌آرامی زمان را تنظیم می‌کند (Slewing — تغییر تدریجی، برای جلوگیری از پرش ناگهانی که می‌تواند برنامه‌های حساس به زمان را دچار مشکل کند)؛ `makestep` یک تنظیم فوری و یک‌باره (Step، نه تدریجی) را اجبار می‌کند.

### راه‌اندازی سرور NTP داخلی برای یک سازمان

در سازمان‌های بزرگ، معمولاً بهتر است فقط چند سرور داخلی (که خودشان با اینترنت خارجی همگام هستند) به‌عنوان منبع NTP برای بقیه سرورهای داخلی عمل کنند — این هم ترافیک خارجی را کاهش می‌دهد و هم یک منبع زمان یکپارچه و قابل‌کنترل برای کل سازمان فراهم می‌کند:

```bash
#i روی سرور NTP داخلی:

allow 192.168.1.0/24
local stratum 10
```
ا `allow` به این سرور اجازه می‌دهد به کلاینت‌های آن subnet خاص پاسخ دهد (نه فقط خودش کلاینت باشد)؛ `local stratum 10` اجازه می‌دهد این سرور حتی اگر موقتاً از تمام منابع خارجی قطع باشد، همچنان یک زمان معقول (هرچند با Stratum بالا، یعنی اعتبار کمتر) به کلاینت‌های داخلی ارائه دهد — بهتر از این‌که کلاینت‌ها اصلاً هیچ منبع زمانی نداشته باشند.

## ۱۱.۳ ا PAM — لایه انتزاعی احراز هویت

### مروری از پایه — چرا PAM وجود دارد

فرض کنید ده‌ها برنامه مختلف روی سیستم شما (login، sshd، sudo، passwd) هرکدام باید کاربر را احراز هویت کنند. اگر هرکدام جداگانه منطق «چگونه رمز عبور را بررسی کنم» را در کد خودشان hardcode می‌کردند، تغییر روش احراز هویت (مثلاً افزودن یک قدم دو-مرحله‌ای، یا سوییچ به LDAP) نیازمند بازنویسی ده‌ها برنامه مختلف می‌بود.

ا **PAM (Pluggable Authentication Modules)** این مشکل را با یک لایه انتزاعی مشترک حل می‌کند — دقیقاً همان فلسفه‌ای که در بخش ۳ با VFS و در بخش ۹ با مدل OSI دیدیم: برنامه‌ها فقط با یک رابط استاندارد PAM صحبت می‌کنند، و PAM خودش تصمیم می‌گیرد از کدام «ماژول» واقعی (بررسی رمز محلی، LDAP، اثر انگشت، کلید سخت‌افزاری) برای انجام کار واقعی استفاده کند — بدون این‌که آن برنامه‌ها اصلاً نیاز باشد از این جزئیات باخبر باشند.

### ساختار فایل‌های PAM — چهار نوع Type

هر فایل در `/etc/pam.d/<service-name>` (مثلاً `/etc/pam.d/sshd`) شامل خطوطی با این فرمت است:
```
type   control   module_path   arguments
```

چهار نوع (type):

ا **`auth`**: بررسی «آیا واقعاً این کسی است که ادعا می‌کند؟» — معمولاً بررسی رمز عبور یا سایر عوامل احراز هویت.

ا **`account`**: بعد از تایید هویت، بررسی محدودیت‌های حساب — آیا این حساب منقضی شده؟ آیا این کاربر اجازه دارد در این ساعت خاص وارد شود؟ آیا حساب قفل شده؟

ا **`password`**: منطق مربوط به **تغییر** رمز عبور — چه سیاست‌های پیچیدگی باید رعایت شود، رمز جدید چگونه ذخیره (هش) شود.

ا **`session`**: کارهایی که باید در **آغاز** یا **پایان** یک نشست انجام شوند — مثل mount کردن پوشه home، تنظیم متغیرهای محیطی، یا ثبت لاگ ورود.

### ا Control — چگونه نتیجه هر ماژول در تصمیم نهایی تاثیر می‌گذارد

```
auth    required     pam_unix.so
auth    sufficient    pam_ldap.so
auth    required     pam_deny.so
```

ا **`required`**: این ماژول باید موفق شود؛ اما حتی اگر شکست بخورد، PAM بلافاصله متوقف نمی‌شود — بقیه ماژول‌های همان stack را هم اجرا می‌کند (این برای امنیت مهم است: یک مهاجم نمی‌تواند از زمان‌بندی پاسخ بفهمد دقیقاً کدام مرحله شکست خورده)، اما در نهایت کل زنجیره **رد** می‌شود.

ا **`requisite`**: مشابه `required`، اما اگر شکست بخورد، **بلافاصله** متوقف می‌شود (بدون اجرای بقیه ماژول‌ها) — سریع‌تر اما ممکن است اطلاعات زمان‌بندی بیشتری به یک مهاجم بالقوه بدهد.

ا **`sufficient`**: اگر این ماژول موفق شود، همین برای قبولی **کافی** است (به شرطی که هیچ ماژول `required` قبلی شکست نخورده باشد) — بقیه ماژول‌های بعدی اصلاً بررسی نمی‌شوند.

ا **`optional`**: نتیجه این ماژول معمولاً در تصمیم نهایی تاثیری ندارد، مگر این‌که تنها ماژول موجود در کل stack باشد.

📌 مثال بالا را با این دانش بخوانید: ابتدا تلاش برای احراز هویت محلی (`pam_unix.so` با `required` — باید بررسی شود، اما شکست فوری متوقف نمی‌کند)؛ اگر آن ماژول شکست خورد، تلاش با LDAP (`pam_ldap.so` با `sufficient` — اگر این موفق شود، کافی است)؛ اگر هر دو شکست خوردند، در نهایت `pam_deny.so` (که همیشه رد می‌کند) اجرا می‌شود تا مطمئن شویم بدون یک قبولی واقعی، هرگز دسترسی داده نمی‌شود.

### مثال عملی — محدودسازی تلاش‌های ناموفق ورود

```bash
# /etc/pam.d/sshd (نزدیک ابتدای بخش auth)

auth required pam_faillock.so preauth silent deny=5 unlock_time=600
auth [success=1 default=ignore] pam_unix.so
auth [default=die] pam_faillock.so authfail deny=5 unlock_time=600
account required pam_faillock.so
```
این مجموعه، بعد از ۵ تلاش ناموفق، حساب را برای ۶۰۰ ثانیه (۱۰ دقیقه) قفل می‌کند — یک محافظت پایه در برابر حملات Brute-force، مستقل و اضافه بر هر محافظت دیگری (مثل Fail2ban که در فصل‌های امنیت دیده‌ایم/می‌بینیم).

```bash
faillock --user alice                # نمایش تعداد تلاش‌های ناموفق ثبت‌شده برای این کاربر
faillock --user alice --reset          # بازنشانی دستی (مثلاً بعد از تایید هویت واقعی کاربر توسط مدیر سیستم)
```

⚠️ همان هشدار حیاتی که در بخش‌های قبلی هم گفتیم: هرگز فایل‌های PAM را بدون یک نشست root باز دیگر ویرایش نکنید — یک اشتباه در این فایل‌ها می‌تواند کاملاً قفل شدن دسترسی (حتی برای root) را به همراه داشته باشد.

## ۱۱.۴ ا NSS — از کجا PAM نام کاربری را واقعاً پیدا می‌کند؟

### تفاوت PAM و NSS — یک تمایز مفهومی مهم که اغلب گیج‌کننده است

ا PAM مسئول **احراز هویت** است («آیا این رمز درست است؟»)، اما یک سوال قبل از آن وجود دارد: «این کاربر خاص اصلاً کیست؟ UID او چیست؟ پوشه home او کجاست؟» — این سوال دوم به **NSS (Name Service Switch)** مربوط است، نه PAM.

فایل `/etc/nsswitch.conf` مشخص می‌کند برای هر نوع اطلاعات (کاربران، گروه‌ها، نام میزبان‌ها)، سیستم باید ابتدا کجا را بررسی کند:

```
passwd:     files sss
group:      files sss
hosts:      files dns
```

ا `passwd: files sss` یعنی برای پیدا کردن اطلاعات کاربر، ابتدا فایل محلی `/etc/passwd` بررسی شود، و اگر آنجا پیدا نشد، به `sss` (که مخفف SSSD است، در بخش بعد توضیح می‌دهیم) مراجعه شود — این ترتیب یعنی حساب‌های محلی همیشه اولویت دارند و سریع‌تر resolve می‌شوند، و فقط برای کاربرانی که محلی تعریف نشده‌اند، سیستم به منبع خارجی (مثل LDAP یا Active Directory) مراجعه می‌کند.

```bash
getent passwd alice
```
ا `getent` مستقیماً از طریق NSS (نه صرفاً `/etc/passwd`) اطلاعات کاربر را جستجو می‌کند — دقیقاً همان مسیری که PAM/سیستم به‌طور داخلی طی می‌کند؛ این ابزار بسیار مفید برای عیب‌یابی است: اگر `getent passwd alice` چیزی برنمی‌گرداند، یعنی سیستم اصلاً نمی‌تواند این کاربر را پیدا کند، مستقل از این‌که رمز عبور او درست است یا نه.

## ۱۱.۵ ا SSSD — پل یکپارچه به دایرکتوری‌های خارجی

### چرا SSSD به‌جای اتصال مستقیم به LDAP/AD؟

می‌شد سیستم را طوری پیکربندی کرد که مستقیماً و بی‌واسطه به یک سرور LDAP یا Active Directory متصل شود هر بار که نیاز به احراز هویت یا جستجوی کاربر است. اما این روش چند مشکل دارد: هر بار درخواست باید از شبکه عبور کند (کند، و اگر شبکه/سرور مرکزی موقتاً در دسترس نباشد، کاربران حتی نمی‌توانند لاگین کنند)، و مدیریت پیکربندی این اتصال مستقیم در چندین جای مختلف (PAM، NSS) پیچیده و تکراری است.

ا **SSSD (System Security Services Daemon)** یک لایه واسط هوشمند است که این ارتباط را متمرکز، بهینه، و **کش‌شده** می‌کند: SSSD یک‌بار به دایرکتوری خارجی متصل می‌شود، اطلاعات را کش می‌کند (به‌طور امن، رمزنگاری‌شده)، و به PAM/NSS به‌سرعت از این کش پاسخ می‌دهد. این کش حتی به سیستم اجازه می‌دهد در صورت قطع موقت شبکه، کاربرانی که قبلاً موفق به لاگین شده‌اند، دوباره (با استفاده از آخرین اطلاعات کش‌شده) وارد شوند.

```ini
# /etc/sssd/sssd.conf
[sssd]
services = nss, pam
domains = corp.example.com

[domain/corp.example.com]
id_provider = ldap
auth_provider = ldap
ldap_uri = ldap://ldap.corp.example.com
ldap_search_base = dc=corp,dc=example,dc=com
cache_credentials = true
```
ا `cache_credentials = true` دقیقاً همان قابلیت کش امن که در بالا توضیح دادیم را فعال می‌کند.

```bash
systemctl enable --now sssd
id alice@corp.example.com
```

## ۱۱.۶ ا LDAP — دایرکتوری سلسله‌مراتبی اطلاعات

### مدل داده LDAP — DN و ساختار درختی

ا **LDAP (Lightweight Directory Access Protocol)** یک دیتابیس تخصصی برای ذخیره اطلاعات سلسله‌مراتبی (کاربران، گروه‌ها، ساختار سازمانی) است. هر ورودی (Entry) با یک **DN (Distinguished Name)** یکتا شناسایی می‌شود که مسیر کامل آن ورودی در درخت را نشان می‌دهد:

```
dn: uid=alice,ou=People,dc=corp,dc=example,dc=com
```

این را از راست به چپ (از کلی به جزئی) بخوانید: `dc=com` → `dc=example` → `dc=corp` (اجزای دامنه، Domain Component) → `ou=People` (یک واحد سازمانی، Organizational Unit) → `uid=alice` (خود کاربر با شناسه یکتا).

### دستورات پایه مدیریت LDAP

```bash
ldapsearch -x -b "dc=corp,dc=example,dc=com" "(uid=alice)"
```
ا `-x` احراز هویت ساده (نه SASL)؛ `-b` نقطه شروع جستجو در درخت (Base DN)؛ عبارت داخل پرانتز یک **فیلتر جستجو** است (اینجا: کاربرانی که `uid` آن‌ها دقیقاً `alice` است).

```bash
ldapadd -x -D "cn=admin,dc=corp,dc=example,dc=com" -W -f newuser.ldif
```
ا `-D` مشخص می‌کند با کدام هویت (Bind DN) به سرور متصل می‌شویم (اینجا حساب مدیر)؛ `-W` باعث می‌شود سیستم رمز عبور را تعاملی بپرسد؛ `-f` فایل LDIF (فرمت متنی استاندارد برای تعریف/تغییر ورودی‌های LDAP) حاوی داده جدید است.

```bash
slapcat
```
یک dump کامل از کل دیتابیس LDAP به فرمت LDIF — بسیار مفید برای Backup یا مهاجرت.

## ۱۱.۷ ا Kerberos — احراز هویت رمزنگاری‌شده بدون ارسال رمز روی شبکه

### مشکل بنیادین که Kerberos حل می‌کند

در بسیاری از پروتکل‌های ساده‌تر، برای احراز هویت، رمز عبور (یا نسخه هش‌شده آن) باید از کلاینت به سرور از طریق شبکه ارسال شود. حتی با رمزنگاری TLS، این یعنی رمز واقعی (یا معادل قابل‌استفاده آن) در یک لحظه‌ای از پروتکل روی شبکه منتقل می‌شود — یک نقطه ریسک بالقوه. **Kerberos** با یک رویکرد کاملاً متفاوت این ریسک را از بین می‌برد: رمز عبور **هرگز** روی شبکه ارسال نمی‌شود، حتی به‌صورت رمزنگاری‌شده.

### مفهوم Ticket — بلیط‌های موقت به‌جای ارسال مکرر رمز

ایده اصلی Kerberos شبیه یک پارک تفریحی است: شما یک‌بار در ورودی (که Kerberos آن را **KDC — Key Distribution Center** می‌نامد) هویت خودتان را (با رمز عبور) ثابت می‌کنید و یک **بلیط اصلی (TGT — Ticket Granting Ticket)** دریافت می‌کنید. از این لحظه، برای دسترسی به هر سرویس خاص در آن پارک (هر «دستگاه بازی»)، به‌جای نشان دادن مجدد کارت شناسایی، فقط بلیط اصلی خودتان را نشان می‌دهید و یک **بلیط خدمت (Service Ticket)** کوچک‌تر و مخصوص همان سرویس دریافت می‌کنید — بدون این‌که هرگز دوباره لازم باشد رمز عبور اصلی خود را نشان دهید.

```bash
kinit alice
```
دریافت اولین TGT با احراز هویت رمز عبور (تنها لحظه‌ای که رمز واقعاً درگیر می‌شود، و حتی آن‌جا هم مستقیماً روی شبکه ارسال نمی‌شود — از یک مکانیزم رمزنگاری متقارن استفاده می‌شود).

```bash
klist
```
نمایش تمام بلیط‌های (TGT و Service Tickets) فعلی که این کاربر در اختیار دارد، همراه با زمان انقضای هرکدام — دقیقاً همان دلیلی که در ابتدای این بخش گفتیم چرا زمان دقیق سیستم برای Kerberos حیاتی است: این بلیط‌ها معمولاً عمر بسیار کوتاهی (چند ساعت) دارند.

```bash
kdestroy
```
حذف تمام بلیط‌های فعلی (معادل مفهومی "logout" از دید Kerberos).

📌 ا Kerberos پایه احراز هویت در بسیاری از محیط‌های Enterprise (مخصوصاً Active Directory ویندوزی، که در بخش ۵ هنگام یکپارچه‌سازی Samba با AD دیدیم) است — وقتی گفتیم `security = ads`، در پس‌زمینه این دقیقاً Kerberos است که کار احراز هویت واقعی را انجام می‌دهد.

## ۱۱.۸ ا sudo — دسترسی موقت و کنترل‌شده به امتیازات بالاتر

### چرا sudo بهتر از لاگین مستقیم به‌عنوان root است

اگر همه کاربران مدیریتی مستقیماً با حساب `root` کار کنند، دو مشکل بزرگ به وجود می‌آید: **عدم ردیابی مسئولیت** (اگر ۵ نفر رمز root را بدانند و یک اشتباه رخ دهد، هیچ راهی برای فهمیدن «کدام‌شان این کار را کرد» وجود ندارد — همه لاگ‌ها فقط «root» را نشان می‌دهند)، و **عدم کنترل دقیق** (یا کسی دسترسی کامل root دارد، یا هیچ — نمی‌توان گفت «این کاربر فقط اجازه ری‌استارت سرویس nginx را دارد، نه هر کار دیگری»).

ا **sudo** هر دو مشکل را حل می‌کند: کاربران با حساب شخصی و رمز خودشان لاگین می‌کنند، و برای اجرای یک دستور خاص با امتیاز بالاتر، از `sudo` استفاده می‌کنند — که هم در لاگ دقیقاً ثبت می‌شود «کدام کاربر واقعی این دستور خاص را اجرا کرد»، و هم می‌توان به‌طور دقیق کنترل کرد چه کسی اجازه اجرای چه دستوراتی را دارد.

### فایل تنظیمات — /etc/sudoers

```bash
visudo
```
⚠️ همیشه باید از `visudo` (نه ویرایش مستقیم فایل با یک ویرایشگر معمولی) استفاده کرد — `visudo` قبل از ذخیره نهایی، صحت syntax فایل را بررسی می‌کند؛ یک خطای syntax در `/etc/sudoers` می‌تواند به‌طور کامل قابلیت استفاده از `sudo` را برای همه (حتی خود root در برخی حالت‌ها) از بین ببرد.

```
alice   ALL=(ALL:ALL) ALL
%webadmins   ALL=(www-data) /usr/sbin/nginx, /bin/systemctl restart nginx
```

خط اول: کاربر `alice` می‌تواند از هر ترمینال (`ALL`)، به‌عنوان هر کاربر و هر گروه (`ALL:ALL`)، هر دستوری (`ALL`) را اجرا کند — دسترسی کامل.

خط دوم: تمام اعضای گروه `webadmins` (نماد `%` یعنی گروه، نه کاربر) فقط می‌توانند به‌عنوان کاربر `www-data` (نه root)، و فقط دو دستور مشخص (`nginx` مستقیم، یا ری‌استارت سرویس nginx از طریق systemctl) را اجرا کنند — این دقیقاً همان کنترل دقیق و محدود است که با لاگین مستقیم root غیرممکن بود.

```bash
sudo -l                       # نمایش این‌که کاربر فعلی چه دستوراتی اجازه اجرا با sudo دارد
sudo -u www-data whoami         # اجرای یک دستور به‌عنوان یک کاربر دیگر (نه فقط root)
```

## ۱۱.۹ خلاصه نکات کلیدی برای آزمون

- تفاوت RTC (سخت‌افزاری، همیشه در حال کار حتی وقتی خاموش) و System Clock (نرم‌افزاری، فقط وقتی سیستم روشن است) را بدانید
- ا Chrony جانشین مدرن ntpd است؛ `chronyc tracking` وضعیت همگام‌سازی و `chronyc sources -v` منابع فعلی را نشان می‌دهد
- ا PAM چهار type دارد (`auth`, `account`, `password`, `session`)؛ تفاوت control ها (`required`/`requisite`/`sufficient`/`optional`) رفتار زنجیره را کاملاً تغییر می‌دهد
- تفاوت بنیادین PAM (احراز هویت — آیا رمز درست است؟) و NSS (شناسایی — این کاربر کیست؟ اطلاعاتش کجاست؟) را دقیق بدانید
- ا SSSD یک لایه واسط کش‌شده بین سیستم محلی و دایرکتوری خارجی (LDAP/AD) است؛ `cache_credentials` امکان لاگین حتی در قطعی موقت شبکه را می‌دهد
- در LDAP، DN از راست (کلی) به چپ (جزئی) خوانده می‌شود
- ا Kerberos هرگز رمز عبور واقعی را روی شبکه ارسال نمی‌کند؛ به‌جای آن از بلیط‌های موقت (TGT و Service Ticket) استفاده می‌کند — که به‌شدت به همگام بودن زمان سیستم‌ها وابسته‌اند
- همیشه از `visudo` برای ویرایش `/etc/sudoers` استفاده کنید، هرگز مستقیم ویرایش نکنید
- ا sudo دو مشکل لاگین مستقیم root را حل می‌کند: ردیابی دقیق مسئولیت، و کنترل دقیق دسترسی به دستورات خاص
