> هر دستور بلافاصله بعد از خودش یک بخش «🔍 تحلیل دستور» دارد که تک‌تک سوییچ‌های آن را جداگانه توضیح می‌دهد.

---

## سناریو ۱ (مبتدی): ساخت و استفاده از یک جفت‌کلید SSH ساده (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوهای پیچیده سخت‌سازی کامل، باید ساده‌ترین چرخه — ساخت کلید و اتصال با آن — را یک‌بار کامل انجام داده باشید.

### قدم‌به‌قدم

**۱. ساخت جفت‌کلید جدید**
```bash
ssh-keygen -t ed25519 -C "test@example"
```
🔍 **تحلیل دستور:**
- `-t ed25519`: مخفف `--type` — نوع الگوریتم کلید؛ `ed25519` نسبت به `rsa` سنتی سریع‌تر و با کلید کوچک‌تر امنیت معادل یا بالاتر دارد.
- `-C "test@example"`: مخفف `--comment` — یک یادداشت متنی دلخواه که در انتهای فایل کلید عمومی ذخیره می‌شود، معمولاً برای شناسایی راحت‌تر مالک کلید.

**۲. مشاهده فایل‌های ساخته‌شده**
```bash
ls -la ~/.ssh/
```
🔍 **تحلیل دستور:** باید دو فایل جدید ببینید — `id_ed25519` (کلید **خصوصی**، هرگز نباید به اشتراک گذاشته شود) و `id_ed25519.pub` (کلید **عمومی**، قابل اشتراک).

**۳. کپی کلید عمومی به یک سرور**
```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub alice@server
```
🔍 **تحلیل دستور:** `-i`: مخفف `--identity` — مسیر دقیق فایل کلید **عمومی** که باید کپی شود؛ `ssh-copy-id` خودکار محتوای این فایل را به انتهای `~/.ssh/authorized_keys` روی سرور مقصد اضافه می‌کند.

**۴. تست اتصال با کلید (بدون رمز عبور)**
```bash
ssh -i ~/.ssh/id_ed25519 alice@server
```
🔍 **تحلیل دستور:** `-i` این‌بار روی خود `ssh` (نه `ssh-copy-id`)، صراحتاً مشخص می‌کند کدام کلید خصوصی برای احراز هویت استفاده شود (معمولاً اگر نام فایل استاندارد باشد، نیازی به این سوییچ نیست چون `ssh` خودش پیدا می‌کند).

**۵. بررسی مجوزهای صحیح**
```bash
chmod 600 ~/.ssh/id_ed25519
```
🔍 **تحلیل دستور:** `600` (فقط مالک بخواند/بنویسد) — SSH از نظر امنیتی اتصال را رد می‌کند اگر کلید خصوصی مجوز بازتری داشته باشد.

### ✅ Best Practice
همیشه `ed25519` را برای کلیدهای جدید ترجیح دهید، مگر یک سیستم بسیار قدیمی نیاز به `rsa` داشته باشد.

## سناریو ۲ (مبتدی): نصب و راه‌اندازی Fail2ban با تنظیمات پیش‌فرض (سطح مبتدی)

### زمینه و چرایی
قبل از سناریوی پیچیده تست عملی مسدودسازی، باید ساده‌ترین راه‌اندازی اولیه را انجام دهید.

### قدم‌به‌قدم

**۱. نصب**
```bash
apt install fail2ban -y
```

**۲. بررسی فایل تنظیمات پیش‌فرض**
```bash
cat /etc/fail2ban/jail.conf | grep -A5 "^\[sshd\]"
```
🔍 **تحلیل دستور:** `-A5`: نمایش ۵ خط بعد از خط `[sshd]`؛ الگوی جستجو `^\[sshd\]` — `^` یعنی شروع خط، بک‌اسلش‌ها escape کردن پرانتز مربعی (که در regex معنای خاص دارند).

**۳. ساخت فایل override شخصی (روش صحیح، نه ویرایش مستقیم jail.conf)**
```bash
cat > /etc/fail2ban/jail.local << 'EOF'
[sshd]
enabled = true
EOF
```
🔍 **تحلیل دستور:** فایل `.local` (نه `.conf`) — قرارداد Fail2ban این است که فایل‌های `.local` مقادیر فایل `.conf` اصلی را override می‌کنند، بدون نیاز به ویرایش مستقیم فایل پکیج (مشابه فلسفه Drop-in که در systemd دیدیم).

**۴. راه‌اندازی**
```bash
systemctl enable --now fail2ban
```

**۵. بررسی وضعیت کلی**
```bash
fail2ban-client status
```
🔍 **تحلیل دستور:** بدون آرگومان اضافه؛ لیست تمام jail های فعال (مثل `sshd`).

### 📌 نکته آزمون
همیشه از فایل `.local` برای override استفاده کنید، هرگز فایل `.conf` اصلی را مستقیم ویرایش نکنید.

## سناریو ۳: سخت‌سازی کامل SSH با ترتیب صحیح (سطح متوسط تا پیشرفته)

### قدم‌به‌قدم

**۱. تایید کارکرد کلید قبل از هر تغییر**
```bash
ssh -i ~/.ssh/id_ed25519 admin@server "echo Key auth works"
```
🔍 **تحلیل دستور:** آرگومان آخر (رشته دستور) — وقتی به `ssh` یک دستور داده شود، فقط همان دستور را روی سرور راه دور اجرا می‌کند و بلافاصله خارج می‌شود (بدون باز کردن یک نشست تعاملی کامل).

**۲. اعمال تدریجی تنظیمات سخت‌سازی**
```bash
cat >> /etc/ssh/sshd_config << 'EOF'
PermitRootLogin no
PasswordAuthentication no
MaxAuthTries 3
EOF
```
🔍 **تحلیل دستور:** `MaxAuthTries 3`: محدود کردن تعداد تلاش‌های احراز هویت **در یک اتصال واحد** به ۳ بار، قبل از قطع کامل آن اتصال.

**۳. بررسی صحت قبل از اعمال**
```bash
sshd -t
```
🔍 **تحلیل دستور:** `-t`: مخفف `--test` روی `sshd` — بررسی syntax فایل تنظیمات بدون واقعاً راه‌اندازی مجدد سرویس؛ اگر خطا داشته باشد، اینجا مشخص می‌شود، نه بعد از restart که ممکن است سرویس بالا نیاید.

**۴. اعمال با نشست موازی باز**
```bash
systemctl restart sshd
```

**۵. تست منفی رمز عبور**
```bash
ssh -o PreferredAuthentications=password admin@server
```
🔍 **تحلیل دستور:** `-o PreferredAuthentications=password`: مخفف `--option` — اجبار SSH به تلاش **فقط** با روش رمز عبور (نه کلید)، برای تایید این‌که این روش واقعاً مسدود شده.

### ✅ Best Practice
ترتیب: کلید بساز → تست کن → سپس رمز عبور را غیرفعال کن.

## سناریو ۴: راه‌اندازی WireGuard برای دسترسی امن از راه دور (سطح پیشرفته)

### قدم‌به‌قدم

**۱. تولید کلید سرور**
```bash
wg genkey | tee /etc/wireguard/server_private.key | wg pubkey > /etc/wireguard/server_public.key
```
🔍 **تحلیل دستور:**
- `wg genkey`: تولید یک کلید خصوصی تصادفی جدید، چاپ‌شده در خروجی استاندارد.
- `tee FILE`: خواندن ورودی، هم‌زمان چاپ روی صفحه **و** نوشتن در فایل مشخص‌شده — این ابزار به شما اجازه می‌دهد یک جریان داده را هم ذخیره کنید هم به دستور بعدی لوله‌کشی کنید.
- `| wg pubkey`: کلید خصوصی (که از `tee` عبور کرده) به دستور دوم لوله‌کشی می‌شود که کلید عمومی متناظر را از آن محاسبه می‌کند.
- `> server_public.key`: ذخیره کلید عمومی محاسبه‌شده در فایل جدا.

**۲. تعریف اینترفیس سرور**
```bash
cat > /etc/wireguard/wg0.conf << EOF
[Interface]
PrivateKey = $(cat /etc/wireguard/server_private.key)
Address = 10.0.0.1/24
ListenPort = 51820
EOF
```
🔍 **تحلیل دستور:** `$(cat ...)`: Command Substitution — محتوای فایل کلید خصوصی مستقیماً در متن فایل تنظیمات جایگذاری می‌شود.

**۳. افزودن Peer (کلاینت)**
```bash
cat >> /etc/wireguard/wg0.conf << EOF

[Peer]
PublicKey = $(cat client_public.key)
AllowedIPs = 10.0.0.2/32
EOF
```
🔍 **تحلیل دستور:** `AllowedIPs = 10.0.0.2/32`: مشخص می‌کند این Peer خاص فقط مجاز به استفاده از این یک IP دقیق است (`/32` یعنی فقط همین یک آدرس، نه یک محدوده).

**۴. راه‌اندازی**
```bash
wg-quick up wg0
```
🔍 **تحلیل دستور:** `wg-quick`: یک ابزار کمکی سطح بالاتر از `wg` خام — علاوه بر تنظیم پارامترهای WireGuard، خودکار اینترفیس شبکه را هم می‌سازد و روت‌های لازم را اضافه می‌کند.

**۵. بررسی وضعیت**
```bash
wg show
```
🔍 **تحلیل دستور:** بدون آرگومان، نمایش خلاصه تمام اینترفیس‌های WireGuard فعال، Peer های هرکدام، و آخرین زمان handshake موفق.

### ✅ Best Practice
پورت VPN را باز نگه دارید، اما سرورهای داخلی را فقط از طریق tunnel VPN در دسترس قرار دهید.

## سناریو ۵: تست عملی مسدودسازی خودکار Fail2ban (سطح متوسط)

### قدم‌به‌قدم

**۱. تنظیم آستانه پایین برای تست سریع**
```bash
cat > /etc/fail2ban/jail.local << 'EOF'
[sshd]
enabled = true
maxretry = 3
bantime = 600
findtime = 120
EOF
```
🔍 **تحلیل دستور:** `maxretry = 3`: تعداد تلاش ناموفق مجاز قبل از مسدودسازی؛ `findtime = 120`: پنجره زمانی (ثانیه) که در آن این تلاش‌ها شمارش می‌شوند؛ `bantime = 600`: مدت مسدودسازی (ثانیه).

**۲. راه‌اندازی مجدد با تنظیمات جدید**
```bash
systemctl restart fail2ban
```

**۳. شبیه‌سازی تلاش‌های ناموفق**
```bash
for i in {1..4}; do ssh baduser@localhost -o PasswordAuthentication=yes 2>&1 | head -1; done
```
🔍 **تحلیل دستور:** حلقه تکرار ۴ بار (بیشتر از `maxretry=3`) برای اطمینان از عبور از آستانه.

**۴. بررسی وضعیت مسدودسازی**
```bash
fail2ban-client status sshd
```
🔍 **تحلیل دستور:** آرگومان `sshd` (نام jail خاص) برخلاف سناریو ۲ که بدون آرگومان بود — این‌بار جزئیات همان یک jail، شامل لیست IP های مسدودشده.

**۵. بازگشایی دستی**
```bash
fail2ban-client set sshd unbanip 127.0.0.1
```
🔍 **تحلیل دستور:** `set sshd unbanip`: زیردستور تغییر وضعیت — `set` برای اعمال یک تغییر (برخلاف `status` که فقط خواندنی است)، `unbanip` عملیات خاص، و آرگومان آخر IP هدف.

### 📌 نکته آزمون
ا `findtime` و `bantime` باید متناسب با ریسک واقعی تنظیم شوند.

## سناریو ۶: دفاع لایه‌ای کامل SSH — ترکیب همه ابزارها (سطح پیشرفته، جمع‌بندی)

### قدم‌به‌قدم

**۱. لایه فایروال**
```bash
nft add rule inet filter input ip saddr 10.0.9.0/24 tcp dport 22 accept
nft add rule inet filter input tcp dport 22 drop
```
🔍 **تحلیل دستور:** دو قانون پشت‌سرهم — اول اجازه صریح برای شبکه مدیریتی، دوم رد **همه** بقیه تلاش‌ها روی همین پورت (چون قانون اول با اولویت بالاتر/قبل‌تر بررسی می‌شود).

**۲. لایه SSH config**
```bash
grep -E "PasswordAuthentication|PermitRootLogin" /etc/ssh/sshd_config
```

**۳. لایه Fail2ban**
```bash
fail2ban-client status sshd
```

**۴. لایه PAM**
```bash
grep google_authenticator /etc/pam.d/sshd
```

**۵. تست یکپارچه نهایی**
```bash
ssh -o PreferredAuthentications=password admin@server
```
🔍 **تحلیل دستور:** همان تست منفی سناریو ۳؛ اینجا برای تایید این‌که حتی اگر بسته از فایروال هم عبور کند، لایه بعدی (SSH config) همچنان آن را متوقف می‌کند.

### 📌 نکته آزمون نهایی
چهار لایه کاملاً مستقل (فایروال، SSH config، Fail2ban، PAM) با هم دفاع در عمق واقعی برای تنها درِ ورودی مدیریتی سرور می‌سازند.

## جمع‌بندی مهارت‌های این بخش

- ساخت و استفاده پایه از جفت‌کلید SSH با `ssh-keygen`/`ssh-copy-id`
- راه‌اندازی اولیه Fail2ban با فایل `.local` صحیح
- سخت‌سازی کامل SSH با ترتیب ایمن و تحلیل هر تنظیم
- راه‌اندازی WireGuard با تحلیل عمیق الگوی `tee`/Command Substitution
- تست عملی مسدودسازی خودکار Fail2ban با تحلیل `maxretry`/`findtime`/`bantime`
- دفاع لایه‌ای کامل ترکیبی برای تنها درِ ورودی مدیریتی سرور
