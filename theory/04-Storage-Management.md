# بخش ۴: Storage Management (مدیریت ذخیره‌سازی)

> پیش‌نیاز مفهومی: در بخش ۳ یاد گرفتیم فایل‌سیستم چیست و چگونه mount می‌شود. اما قبل از این‌که بتوانیم یک فایل‌سیستم بسازیم، باید بفهمیم دیسک فیزیکی چگونه به «پارتیشن‌های» قابل‌استفاده تقسیم می‌شود — و چگونه می‌توانیم لایه‌های انعطاف‌پذیرتری (LVM) یا مقاوم‌تری (RAID) روی آن‌ها بسازیم.

---

## ۴.۱ مبانی دیسک — از پلاتر مغناطیسی تا آرایه فلش

### دو نسل سخت‌افزار ذخیره‌سازی

ا **HDD (Hard Disk Drive)** یک دیسک مغناطیسی چرخان است — داده روی صفحات فلزی مغناطیسی (پلاتر) که با سرعت بالا می‌چرخند نوشته می‌شود و یک بازوی مکانیکی (Head) روی سطح آن حرکت می‌کند تا داده را بخواند یا بنویسد. این حرکت مکانیکی، سرعت HDD را محدود می‌کند و باعث می‌شود دسترسی تصادفی (Random Access — خواندن فایل‌های پراکنده در نقاط مختلف دیسک) بسیار کندتر از دسترسی متوالی (Sequential Access) باشد.

ا **SSD (Solid State Drive)** هیچ قطعه متحرکی ندارد — داده مستقیماً در تراشه‌های حافظه فلش (مشابه اما پیچیده‌تر از حافظه یک فلش‌درایو USB) ذخیره می‌شود. چون هیچ بازوی مکانیکی نیاز به جابه‌جایی ندارد، سرعت دسترسی تصادفی SSD به‌طور چشمگیری بالاتر از HDD است.

📌 این تفاوت در دنیای واقعی اهمیت زیادی دارد: بارهای کاری با دسترسی تصادفی زیاد (مثل دیتابیس‌ها) از SSD سود چشمگیر می‌برند، در حالی که ذخیره‌سازی آرشیوی متوالی (مثل backup های بزرگ) گاهی همچنان با HDD (که هزینه هر گیگابایت پایین‌تری دارد) مقرون‌به‌صرفه‌تر است.

### چگونه سیستم‌عامل به دیسک دسترسی پیدا می‌کند؟ — نام‌گذاری دستگاه‌ها

هر دیسکی که کرنل شناسایی می‌کند، یک فایل دستگاه (Device File) در `/dev/` می‌گیرد:

- ا `/dev/sda`, `/dev/sdb`, ... : دیسک‌های متصل از طریق SATA/SAS/USB (رابط استاندارد SCSI)
- ا `/dev/nvme0n1`, `/dev/nvme1n1`, ... : دیسک‌های NVMe (SSD های مدرن با رابط PCIe بسیار سریع‌تر از SATA)
- ا `/dev/vda`, `/dev/vdb`, ... : دیسک‌های مجازی در محیط‌های مجازی‌سازی‌شده با virtio (رایج در KVM/QEMU)

حرف بعد از `sd`/`vd` (مثل `a`, `b`, `c`) ترتیب شناسایی دیسک توسط کرنل را نشان می‌دهد؛ برای دیسک‌های NVMe، شماره‌گذاری کمی متفاوت است (`nvme0n1` یعنی namespace شماره ۱ روی کنترلر NVMe شماره ۰).

⚠️ نکته بسیار مهم: این نام‌گذاری‌ها **می‌توانند بین بوت‌ها تغییر کنند**، خصوصاً اگر چند دیسک اضافه/حذف شوند (دیسکی که همیشه `/dev/sdb` بود، ممکن است بعد از افزودن یک دیسک جدید، `/dev/sdc` شود). این دقیقاً همان دلیلی است که در بخش ۳ گفتیم چرا در `fstab` باید از UUID استفاده کرد، نه نام دستگاه مستقیم.

## ۴.۲ جدول پارتیشن — MBR در برابر GPT

### چرا نمی‌توانیم مستقیماً کل دیسک را یک فایل‌سیستم واحد کنیم؟

از نظر فنی می‌توانستیم (و گاهی برای دیسک‌های ساده این کار انجام می‌شود)، اما تقسیم یک دیسک فیزیکی واحد به چند **پارتیشن (Partition)** منطقی، انعطاف بسیار بیشتری می‌دهد: می‌توانید فایل‌سیستم‌های مختلف برای اهداف مختلف داشته باشید (مثلاً یک پارتیشن کوچک برای `/boot` که همیشه باید ext4 ساده باشد، و یک پارتیشن بزرگ‌تر برای داده‌ها با XFS)، یا چند سیستم‌عامل روی یک دیسک نصب کنید.

**جدول پارتیشن (Partition Table)** ساختار داده‌ای است که در ابتدای دیسک ذخیره می‌شود و مشخص می‌کند دیسک به چند بخش تقسیم شده و هر بخش دقیقاً از کدام سکتور تا کدام سکتور را اشغال می‌کند.

### استاندارد قدیمی MBR

ا **MBR (Master Boot Record)** جدول پارتیشن سنتی است که از دهه ۱۹۸۰ استفاده می‌شود. MBR در دقیقاً ۵۱۲ بایت اول دیسک ذخیره می‌شود و شامل: کد بوت‌لودر اولیه (که در بخش ۱ به‌عنوان Stage 1 GRUB دیدیم)، و اطلاعات حداکثر **۴ پارتیشن اصلی (Primary Partition)**.

این محدودیت ۴ پارتیشن یک مشکل عملی ایجاد می‌کرد، پس یک راه‌حل دورزدن ابداع شد: یکی از این ۴ پارتیشن می‌تواند به‌عنوان **پارتیشن گسترده (Extended Partition)** تعریف شود که خودش می‌تواند شامل چندین **پارتیشن منطقی (Logical Partition)** باشد — یک لایه غیرمستقیم برای دور زدن محدودیت سخت‌افزاری اصلی.

محدودیت‌های مهم MBR:
- حداکثر ۴ پارتیشن اصلی (یا ۳ اصلی + ۱ گسترده با چند منطقی داخل آن)
- حداکثر اندازه دیسک قابل‌آدرس‌دهی: ۲ ترابایت (به‌خاطر استفاده از عدد ۳۲ بیتی برای آدرس‌دهی سکتور)
- بدون هیچ مکانیزم داخلی برای بررسی خرابی جدول پارتیشن (اگر آن ۵۱۲ بایت خراب شود، کل اطلاعات پارتیشن‌بندی از دست می‌رود)

### استاندارد مدرن GPT  

ا **GPT (GUID Partition Table)** جانشین مدرن MBR است که بخشی از مشخصات UEFI است (هرچند می‌تواند با BIOS هم — با محدودیت‌هایی — استفاده شود). GPT این محدودیت‌ها را برطرف می‌کند:

- بدون محدودیت عملی در تعداد پارتیشن‌ها (معمولاً تا ۱۲۸ پارتیشن به‌طور پیش‌فرض، بدون نیاز به مفهوم پیچیده «گسترده/منطقی»)
- پشتیبانی از دیسک‌های بسیار بزرگ‌تر (تئوری تا حدود ۹.۴ زتابایت)
- هر پارتیشن یک **GUID (شناسه یکتای جهانی)** مخصوص به خودش دارد، نه فقط یک شماره ساده
- شامل **نسخه پشتیبان از خودِ جدول پارتیشن** در انتهای دیسک — اگر جدول اصلی در ابتدای دیسک خراب شود، سیستم می‌تواند از نسخه پشتیبان در انتها بازیابی کند
- شامل **Checksum (CRC32)** برای تشخیص خودکار خرابی جدول

📌 امروزه برای دیسک‌های جدید، خصوصاً روی سیستم‌های UEFI، تقریباً همیشه باید GPT استفاده کرد، مگر یک محدودیت سازگاری خاص با سیستم‌های بسیار قدیمی وجود داشته باشد.

### ابزارهای پارتیشن‌بندی

ا **fdisk** — ابزار سنتی، در ابتدا فقط MBR را پشتیبانی می‌کرد اما نسخه‌های مدرن آن اکنون از GPT هم پشتیبانی می‌کنند:
```bash
fdisk -l                    # نمایش تمام دیسک‌ها و پارتیشن‌بندی فعلی
fdisk /dev/sdb               # ورود به رابط تعاملی برای دیسک sdb
```
داخل رابط تعاملی `fdisk`، دستورات تک‌حرفی رایج: `n` (پارتیشن جدید)، `d` (حذف پارتیشن)، `p` (نمایش جدول فعلی)، `t` (تغییر نوع پارتیشن)، `w` (نوشتن تغییرات روی دیسک و خروج)، `q` (خروج بدون ذخیره).

ا **gdisk** — معادل fdisk اما اختصاصاً برای GPT، با رابط و دستورات بسیار مشابه:
```bash
gdisk /dev/sdb
```

ا **parted** — ابزار قدرتمندتر که هم MBR و هم GPT را پشتیبانی می‌کند و مهم‌تر، **قابلیت اسکریپت‌نویسی (غیرتعاملی)** دارد که برای اتوماسیون بسیار مفید است:
```bash
parted /dev/sdb --script mklabel gpt
parted /dev/sdb --script mkpart primary ext4 0% 100%
parted -l
```
ا `mklabel gpt` نوع جدول پارتیشن را روی GPT تنظیم می‌کند؛ `mkpart primary ext4 0% 100%` یک پارتیشن که کل فضای دیسک (از ۰٪ تا ۱۰۰٪) را اشغال می‌کند می‌سازد.

### اطلاع‌رسانی به کرنل بعد از تغییر پارتیشن‌بندی

وقتی جدول پارتیشن یک دیسک را تغییر می‌دهید، کرنل که از قبل این دیسک را با پارتیشن‌بندی **قدیمی** شناخته، باید مطلع شود که جدول تغییر کرده:

```bash
partprobe /dev/sdb
```
ا `partprobe` کرنل را وادار می‌کند جدول پارتیشن دیسک مشخص‌شده را دوباره بخواند، بدون نیاز به ریبوت کامل سیستم.

## ۴.۳  لایه انتزاعی بین دیسک فیزیکی و فایل‌سیستم — LVM 

### مشکلی که LVM حل می‌کند

فرض کنید یک پارتیشن ext4 مستقیم روی `/dev/sdb1` ساخته‌اید و بعد از مدتی فضای آن تمام می‌شود. با پارتیشن‌بندی سنتی، بزرگ کردن این پارتیشن بسیار محدود و پرریسک است (باید فضای خالی *بلافاصله بعد* از آن پارتیشن روی همان دیسک فیزیکی وجود داشته باشد، و حتی آن‌وقت هم عملیات دستکاری مستقیم جدول پارتیشن خطرناک است). اگر بخواهید فضا را از **یک دیسک فیزیکی کاملاً دیگر** اضافه کنید، اصلاً امکان‌پذیر نیست — یک پارتیشن سنتی نمی‌تواند بین دو دیسک فیزیکی «کش بیاید».

ا **LVM (Logical Volume Manager)** یک لایه انتزاعی اضافی بین دیسک‌های فیزیکی خام و فایل‌سیستم نهایی قرار می‌دهد که این محدودیت‌ها را کاملاً برطرف می‌کند.

### معماری سه‌لایه LVM

```text
دیسک/پارتیشن فیزیکی خام (/dev/sdb1, /dev/sdc1, ...)
        ↓  (pvcreate)

Physical Volume — PV
        ↓  (vgcreate/vgextend)

Volume Group — VG   (یک «استخر» مشترک از فضای چند PV)
        ↓  (lvcreate)

Logical Volume — LV   (یک «برش» از این استخر، که فایل‌سیستم روی آن ساخته می‌شود)
        ↓  (mkfs)

فایل‌سیستم (ext4/xfs/...)
```

ا **Physical Volume (PV):** یک دیسک یا پارتیشن خام که «آماده‌سازی» شده تا بتواند بخشی از LVM باشد. این آماده‌سازی یک متادیتای کوچک LVM در ابتدای آن دستگاه می‌نویسد.

```bash
pvcreate /dev/sdb1 /dev/sdc1
pvdisplay
pvs                          # نمایش خلاصه‌تر (یک خط برای هر PV)
```

ا **Volume Group (VG):** یک «استخر» مجازی از فضا که از یک یا چند PV تشکیل شده است. از این لحظه به بعد، مرز فیزیکی بین دیسک‌های مختلف از دید کاربر محو می‌شود — VG فقط یک عدد بزرگ از فضای کل موجود را نشان می‌دهد.

```bash
vgcreate <" vg_data ">  /dev/sdb1 /dev/sdc1
vgdisplay vg_data
vgs
```

ا **Logical Volume (LV):** یک «برش» با اندازه مشخص از فضای VG، که رفتاری کاملاً مشابه یک پارتیشن سنتی دارد (روی آن `mkfs` اجرا می‌کنید و mount می‌کنید)، اما با یک تفاوت بنیادین: چون از یک استخر مشترک آمده، تغییر اندازه آن (تا وقتی فضای کافی در VG موجود باشد) بسیار ساده‌تر و انعطاف‌پذیرتر است.

```bash
lvcreate -L 50G -n <" lv_web ">  vg_data          # ساخت LV با اندازه دقیق مشخص (50 گیگابایت)
lvcreate -l 100%FREE -n lv_data vg_data      # استفاده از تمام فضای باقی‌مانده VG (توجه: -l کوچک، نه -L بزرگ، برای درصد/تعداد extent به‌جای حجم مطلق)
lvdisplay
lvs
```

📌 دستگاه نهایی LV در مسیر `/dev/<VG_NAME>/<LV_NAME>` (مثلاً `/dev/vg_data/lv_web`) یا معادل آن `/dev/mapper/vg_data-lv_web` قابل دسترسی است.

### چرا LVM این‌قدر انعطاف‌پذیر است؟ — مفهوم Extent

در پس‌زمینه، LVM فضای هر PV را به واحدهای کوچک با اندازه ثابت به نام **Physical Extent (PE)** تقسیم می‌کند (اندازه پیش‌فرض معمولاً ۴ مگابایت). یک LV در واقع چیزی نیست جز یک **نگاشت** از تعدادی Extent منطقی (Logical Extent) به این Extent های فیزیکی — که می‌توانند از **هر PV در آن VG** بیایند، حتی اگر روی دیسک‌های فیزیکی کاملاً متفاوتی باشند.

این طراحی همان چیزی است که امکان **بزرگ کردن یک LV با اضافه کردن یک دیسک کاملاً جدید** را فراهم می‌کند — چیزی که با پارتیشن‌بندی سنتی هرگز ممکن نبود.

### افزایش فضای LVM — گام‌به‌گام مفهومی

```bash
#i  فرض: یک دیسک جدید /dev/sdd به سرور اضافه شده و می‌خواهیم فضای LV موجود را افزایش دهیم

pvcreate /dev/sdd                     # آماده‌سازی دیسک جدید به‌عنوان PV
vgextend <" vg_data ">  /dev/sdd              # اضافه کردن این PV به VG موجود (فضای VG اکنون بزرگ‌تر شده)
lvextend -L +100G -r /dev/vg_data/lv_web    # بزرگ کردن LV و همزمان resize فایل‌سیستم (-r)
```
همان‌طور که در بخش ۳ (Filesystems) دیدیم، `-r` در `lvextend` هر دو مرحله (بزرگ کردن LV و رشد فایل‌سیستم روی آن) را در یک دستور واحد ترکیب می‌کند.

### کوچک کردن — ترتیب معکوس و حیاتی

⚠️ این تکرار عمدی است چون یکی از پرتکرارترین نکات آزمون LPIC-2 است: برای **کوچک کردن**، ترتیب باید **دقیقاً معکوس** بزرگ کردن باشد:

```bash
umount /mnt/data
e2fsck -f /dev/vg_data/lv_web
resize2fs /dev/vg_data/lv_web 30G      # ابتدا فایل‌سیستم را کوچک کن
lvreduce -L 30G /dev/vg_data/lv_web     # سپس LV را کوچک کن
```
اگر ترتیب برعکس شود (اول LV کوچک شود، بعد فایل‌سیستم)، بخشی از داده که هنوز روی فضای حذف‌شده LV قرار دارد از بین می‌رود — این خطا می‌تواند به‌طور کامل غیرقابل‌بازگشت باشد.

### گرفتن Snapshot 

ا **LVM Snapshot** یک قابلیت قدرتمند است که به شما اجازه می‌دهد در یک لحظه خاص، یک «کپی مجازی» از وضعیت فعلی یک LV بسازید، بدون این‌که واقعاً تمام داده را فیزیکی کپی کنید.

نحوه کار داخلی: وقتی یک Snapshot می‌سازید، LVM شروع می‌کند به ردیابی **تغییرات** روی LV اصلی از آن لحظه به بعد؛ هر بار که یک بلاک داده روی LV اصلی تغییر می‌کند، **نسخه قدیمی آن بلاک** (قبل از تغییر) در فضای اختصاصی Snapshot ذخیره می‌شود (این تکنیک را **Copy-on-Write** می‌نامند). به این ترتیب، Snapshot همیشه می‌تواند وضعیت دقیق لحظه ایجاد را بازسازی کند، اما فقط برای بلاک‌هایی که واقعاً تغییر کرده‌اند فضای اضافی مصرف می‌شود — نه کل حجم داده.

```bash
lvcreate -L 5G -s -n lv_web_snapshot /dev/vg_data/lv_web
```
ا `-s` مشخص می‌کند این یک Snapshot است (نه یک LV عادی جدید)؛ `-L 5G` فضایی است که برای ذخیره تغییرات آینده در نظر گرفته می‌شود (نه اندازه کل داده — چون Snapshot از فضای مشترک با اصل استفاده می‌کند).

⚠️ اگر حجم تغییرات از فضای اختصاص‌یافته به Snapshot بیشتر شود، آن Snapshot **نامعتبر (invalid)** می‌شود و دیگر قابل استفاده نیست — پس باید فضای کافی متناسب با میزان تغییرات مورد انتظار در بازه زمانی نگهداری Snapshot، در نظر گرفت.

**کاربرد اصلی Snapshot در دنیای واقعی:** گرفتن یک Backup سازگار (Consistent) از یک فایل‌سیستم در حال استفاده فعال (مثلاً یک دیتابیس). چون خود عملیات ساخت Snapshot تقریباً آنی است، می‌توانید بلافاصله از آن Snapshot (که یک لحظه دقیق و ثابت را نشان می‌دهد) یک Backup کامل بگیرید، در حالی که LV اصلی همچنان بدون وقفه به کار خودش (و تغییر دادن داده) ادامه می‌دهد.

```bash
mount /dev/vg_data/lv_web_snapshot /mnt/snapshot-backup
tar czf /backup/consistent-backup.tar.gz -C /mnt/snapshot-backup .
umount /mnt/snapshot-backup
lvremove /dev/vg_data/lv_web_snapshot     # بعد از اتمام backup، Snapshot را حذف می‌کنیم (فضایش را پس می‌دهد)
```

### تخصیص فضای «مجازی» بیشتر از فضای واقعی —  Thin Provisioning 

ا **Thin Provisioning** یک قابلیت پیشرفته‌تر LVM است که به شما اجازه می‌دهد چندین LV بسازید که مجموع اندازه «اعلامی» آن‌ها بیشتر از فضای فیزیکی واقعی موجود باشد — فضای واقعی فقط زمانی که داده واقعاً نوشته می‌شود، تخصیص داده می‌شود (شبیه یک اضافه‌برداشت بانکی کنترل‌شده).

```bash
lvcreate -L 100G -T vg_data/thinpool         # ساخت یک "استخر " با ظرفیت فیزیکی واقعی ۱۰۰ گیگابایت
lvcreate -V 500G -T vg_data/thinpool -n lv_thin1    # یک LV با اندازه "مجازی" 500 گیگابایت (بیشتر از استخر واقعی!)
lvs -a vg_data       # نمایش درصد استفاده واقعی استخر thin
```
⚠️ این قابلیت نیازمند مانیتورینگ دقیق است — اگر مجموع داده واقعی نوشته‌شده در تمام LV های thin به ظرفیت فیزیکی واقعی استخر برسد، نوشتن دیگر ممکن نخواهد بود، حتی اگر از دید هر LV به‌تنهایی هنوز فضای «مجازی» باقی مانده باشد.

### جابه‌جایی داده بین دیسک‌های فیزیکی بدون قطعی — Migration  

یکی از قدرتمندترین قابلیت‌های LVM، امکان جابه‌جایی داده از یک PV به PV دیگر است، **در حالی که سیستم کاملاً آنلاین و در حال استفاده است** — بسیار مفید هنگام تعویض یک دیسک قدیمی‌تر با یک دیسک جدید:

```bash
pvmove /dev/sdb1 /dev/sdd1
```
ا `pvmove` تمام Extent های فیزیکی داده‌ای که روی `/dev/sdb1` قرار دارند را به‌تدریج و بدون وقفه به `/dev/sdd1` منتقل می‌کند. بعد از اتمام، `/dev/sdb1` را می‌توان با خیال راحت از VG حذف کرد (`vgreduce`) و فیزیکی از سیستم خارج نمود.

## ۴.۴ افزونگی و کارایی با ترکیب چند دیسک — RAID  

### چرا به RAID نیاز داریم؟ (این بخش با هدف متفاوت از LVM است)

توجه کنید LVM انعطاف‌پذیری فضا را حل می‌کند، اما هیچ محافظتی در برابر **خرابی فیزیکی دیسک** ارائه نمی‌دهد — اگر یک PV از بین برود، تمام داده روی آن (و هر LV که از آن استفاده می‌کرد) از بین می‌رود. **RAID (Redundant Array of Independent Disks)** مشکل کاملاً متفاوتی را حل می‌کند: چگونه چند دیسک فیزیکی را طوری ترکیب کنیم که خرابی یک (یا حتی چند) دیسک، باعث از دست رفتن داده نشود.

### سطوح اصلی RAID و منطق پشت هرکدام

**RAID 0 — Striping (بدون افزونگی)**

داده به قطعات کوچک تقسیم شده و به‌طور متناوب روی تمام دیسک‌ها نوشته می‌شود (قطعه اول روی دیسک ۱، قطعه دوم روی دیسک ۲، قطعه سوم دوباره روی دیسک ۱، و...). چون همه دیسک‌ها می‌توانند هم‌زمان بخوانند/بنویسند، سرعت به‌طور چشمگیری افزایش می‌یابد. اما هیچ افزونگی وجود ندارد — اگر **هرکدام** از دیسک‌ها از کار بیفتد، **تمام داده کل آرایه** از دست می‌رود (چون هر فایل روی هر دو دیسک پخش شده). به همین دلیل، RAID 0 در واقع نه‌تنها محافظتی اضافه نمی‌کند، بلکه ریسک خرابی را (نسبت به یک دیسک تنها) **افزایش** هم می‌دهد.

**RAID 1 — Mirroring (افزونگی کامل)**

داده به‌طور کامل و یکسان روی هر دو (یا بیشتر) دیسک نوشته می‌شود — هرکدام یک کپی دقیقاً یکسان از دیگری است. اگر یک دیسک از کار بیفتد، دیسک دیگر همچنان تمام داده را دارد و سیستم بدون وقفه به کار ادامه می‌دهد. هزینه: فضای قابل‌استفاده نهایی فقط برابر با **یک** دیسک است (نه مجموع همه)، چون نیمی (یا بیشتر) فضا صرف کپی تکراری می‌شود.

**RAID 5 — Striping با Parity توزیع‌شده**

داده مثل RAID 0 روی چند دیسک پخش می‌شود، اما علاوه بر آن، یک بلاک اطلاعات ریاضی به نام **Parity** (که با عملیات XOR روی بلاک‌های داده محاسبه می‌شود) هم روی دیسک‌ها ذخیره می‌شود. اگر **دقیقاً یک** دیسک از کار بیفتد، سیستم می‌تواند با استفاده از Parity و داده باقی‌مانده روی دیسک‌های سالم، محتوای دیسک ازدست‌رفته را **بازسازی (rebuild)** کند. حداقل ۳ دیسک لازم است؛ فضای قابل‌استفاده معادل (تعداد دیسک - ۱) است — مثلاً با ۴ دیسک ۲ ترابایتی، فضای نهایی ۶ ترابایت است (یک دیسک معادل صرف Parity می‌شود، هرچند Parity واقعی به‌طور مساوی روی همه دیسک‌ها توزیع شده، نه روی یک دیسک ثابت).

**RAID 6 — مشابه RAID 5 اما با دو Parity**

دقیقاً مثل RAID 5، اما با **دو** بلاک Parity مستقل، که یعنی حتی اگر **دو** دیسک هم‌زمان از کار بیفتند، داده همچنان قابل‌بازیابی است. حداقل ۴ دیسک لازم است. مناسب برای آرایه‌های بزرگ که زمان rebuild طولانی است (در طول rebuild یک RAID 5، اگر دیسک دوم هم خراب شود، تمام داده از دست می‌رود؛ RAID 6 این ریسک را کاهش می‌دهد).

**RAID 10 — ترکیب Mirror و Stripe**

چند جفت Mirror (RAID 1) ساخته می‌شود، و سپس این جفت‌ها با هم Stripe (RAID 0) می‌شوند. نتیجه، هم سرعت بالا (از Striping) و هم افزونگی قوی (از Mirroring) است، اما هزینه فضایی آن مشابه RAID 1 (فقط نیمی از کل فضا قابل‌استفاده است) باقی می‌ماند. حداقل ۴ دیسک لازم است.

| سطح | حداقل دیسک | فضای قابل‌استفاده | تحمل خرابی | کاربرد رایج |
|---|---|---|---|---|
| RAID 0 | ۲ | ۱۰۰٪ | هیچ (ریسک بیشتر!) | کش موقت، داده غیرحیاتی که سرعت اولویت دارد |
| RAID 1 | ۲ | ۵۰٪ | ۱ دیسک | سیستم‌عامل، داده‌های حیاتی کوچک |
| RAID 5 | ۳ | (n-1)/n | ۱ دیسک | فایل‌سرور عمومی با تعادل هزینه/امنیت |
| RAID 6 | ۴ | (n-2)/n | ۲ دیسک | آرایه‌های بزرگ که rebuild طولانی دارند |
| RAID 10 | ۴ | ۵۰٪ | حداقل ۱ از هر جفت | دیتابیس‌های با کارایی بالا |

### ابزار RAID نرم‌افزاری لینوکس — mdadm  

```bash
mdadm --create <" /dev/md0 "> --level=5 --raid-devices=3 <" /dev/sdb1 ">  <" /dev/sdc1 ">  <" /dev/sdd1 ">
```
ا `--create` یک آرایه جدید می‌سازد؛ `--level=5` نوع RAID؛ `--raid-devices=3` تعداد دیسک‌های عضو؛ نام دستگاه نهایی (`/dev/md0`) از الگوی «multiple device» گرفته شده.

بعد از ساخت، آرایه بلافاصله شروع به یک فرآیند پس‌زمینه به نام **Sync اولیه (Initial Resync)** می‌کند — محاسبه و نوشتن مقادیر Parity برای تمام فضا، حتی اگر هنوز داده واقعی روی آن ننوشته باشید. این فرآیند می‌تواند بسته به اندازه دیسک‌ها، ساعت‌ها طول بکشد.

```bash
cat /proc/mdstat
```
نمایش وضعیت زنده تمام آرایه‌های RAID، شامل درصد پیشرفت Sync اولیه یا Rebuild.

```bash
mdadm --detail /dev/md0
```
اطلاعات کامل و دقیق آرایه: وضعیت هر دیسک عضو (`active sync` یا `faulty` یا `spare`)، سطح RAID، اندازه کل.

### شبیه‌سازی و مدیریت خرابی دیسک

```bash
mdadm /dev/md0 --fail /dev/sdc1        # علامت‌گذاری دستی یک دیسک به‌عنوان خراب (برای تست، یا وقتی خرابی واقعی رخ داده)
mdadm --detail /dev/md0                  # وضعیت آرایه اکنون "degraded" است اما همچنان کار می‌کند (اگر سطح RAID افزونگی دارد)
mdadm /dev/md0 --remove /dev/sdc1        # حذف رسمی دیسک خراب از آرایه (آماده برای تعویض فیزیکی)

# بعد از تعویض فیزیکی دیسک (یا وصل کردن یک دیسک جایگزین جدید):
mdadm /dev/md0 --add /dev/sde1
cat /proc/mdstat      # مشاهده فرآیند Rebuild خودکار شروع‌شده
```

### دیسک پشتیبان آماده‌به‌کار — Hot Spare  

یک **Hot Spare** دیسکی است که از ابتدا به آرایه معرفی شده اما در حالت غیرفعال/آماده‌باش باقی می‌ماند؛ به محض این‌که یکی از دیسک‌های فعال خراب شود، mdadm به‌طور **کاملاً خودکار** (بدون نیاز به دخالت دستی) شروع به rebuild با استفاده از این دیسک پشتیبان می‌کند — این زمان واکنش به خرابی را به‌شدت کاهش می‌دهد (نیازی به این نیست که یک انسان متوجه خرابی شود و دستی دیسک جدید اضافه کند).

```bash
mdadm --create /dev/md0 --level=5 --raid-devices=3 --spare-devices=1 /dev/sdb1 /dev/sdc1 /dev/sdd1 /dev/sde1
```
اینجا ۳ دیسک فعال (`raid-devices=3`) و ۱ دیسک پشتیبان (`spare-devices=1`) تعریف شده‌اند.

### Bitmap — تسریع Rebuild بعد از خاموشی موقت (نه خرابی کامل)

اگر یک آرایه RAID به‌خاطر یک خاموشی موقت (نه خرابی دائمی دیسک) sync خودش را از دست بدهد، به‌طور پیش‌فرض mdadm مجبور است **کل** آرایه را از نو Sync/Rebuild کند — که برای دیسک‌های بزرگ بسیار زمان‌بر است. یک **Write-Intent Bitmap** رکورد کوچکی نگه می‌دارد که مشخص می‌کند کدام بخش‌های آرایه اخیراً تغییر کرده‌اند، تا در صورت این‌گونه وقفه‌های کوتاه، فقط همان بخش‌های تغییریافته (نه کل آرایه) دوباره sync شوند.

```bash
mdadm --grow /dev/md0 --bitmap=internal
```

### ذخیره‌سازی دائمی تنظیمات RAID — نکته حیاتی که تکرار می‌کنیم

همان‌طور که در بخش ۱ (initramfs) با جزئیات دیدیم، این مرحله برای بوت صحیح **الزامی** است:

```bash
mdadm --detail --scan >> /etc/mdadm/mdadm.conf     # 🔵
mdadm --detail --scan >> /etc/mdadm.conf             # 🔴
update-initramfs -u                                    # 🔵
dracut --force                                          # 🔴
```

## ۴.۵  رمزنگاری کامل دیسک — LUKS 

### مدل تهدید — از چه چیزی محافظت می‌کنیم؟

رمزنگاری دیسک با LUKS مشخصاً در برابر **دسترسی فیزیکی غیرمجاز** محافظت می‌کند: اگر یک دیسک (یا کل سرور) سرقت شود، یا یک دیسک قدیمی بدون پاک‌سازی صحیح دور انداخته شود، بدون دانستن passphrase، محتوای آن کاملاً غیرقابل‌خواندن (به‌صورت عملی، رمزگشایی بدون کلید از نظر محاسباتی غیرممکن) است.

⚠️ نکته مهم مدل تهدید: LUKS در برابر یک مهاجم که به یک **سیستم در حال اجرا و باز شده** دسترسی پیدا می‌کند (مثلاً از طریق یک آسیب‌پذیری نرم‌افزاری با سیستم روشن) محافظت **نمی‌کند** — چون در آن حالت، دیسک از قبل باز (unlock) شده و داده به‌صورت عادی در دسترس است. LUKS محافظت در برابر **سرقت فیزیکی دیسک خاموش** است، نه یک فایروال یا آنتی‌ویروس.

### دو لایه مکمل — LUKS و dm-crypt  

ا **dm-crypt** بخش سطح کرنل (device-mapper) است که واقعاً عملیات رمزنگاری/رمزگشایی زنده داده را در پس‌زمینه انجام می‌دهد. **LUKS (Linux Unified Key Setup)** یک لایه مدیریتی روی dm-crypt است که استاندارد می‌کند چگونه passphrase ها به کلید رمزنگاری واقعی تبدیل شوند و چگونه چند passphrase مختلف بتوانند به یک کلید مشترک دسترسی داشته باشند.

### ا Key Slots — چرا چند passphrase ممکن است؟

ا LUKS به‌طور پیش‌فرض حداکثر **۸ Key Slot** دارد. کلید رمزنگاری واقعی داده (Master Key) هرگز مستقیماً از passphrase شما مشتق نمی‌شود؛ در عوض، یک Master Key تصادفی یک‌بار (در زمان `luksFormat`) تولید می‌شود، و passphrase شما فقط برای **رمزگشایی همان Master Key** (که خودش در هدر LUKS، رمزنگاری‌شده ذخیره است) استفاده می‌شود.

این طراحی یک مزیت بزرگ دارد: می‌توانید **چند passphrase مختلف** (مثلاً یکی برای خودتان، یکی برای یک همکار، یکی به‌عنوان پشتیبان اضطراری) تعریف کنید که هرکدام مستقل می‌توانند همان Master Key را باز کنند — و اگر یکی از آن‌ها compromise شد، می‌توانید فقط همان یک Key Slot را حذف کنید (`luksRemoveKey`) **بدون نیاز به رمزنگاری مجدد کل دیسک** (چون Master Key واقعی تغییر نکرده، فقط یکی از راه‌های دسترسی به آن حذف شده).

```bash
cryptsetup luksFormat /dev/sdb1
```
این دستور یک Master Key تصادفی جدید می‌سازد، آن را با اولین passphrase (که از شما می‌پرسد) رمزنگاری می‌کند و در Key Slot شماره ۰ ذخیره می‌کند. ⚠️ این عملیات کاملاً داده موجود روی پارتیشن را از بین می‌برد؛ فقط روی یک پارتیشن خالی یا جدید اجرا شود.

```bash
cryptsetup luksAddKey /dev/sdb1
```
یک passphrase جدید (در یک Key Slot خالی دیگر) اضافه می‌کند — از شما یکی از passphrase های **موجود** (برای اثبات مجاز بودن) و سپس passphrase **جدید** را می‌پرسد.

```bash
cryptsetup luksRemoveKey /dev/sdb1
```
یک passphrase خاص را حذف می‌کند (بدون تاثیر روی سایر Key Slot ها یا خود داده).

```bash
cryptsetup luksDump /dev/sdb1
```
نمایش اطلاعات کامل هدر LUKS، شامل این‌که کدام Key Slot ها فعال هستند و پارامترهای رمزنگاری (الگوریتم، طول کلید) در حال استفاده.

### باز کردن و استفاده از پارتیشن رمزنگاری‌شده

```bash
cryptsetup luksOpen /dev/sdb1 secure_data
```
با وارد کردن یک passphrase معتبر، یک دستگاه mapped جدید در `/dev/mapper/secure_data` ساخته می‌شود — این دستگاه، نسخه **رمزگشایی‌شده و شفاف** پارتیشن است؛ هر خواندن/نوشتنی که روی آن انجام دهید، به‌طور خودکار (توسط dm-crypt در سطح کرنل) رمزگشایی/رمزنگاری می‌شود، کاملاً نامرئی برای فایل‌سیستم و برنامه‌ها.

```bash
mkfs.ext4 /dev/mapper/secure_data
mount /dev/mapper/secure_data /mnt/secure
```
از این لحظه، `/mnt/secure` دقیقاً مثل هر mount point دیگری کار می‌کند — تفاوت فقط این است که تمام داده روی دیسک فیزیکی به‌صورت رمزنگاری‌شده ذخیره است.

```bash
umount /mnt/secure
cryptsetup luksClose secure_data
```
بستن دستگاه mapped — از این لحظه، بدون باز کردن مجدد با passphrase، محتوای دیسک کاملاً غیرقابل‌دسترس است.

### ا mount خودکار در بوت — تعادل بین امنیت و راحتی

فایل `/etc/crypttab` مشابه `/etc/fstab` اما برای دستگاه‌های رمزنگاری‌شده است:

```
# /etc/crypttab
secure_data  UUID=xxxx-xxxx  none  luks
```
مقدار `none` (به‌جای مسیر یک فایل کلید) یعنی سیستم در بوت **passphrase را از کاربر می‌پرسد** — امن‌ترین حالت، اما نیازمند دخالت انسانی در هر ریبوت (مناسب سرورهایی که همیشه توسط یک اپراتور فیزیکی ریبوت می‌شوند).

جایگزین (کمتر امن اما خودکار):
```
secure_data  UUID=xxxx-xxxx  /root/keyfile  luks
```
با یک مسیر فایل کلید مشخص، سیستم بدون دخالت انسانی باز می‌شود — اما این یعنی اگر مهاجم به کل دیسک (شامل جایی که کلید ذخیره است) دسترسی پیدا کند، رمزنگاری عملاً بی‌اثر می‌شود.

- معماری سه‌لایه LVM: PV → VG → LV؛ انعطاف اصلی از این می‌آید که یک VG می‌تواند چند PV (حتی از دیسک‌های فیزیکی متفاوت) داشته باشد
- ترتیب معکوس extend/reduce در LVM را حفظ کنید: بزرگ‌سازی (LV سپس فایل‌سیستم)، کوچک‌سازی (فایل‌سیستم سپس LV)
- ا Snapshot از تکنیک Copy-on-Write استفاده می‌کند؛ فقط فضای متناسب با میزان **تغییرات** لازم دارد، نه کل داده
- تفاوت سطوح RAID را از نظر حداقل دیسک، فضای قابل‌استفاده، و تحمل خرابی دقیق بدانید (جدول بخش ۴.۴)
- ا RAID 0 هیچ افزونگی ندارد و ریسک را نسبت به یک دیسک تنها **افزایش** می‌دهد؛ این یک نکته آزمونی رایج و بدفهمیده‌شده است
- بعد از ساخت RAID، حتماً `mdadm.conf` را به‌روزرسانی و initramfs را بازسازی کنید
- ا LUKS از یک Master Key تصادفی استفاده می‌کند که passphrase های مختلف (در Key Slot های جدا) می‌توانند مستقل آن را باز کنند؛ حذف یک passphrase نیازی به رمزنگاری مجدد کل دیسک ندارد
- تفاوت `/etc/crypttab` با `none` (پرسیدن passphrase در بوت) و با یک keyfile (باز شدن خودکار، امنیت کمتر) را بدانید
