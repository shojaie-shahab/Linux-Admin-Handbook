# بخش ۱۰: DNS & DHCP

> پیش‌نیاز مفهومی: بخش ۹ (Networking) برای درک IP/Subnetting. این بخش دو سرویس زیرساختی حیاتی را پوشش می‌دهد: DNS (ترجمه نام به IP) و DHCP (تخصیص خودکار IP).

---

## ۱۰.۱ ا DNS — چرا اصلاً به یک سیستم نام‌گذاری نیاز داریم؟

### مشکل بنیادین: انسان‌ها با نام کار می‌کنند، کامپیوترها با عدد

در بخش ۹ دیدیم که ارتباط واقعی بین دو کامپیوتر بر اساس آدرس IP (مثل `93.184.216.34`) انجام می‌شود. اما هیچ انسانی نمی‌خواهد این اعداد را به خاطر بسپارد — ما با نام‌هایی مثل `example.com` راحت‌تریم. **DNS (Domain Name System)** یک سیستم توزیع‌شده و سلسله‌مراتبی است که این ترجمه (نام ↔ IP) را در مقیاس کل اینترنت انجام می‌دهد.

### چرا DNS باید سلسله‌مراتبی و توزیع‌شده باشد؟

فرض کنید یک فایل واحد وجود داشت که تمام نام‌های دامنه دنیا و IP متناظرشان را نگه می‌داشت — این فایل باید روی یک سرور مرکزی می‌بود که هر جستجوی DNS در کل جهان (میلیاردها بار در روز) باید به آن مراجعه می‌کرد؛ چنین سیستمی هم از نظر کارایی و هم از نظر مقاومت در برابر خرابی (اگر آن یک سرور از کار بیفتد، کل اینترنت از کار می‌افتد) کاملاً غیرعملی است.

راه‌حل DNS، تقسیم این مسئولیت به یک **ساختار درختی سلسله‌مراتبی** است، که هر سطح از درخت، فقط مسئول بخش کوچکی از فضای نام است:

```
.  (Root — نقطه، معمولاً نامرئی در نوشتار روزمره)
 └── com.
      └── example.com.
           ├── www.example.com.
           └── mail.example.com.
```

هر سطح این درخت را یک **Zone** می‌نامند، و مسئولیت هر Zone (اضافه/تغییر رکوردهای آن) می‌تواند به یک سازمان کاملاً متفاوت واگذار شده باشد — سرورهای Root فقط می‌دانند «برای پیدا کردن هر چیزی زیر `.com`، باید به این سرورهای خاص مراجعه کنی»، و سرورهای `.com` فقط می‌دانند «برای `example.com`، باید به این سرور خاص مراجعه کنی»، و الی‌آخر — هیچ سرور واحدی مسئول *همه* اطلاعات نیست.

### فرآیند کامل یک DNS Lookup — از ابتدا تا انتها

وقتی شما در مرورگر `www.example.com` را تایپ می‌کنید، این فرآیند (به‌صورت ساده‌شده) رخ می‌دهد:

**۱. بررسی کش محلی**: ابتدا سیستم شما (و مرورگر) بررسی می‌کند آیا این نام را اخیراً جستجو کرده و پاسخ را در حافظه نگه داشته — اگر بله، بلافاصله از آن استفاده می‌شود، بدون هیچ ترافیک شبکه‌ای اضافی.

**۲. مراجعه به Resolver پیکربندی‌شده**: اگر در کش نبود، سیستم به سرور DNS که در `/etc/resolv.conf` تعریف شده (معمولاً یک **Recursive Resolver** — مثل سرور DNS ISP شما یا یک سرور عمومی مثل `8.8.8.8`) درخواست می‌فرستد.

**۳. ا Recursive Resolver کار سنگین را انجام می‌دهد**: این سرور (که خودش معمولاً کش بزرگی دارد) اگر پاسخ را از قبل نمی‌داند، شروع به پیمایش درخت DNS از بالا به پایین می‌کند: ابتدا از یک سرور **Root** می‌پرسد («کجا می‌توانم `.com` را پیدا کنم؟»)، سپس از سرور **TLD** (Top-Level Domain، مسئول `.com`) می‌پرسد («کجا می‌توانم `example.com` را پیدا کنم؟»)، و در نهایت از سرور **Authoritative** (مرجع نهایی و واقعی برای `example.com`) پاسخ دقیق IP را دریافت می‌کند.

**۴. بازگشت پاسخ و کش کردن**: پاسخ نهایی به سیستم شما بازگردانده می‌شود، و در هر مرحله از این مسیر (هم روی Recursive Resolver، هم روی سیستم شما) برای مدتی مشخص (بر اساس **TTL** — Time To Live — که در ادامه توضیح می‌دهیم) کش می‌شود تا جستجوهای بعدی سریع‌تر باشند.

## ۱۰.۲ انواع سرور DNS و نقش هرکدام

| نوع | نقش |
|---|---|
| **Recursive Resolver** | سرویس‌دهنده به کلاینت‌ها؛ کار سنگین پیمایش درخت DNS را انجام می‌دهد |
| **Authoritative (Master/Primary)** | منبع اصلی و قابل‌ویرایش داده‌های یک Zone خاص |
| **Authoritative (Slave/Secondary)** | کپی خودکار (از طریق Zone Transfer) از Master، برای افزونگی و توزیع بار |
| **Caching-only** | فقط پاسخ‌های دیگران را موقتاً نگه می‌دارد، هیچ Zone اختصاصی خودش ندارد |
| **Forwarding** | تمام درخواست‌های دریافتی را به یک سرور دیگر (معمولاً یک Resolver قدرتمندتر) هدایت می‌کند، بدون خودش پیمایش کامل انجام دهد |

📌 نکته مهم: یک سرور فیزیکی می‌تواند هم‌زمان چند نقش داشته باشد (مثلاً هم Authoritative برای Zone های خودش باشد، هم به‌عنوان Recursive Resolver برای کلاینت‌های داخلی سازمان عمل کند) — این دو نقش از نظر مفهومی مجزا هستند اما می‌توانند روی یک نرم‌افزار (مثل BIND) پیکربندی شوند.

## ۱۰.۳ انواع رکورد DNS و کاربرد هرکدام

| رکورد | کاربرد |
|---|---|
| `A` | نگاشت نام به آدرس IPv4 |
| `AAAA` | نگاشت نام به آدرس IPv6 |
| `CNAME` | یک نام مستعار (Alias) که به نام دیگری اشاره می‌کند (نه مستقیم به IP) |
| `MX` | مشخص می‌کند کدام سرور مسئول دریافت ایمیل این دامنه است (با یک عدد اولویت) |
| `NS` | مشخص می‌کند کدام سرورها برای این Zone معتبر (Authoritative) هستند |
| `PTR` | نگاشت معکوس — از IP به نام (در یک ساختار Zone خاص به نام `in-addr.arpa`) |
| `SOA` | اطلاعات مدیریتی کلی Zone (سریال، Refresh/Retry timing) |
| `TXT` | داده متنی آزاد — کاربردهای رایج: SPF (تایید سرورهای مجاز ارسال ایمیل)، DKIM، تایید مالکیت دامنه |
| `SRV` | مکان‌یابی یک سرویس خاص (مثل LDAP یا SIP) با پورت و اولویت |

### چرا CNAME با A متفاوت است — یک نکته مفهومی مهم

فرض کنید `www.example.com` باید به همان IP که `example.com` دارد اشاره کند. دو روش ممکن است: یا مستقیماً یک رکورد `A` جداگانه با همان IP برای `www` بسازید، یا یک رکورد `CNAME` بسازید که می‌گوید «`www.example.com` همان چیزی است که `example.com` هست، هرچه که باشد».

مزیت CNAME: اگر بعداً IP سرور اصلی تغییر کند، فقط باید رکورد `A` برای `example.com` را به‌روزرسانی کنید — `www` که CNAME است، خودکار همان IP جدید را «به ارث می‌برد»، بدون نیاز به تغییر جداگانه. این برای مدیریت راحت‌تر بسیار مفید است، اما CNAME یک محدودیت مهم دارد: **در رکورد ریشه یک دامنه (Apex/Root، مثل خود `example.com` بدون هیچ زیردامنه‌ای) نمی‌توان CNAME قرار داد** — این یکی از قوانین فنی پروتکل DNS است که باید همیشه در نظر گرفته شود.

## ۱۰.۴ ا BIND9 — پیاده‌سازی مرجع DNS در لینوکس

### ساختار فایل‌های تنظیمات

| فایل/مسیر | نقش |
|---|---|
| `named.conf` (یا `named.conf.options`) | تنظیمات کلی سرور (recursion، forwarders، امنیت) |
| `named.conf.local` (یا داخل `named.conf`) | تعریف Zone های میزبانی‌شده |
| فایل‌های Zone (مثل `db.example.com`) | داده واقعی رکوردهای هر Zone |

### تعریف یک Zone به‌عنوان Master

```bash
# vi /etc/bind/named.conf

zone "example.com" {
    type master;
    file "/etc/bind/zones/db.example.com";
    allow-transfer { 192.168.1.20; };
};
```

### فایل Zone — نگاه دقیق‌تر به سریال و TTL

```bash
# vi /etc/bind/zones/db.example.com

$TTL    86400
@       IN      SOA     ns1.example.com. admin.example.com. (
                        2026081501   ; Serial
                        3600         ; Refresh
                        1800         ; Retry
                        1209600      ; Expire
                        86400 )      ; Negative Cache TTL
@       IN      NS      ns1.example.com.
ns1     IN      A       192.168.1.10
www     IN      A       192.168.1.20
```

ا **Serial**: یک عدد که باید بعد از **هر** تغییر در فایل Zone افزایش یابد. فرمت رایج `YYYYMMDDNN` (سال-ماه-روز-شماره تغییر همان روز). این عدد تنها راهی است که سرورهای Slave می‌فهمند «آیا نسخه‌ای که من دارم قدیمی است؟» — اگر Serial افزایش نیابد، Slave فکر می‌کند هیچ تغییری رخ نداده و هرگز به‌روزرسانی نمی‌گیرد، حتی اگر محتوای Zone واقعاً تغییر کرده باشد.

ا **Refresh/Retry/Expire**: زمان‌بندی مربوط به رفتار Slave — چند وقت یک‌بار باید Serial را چک کند (Refresh)، اگر Master در دسترس نبود چقدر صبر کند قبل از تلاش مجدد (Retry)، و اگر برای مدت طولانی (Expire) اصلاً نتواند به Master برسد، چه زمانی داده خودش را «منقضی و غیرقابل‌اعتماد» اعلام کند و پاسخ‌دهی را متوقف کند.

ا **TTL** (هم سراسری در بالای فایل، هم قابل‌تنظیم به‌ازای هر رکورد): مدت زمانی که یک پاسخ DNS باید توسط Resolver ها کش شود. TTL کوتاه یعنی تغییرات سریع‌تر در سراسر اینترنت منتشر می‌شوند اما بار بیشتری روی سرور DNS شما می‌گذارد (چون کش‌ها زودتر منقضی می‌شوند و باید دوباره پرسیده شود)؛ TTL طولانی یعنی کارایی بهتر اما تغییرات کندتر منتشر می‌شوند.

📌 یک تکنیک عملیاتی رایج: قبل از یک تغییر برنامه‌ریزی‌شده مهم (مثل مهاجرت سرور)، چند ساعت/روز از قبل TTL آن رکورد را موقتاً کاهش می‌دهند (مثلاً به ۵ دقیقه)، تا وقتی واقعاً IP تغییر می‌کند، این تغییر خیلی سریع در سراسر اینترنت منتشر شود، نه این‌که کاربران ساعت‌ها همچنان به IP قدیمی (کش‌شده) هدایت شوند.




در فایل Zone، هر نامی که به نقطه (.) ختم نشود، یک «نام نسبی» محسوب می‌شود و Bind به‌طور خودکار مقدار $ORIGIN (که معمولاً همان نام دامنه است) را به انتهای آن اضافه می‌کند.

مثال خطرناک: اگر به‌جای ns1.example.com. (با نقطه در انتها)، اشتباهاً بنویسید ns1.example.com (بدون نقطه)، Bind آن را به‌صورت ns1.example.com.example.com. تفسیر می‌کند — چون فکر می‌کند ns1.example.com یک نام نسبی است و دامنه‌ی اصلی را به آن اضافه می‌کند.

📌 قانون طلایی: همیشه نام‌های کامل (FQDN) را با یک نقطه در انتها بنویسید، مگر اینکه واقعاً قصد استفاده از نام نسبی داشته باشید (مثل www که به www.example.com. تبدیل می‌شود).

✉️ نکته‌ی فرمت ایمیل در SOA (تبدیل @ به .)
در خط SOA، فیلد دوم (admin.example.com.) در واقع آدرس ایمیل مدیر است، اما به‌دلیل اینکه کاراکتر @ در فایل‌های Zone معنی خاصی دارد (معادل $ORIGIN)، باید از . به‌جای @ استفاده کنید.

یعنی admin.example.com. در اینجا معادل admin@example.com است.

اگر ایمیل شما admin@mail.example.com است، باید به‌صورت admin.mail.example.com. نوشته شود (باز هم نقطه به‌جای @).


### فایل Zone معکوس — PTR Records

```
; db.192.168.1  (برای zone: 1.168.192.in-addr.arpa)
@       IN      SOA     ns1.example.com. admin.example.com. ( ... )
@       IN      NS      ns1.example.com.
10      IN      PTR     ns1.example.com.
20      IN      PTR     www.example.com.
```
نام Zone معکوس به‌صورت برعکس اکتت‌های IP نوشته می‌شود (`1.168.192.in-addr.arpa` برای شبکه `192.168.1.0/24`) — این ساختار خاص به سیستم DNS اجازه می‌دهد جستجوی معکوس (IP به نام) را هم در همان چارچوب سلسله‌مراتبی درختی مدیریت کند.

### ابزارهای بررسی صحت و مدیریت

```bash
named-checkconf                                     # بررسی صحت syntax تنظیمات کلی
named-checkzone example.com /etc/bind/zones/db.example.com    # بررسی صحت یک فایل Zone خاص
rndc reload                                          # بارگذاری مجدد بدون قطعی کامل سرویس
rndc reload example.com                                # فقط یک Zone خاص را دوباره بارگذاری کن
```

⚠️ همیشه باید `named-checkzone` را **قبل** از `rndc reload` اجرا کرد — یک خطای syntax در فایل Zone می‌تواند باعث شود BIND کل آن Zone را رد کند و سرویس‌دهی برای آن دامنه کاملاً متوقف شود.

## ۱۰.۵ ا DHCP — تخصیص خودکار پیکربندی شبکه

### مشکلی که DHCP حل می‌کند

فرض کنید یک سازمان ۵۰۰ کامپیوتر دارد. اگر هر کامپیوتر باید دستی IP، Subnet Mask، Gateway، و سرورهای DNS را پیکربندی کند، این هم کار طاقت‌فرسایی است و هم بسیار مستعد خطا (تصادفاً دو کامپیوتر با IP یکسان پیکربندی شوند و تداخل ایجاد کنند). **DHCP (Dynamic Host Configuration Protocol)** این فرآیند را کاملاً خودکار می‌کند: کامپیوترها فقط درخواست می‌کنند «به من یک پیکربندی شبکه بده»، و یک سرور مرکزی DHCP این اطلاعات را به‌طور خودکار (و بدون تداخل) تخصیص می‌دهد.

### فرآیند DORA — چهار مرحله تخصیص

```
کلاینت                                    سرور DHCP
   │                                          │
   │──── Discover (Broadcast) ────────────────│   "کسی سرور DHCP هست؟"
   │                                          │
   │───── Offer ──────────────────────────────│   "بله، این IP رو بگیر"
   │                                          │
   │──── Request (Broadcast) ─────────────────│   "باشه، همین IP رو می‌خوام"
   │                                          │
   │───── Acknowledge ────────────────────────│   "تایید شد، مال توئه"
```

چرا مرحله **Discover** و **Request** هر دو به‌صورت **Broadcast** (نه مستقیم به یک IP خاص) هستند؟ چون در همان ابتدا، کلاینت هنوز **هیچ IP** ندارد (این دقیقاً همان چیزی است که می‌خواهد از DHCP بگیرد) — پس نمی‌تواند به یک IP خاص (سرور DHCP) پیام بفرستد؛ باید به‌صورت Broadcast (به همه در شبکه محلی) اعلام کند و منتظر بماند تا سرور(های) DHCP پاسخ دهند.

چرا Request هم دوباره Broadcast است، نه مستقیم به همان سرور که Offer داد؟ چون ممکن است **چند سرور DHCP** هم‌زمان Offer داده باشند (در یک شبکه با بیش از یک سرور DHCP)؛ با Broadcast کردن درخواست نهایی، کلاینت به تمام سرورها اعلام می‌کند «من پیشنهاد فلان سرور را قبول کردم» — این به سرورهای دیگر (که Offer دادند اما انتخاب نشدند) اجازه می‌دهد آن IP رزروشده موقت خودشان را آزاد کنند.

### پیکربندی سرور — dhcpd.conf

```bash
# vi /etc/dhcpcd.conf  or   /etc/dhcp/dhcpd.conf

default-lease-time 600;
max-lease-time 7200;
authoritative;

subnet 192.168.1.0 netmask 255.255.255.0 {
    range 192.168.1.100 192.168.1.200;
    option routers 192.168.1.1;
    option domain-name-servers 8.8.8.8, 1.1.1.1;
    option broadcast-address 192.168.1.255;
}
```

ا `authoritative;` به این سرور اعلام می‌کند که مرجع رسمی این subnet است — اگر یک کلاینت با یک lease نامعتبر (که این سرور آن را نمی‌شناسد) درخواست تمدید کند، سرور صراحتاً آن را رد می‌کند (به‌جای سکوت)، که به کلاینت اجازه می‌دهد سریع‌تر یک درخواست جدید و صحیح بسازد.

ا **Reservation** — تخصیص IP ثابت به یک دستگاه خاص بر اساس MAC Address (مفید برای پرینترها یا سرورهای داخلی که باید همیشه همان IP را داشته باشند، اما همچنان از راحتی مدیریت مرکزی DHCP بهره ببرند):
```bash 
# vi /etc/dhcpcd.conf  or   /etc/dhcp/dhcpd.conf

host printer-office1 {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 192.168.1.50;
}
```

### ا Lease Time — چرا IP ها «اجاره‌ای» هستند، نه دائمی

هر IP که DHCP تخصیص می‌دهد، فقط برای یک مدت زمان مشخص (**Lease Time**) معتبر است، نه برای همیشه. کلاینت باید قبل از پایان این مدت، تمدید (Renew) درخواست کند. چرا این طراحی مهم است؟ فرض کنید یک لپ‌تاپ مهمان یک بار به شبکه Wi-Fi وصل شده و یک IP گرفته، اما بعد برای همیشه شبکه را ترک می‌کند — بدون مفهوم Lease، آن IP برای همیشه «اشغال‌شده» باقی می‌ماند حتی وقتی هیچ دستگاهی واقعاً از آن استفاده نمی‌کند. با Lease Time، بعد از انقضا (و عدم تمدید، چون دستگاه دیگر آنجا نیست)، آن IP خودکار به استخر آزاد بازمی‌گردد و می‌تواند به دستگاه دیگری تخصیص یابد.

### ا DHCP Relay — وقتی سرور DHCP در یک شبکه دیگر است

به یاد بیاورید که مرحله Discover به‌صورت Broadcast است، و بسته‌های Broadcast **معمولاً از یک روتر عبور نمی‌کنند** (محدود به همان شبکه محلی می‌مانند). پس اگر سرور DHCP در یک subnet متفاوت از کلاینت‌ها باشد (رایج در شبکه‌های سازمانی بزرگ که یک سرور DHCP مرکزی به چند شبکه فیزیکی سرویس می‌دهد)، درخواست Discover هرگز به آن سرور نمی‌رسد.

ا **DHCP Relay Agent** این مشکل را حل می‌کند: یک سرویس (اغلب روی خود روتر آن شبکه، یا یک دستگاه اختصاصی) که پیام‌های Broadcast DHCP را در همان شبکه محلی می‌گیرد و آن‌ها را به‌صورت یک بسته **Unicast** مستقیم به سرور DHCP (که در subnet دیگری است) فوروارد می‌کند، و پاسخ را هم به همان ترتیب برمی‌گرداند.

```bash
dhcrelay -i eth1 192.168.1.10
```
این دستور یک نمونه لینوکسی از Relay Agent را روی اینترفیس `eth1` فعال می‌کند که تمام درخواست‌های DHCP دریافتی را به سرور `192.168.1.10` فوروارد می‌کند.

### عیب‌یابی DHCP

```bash
tcpdump -i eth0 port 67 or port 68     # مشاهده مستقیم ترافیک DHCP (پورت‌های استاندارد کلاینت/سرور)
dhclient -v eth0                        # اجرای دستی و verbose کلاینت DHCP (برای دیدن دقیق فرآیند DORA)
cat /var/lib/dhcp/dhcpd.leases           # بررسی دیتابیس lease های فعلی سمت سرور
```

## ۱۰.۶ خلاصه نکات کلیدی برای آزمون

- ا DNS یک ساختار سلسله‌مراتبی توزیع‌شده است؛ هیچ سرور واحدی مسئول تمام داده نیست
- تفاوت Master (قابل‌ویرایش) و Slave (کپی خودکار از طریق Zone Transfer، فقط‌خواندنی) را دقیق بدانید
- فراموش کردن افزایش Serial بعد از تغییر Zone، رایج‌ترین اشتباه عملی DNS است — Slave ها هرگز به‌روزرسانی نمی‌گیرند
- ا CNAME نمی‌تواند در رکورد ریشه (Apex) یک دامنه استفاده شود
- همیشه `named-checkzone` قبل از `rndc reload`
- فرآیند DHCP: Discover → Offer → Request → Acknowledge (DORA)؛ چرا Discover و Request هر دو Broadcast هستند را مفهومی درک کنید
- ا Lease Time مکانیزمی است که IP های بلااستفاده را خودکار به استخر آزاد بازمی‌گرداند
- ا DHCP Relay برای عبور درخواست‌های Broadcast بین subnet های مختلف ضروری است، چون Broadcast از روتر عبور نمی‌کند
- ا `authoritative;` در dhcpd.conf به سرور اجازه می‌دهد لیزهای نامعتبر را صراحتاً رد کند، نه نادیده بگیرد
