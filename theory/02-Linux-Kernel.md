# بخش ۲: Linux Kernel (هسته لینوکس)

> پیش‌نیاز مفهومی: بخش ۱ (System Startup) را قبل از این بخش بخوانید، چون آنجا فهمیدیم کرنل *چه زمانی* بارگذاری می‌شود. اینجا می‌فهمیم کرنل دقیقاً *چه کاری* در طول عمر سیستم انجام می‌دهد.

## ۲.۱ معماری کرنل — دو دنیای Kernel Space و User Space

### چرا اصلاً باید حافظه را به دو بخش تقسیم کنیم؟

فرض کنید هیچ مرزی بین برنامه‌ها و سخت‌افزار وجود نداشت — یعنی هر برنامه‌ای (مثلاً یک بازی یا یک مرورگر وب) می‌توانست مستقیماً به هر آدرس حافظه فیزیکی دسترسی داشته باشد و مستقیماً به دیسک دستور بنویسد. چه اتفاقی می‌افتاد؟

اول، **بی‌ثباتی کامل**: یک باگ ساده در یک برنامه (مثلاً نوشتن به یک آدرس حافظه اشتباه) می‌توانست حافظه‌ای که برنامه دیگری (یا حتی خود سیستم‌عامل) در حال استفاده از آن است را خراب کند و کل سیستم را کرش دهد.

دوم، **عدم امنیت**: هیچ راهی برای جلوگیری از این نبود که یک برنامه مخرب مستقیماً فایل‌های کاربر دیگری را بخواند یا رمزهای عبور را از حافظه سایر برنامه‌ها بردارد.

سوم، **پیچیدگی غیرقابل مدیریت**: هر برنامه‌نویسی که می‌خواست یک برنامه ساده بنویسد، مجبور بود دقیقاً بداند چگونه با صدها مدل مختلف کارت گرافیک، دیسک، و کارت شبکه صحبت کند.

راه‌حل این سه مشکل، تقسیم حافظه و دسترسی‌ها به دو ناحیه کاملاً مجزا با سطوح مختلف امتیاز است:

ا **Kernel Space (فضای کرنل):** ناحیه‌ای از حافظه که فقط خود کرنل به آن دسترسی کامل دارد. کدی که در Kernel Space اجرا می‌شود، می‌تواند مستقیماً با سخت‌افزار صحبت کند، به تمام حافظه فیزیکی دسترسی داشته باشد، و هیچ محدودیتی ندارد. CPU های مدرن این سطح دسترسی بالا را **Ring 0** (یا در معماری‌های جدیدتر، حالت‌های مشابه) می‌نامند.

ا **User Space (فضای کاربر):** ناحیه‌ای که تمام برنامه‌های عادی (مرورگر، ویرایشگر متن، سرورهای وب) در آن اجرا می‌شوند. کد در User Space **هیچ دسترسی مستقیمی** به سخت‌افزار یا حافظه فیزیکی سایر برنامه‌ها ندارد؛ فقط می‌تواند از طریق یک «درِ رسمی و کنترل‌شده» که کرنل فراهم می‌کند، درخواست بدهد. این سطح دسترسی محدود را **Ring 3** می‌نامند.

### ا System Call — تنها راه ارتباط User Space با Kernel Space

اگر یک برنامه در User Space بخواهد کاری انجام دهد که نیاز به دسترسی سخت‌افزاری دارد — مثلاً یک فایل را باز کند، داده‌ای را از شبکه بخواند، یا حافظه بیشتری درخواست کند — نمی‌تواند مستقیماً این کار را انجام دهد. باید یک درخواست رسمی به نام **System Call** (فراخوانی سیستمی) به کرنل ارسال کند.

فرآیند یک System Call به این شکل است:
۱. برنامه در User Space دستوری مثل «فایل X را باز کن» را با فراخوانی یک تابع کتابخانه‌ای استاندارد (مثل `open()` در زبان C) صادر می‌کند.
۲. این تابع کتابخانه‌ای، یک دستورالعمل ویژه CPU را اجرا می‌کند که باعث «تعویض حالت» (Mode Switch) از Ring 3 به Ring 0 می‌شود — یعنی کنترل موقتاً به کرنل داده می‌شود.
۳. کرنل درخواست را بررسی می‌کند: آیا این برنامه اصلاً مجاز به باز کردن این فایل هست؟ (بررسی مجوزها)
۴. اگر مجاز باشد، کرنل خودش (با دسترسی کامل Ring 0) عملیات واقعی را روی سخت‌افزار (دیسک) انجام می‌دهد.
۵. نتیجه به برنامه در User Space بازگردانده می‌شود و کنترل دوباره به Ring 3 برمی‌گردد.

می‌توانید System Call هایی که یک برنامه در حال اجرا صادر می‌کند را مستقیماً مشاهده کنید:

```bash
strace -c ls /tmp
```
ا `strace` تمام System Call هایی که دستور `ls` هنگام اجرا صادر می‌کند (مثل `openat`, `read`, `close`) را ردیابی و نمایش می‌دهد؛ فلگ `-c` یک خلاصه آماری (تعداد فراخوانی هرکدام) نشان می‌دهد. این ابزار برای عیب‌یابی عمیق («این برنامه دقیقاً کجا گیر کرده؟») بسیار مفید است.

📌 مثال‌های رایج System Call: `open` (باز کردن فایل)، `read`/`write` (خواندن/نوشتن)، `fork` (ساخت پردازش فرزند جدید)، `exec` (اجرای یک برنامه جدید)، `mmap` (نگاشت حافظه).

## ۲.۲ مدیریت پردازش‌ها — Scheduler و مفهوم Multitasking

### پردازش (Process) دقیقاً چیست؟

وقتی یک برنامه را اجرا می‌کنید (مثلاً با تایپ `firefox` در ترمینال)، کرنل یک نمونه در حال اجرا از آن برنامه می‌سازد که به آن **پردازش (Process)** می‌گویند. هر پردازش شامل:
- کد برنامه (دستورالعمل‌هایی که باید اجرا شوند)
- فضای حافظه اختصاصی خودش (که پردازش‌های دیگر نمی‌توانند مستقیماً به آن دسترسی داشته باشند)
- وضعیت فعلی رجیسترهای CPU (اگر پردازش موقتاً متوقف است، این اطلاعات ذخیره می‌شوند تا بعداً از همان‌جا ادامه یابد)
- فایل‌های باز، اتصالات شبکه باز، و سایر منابعی که در اختیار دارد

### چگونه چند پردازش هم‌زمان روی یک CPU اجرا می‌شوند؟

اینجا یکی از هوشمندانه‌ترین بخش‌های طراحی سیستم‌عامل‌های مدرن است. اگر سیستم شما فقط ۴ هسته CPU دارد اما ۲۰۰ پردازش در حال اجرا هستند، این ۲۰۰ پردازش **همزمان واقعی** اجرا نمی‌شوند (چون فقط ۴ هسته وجود دارد). در عوض، کرنل بخشی به نام **Scheduler (زمان‌بند)** دارد که به‌سرعت بین پردازش‌ها سوییچ می‌کند — هر پردازش برای یک بازه زمانی بسیار کوتاه (چند میلی‌ثانیه، به نام **Time Slice**) روی یک هسته اجرا می‌شود، سپس کرنل آن را متوقف می‌کند، وضعیتش را ذخیره می‌کند، و پردازش بعدی را اجرا می‌کند.

این سوییچینگ آن‌قدر سریع اتفاق می‌افتد (هزاران بار در ثانیه) که از دید انسان، به نظر می‌رسد همه پردازش‌ها همزمان در حال اجرا هستند — این توهم را **Multitasking** می‌نامند.

### وضعیت‌های مختلف یک پردازش (Process States)

هر پردازش در هر لحظه در یکی از این حالت‌ها قرار دارد:

| حالت | نماد در `ps`/`top` | توضیح |
|---|---|---|
| Running | `R` | در حال اجرا روی CPU، یا در صف آماده اجرا |
| Sleeping (Interruptible) | `S` | منتظر یک رویداد (مثل ورودی کاربر یا داده از شبکه)، می‌تواند با یک سیگنال بیدار شود |
| Uninterruptible Sleep | `D` | منتظر یک عملیات I/O دیسک است؛ نمی‌تواند حتی با سیگنال قطع شود (معمولاً خیلی کوتاه، اما اگر طولانی بماند نشانه مشکل دیسک است) |
| Stopped | `T` | متوقف‌شده (مثلاً با سیگنال `SIGSTOP` یا Ctrl+Z در ترمینال) |
| Zombie | `Z` | پردازش کارش تمام شده اما پدرش هنوز اطلاعات خروجی آن را نخوانده (توضیح کامل در بخش بعد) |

```bash
ps aux | awk '{print $8}' | sort | uniq -c
```
این دستور تعداد پردازش‌ها در هر حالت را می‌شمارد؛ اگر تعداد زیادی پردازش در حالت `D` ببینید، این نشانه قوی یک گلوگاه I/O دیسک است.

### PID، PPID، Process Groups و Sessions

هر پردازش یک **PID (Process ID)** منحصربه‌فرد دارد. هر پردازش (به‌جز PID 1) توسط پردازش دیگری ساخته شده، که به آن **پدر (Parent)** می‌گویند؛ شناسه پدر را **PPID (Parent Process ID)** می‌نامند.

```bash
ps -ef | head -5
```
ستون‌های `PID` و `PPID` این رابطه را نشان می‌دهند. یک ابزار بسیار مفید برای دیدن این رابطه به‌صورت درختی:
```bash
pstree -p
```
ا `pstree` رابطه پدر-فرزند تمام پردازش‌های سیستم را از PID 1 (systemd) به پایین، به‌صورت یک درخت بصری نشان می‌دهد.

پردازش‌ها همچنین می‌توانند در **Process Group ها** و **Session ها** سازمان‌دهی شوند — مفهومی که بیشتر برای مدیریت ترمینال کاربرد دارد: وقتی در یک پنجره ترمینال چند دستور را با `|` به هم متصل می‌کنید (مثل `cat file | grep pattern | sort`)، تمام این پردازش‌ها در یک Process Group قرار می‌گیرند تا بتوان همه آن‌ها را با یک سیگنال (مثل فشار دادن Ctrl+C) هم‌زمان متوقف کرد.

### ا fork و exec — چگونه پردازش‌های جدید ساخته می‌شوند

وقتی یک پردازش می‌خواهد پردازش جدیدی بسازد (مثلاً یک شل که یک دستور جدید اجرا می‌کند)، دو System Call کلیدی درگیر است:

ا **`fork()`**: پردازش فعلی خودش را دقیقاً کپی می‌کند — یک پردازش فرزند جدید با تقریباً همان حافظه، همان فایل‌های باز، ساخته می‌شود، فقط با PID متفاوت.

ا **`exec()`**: کد در حال اجرای پردازش فعلی را با کد یک برنامه کاملاً جدید جایگزین می‌کند (PID همان می‌ماند، اما محتوای اجرایی عوض می‌شود).

الگوی رایج `fork()` و سپس بلافاصله `exec()` این است که وقتی شما در ترمینال یک دستور تایپ می‌کنید، شل ابتدا خودش را `fork` می‌کند (یک کپی از شل ساخته می‌شود)، و سپس آن کپی فرزند بلافاصله `exec` می‌شود تا کد دستوری که شما خواستید (مثلاً `ls`) را اجرا کند — به این ترتیب شل اصلی (پدر) دست‌نخورده باقی می‌ماند و می‌تواند منتظر بماند تا فرزند تمام شود.

### ا Zombie Process — پردازشی که "مرده اما هنوز روی زمین است"

وقتی یک پردازش کارش تمام می‌شود (خارج/exit می‌شود)، کرنل بلافاصله تمام حافظه و منابع آن را آزاد نمی‌کند. یک رکورد کوچک (شامل کد خروجی/exit code و آماری از مصرف منابع) باقی می‌ماند تا **پردازش پدر** بتواند آن را با یک System Call به نام `wait()` بخواند — این یعنی «پدر، بیا ببین فرزندت با چه وضعیتی تمام شد».

اگر پدر این کار را انجام ندهد (مثلاً به‌خاطر یک باگ در برنامه پدر که فراموش کرده منتظر فرزندانش بماند)، آن رکورد کوچک برای همیشه باقی می‌ماند — این حالت را **Zombie Process** می‌نامند: پردازش دیگر در حال اجرا نیست (مصرف CPU/حافظه ندارد)، اما هنوز یک ورودی در جدول پردازش‌های کرنل اشغال کرده.

```bash
ps aux | grep 'Z'
```
تعداد زیاد Zombie نشانه یک باگ در برنامه‌ای است که پردازش‌های فرزند می‌سازد اما هرگز `wait()` نمی‌کند. تنها راه واقعی رفع مشکل، رفع باگ برنامه پدر یا (اگر ممکن نیست) کشتن خود پردازش پدر است — نمی‌توانید مستقیماً یک Zombie را «بکشید» چون از قبل مرده است؛ فقط منتظر است که پدرش رکوردش را بخواند.

## ۲.۳ سیگنال‌ها (Signals) — زبان ارتباطی بین پردازش‌ها و کرنل

### سیگنال چیست؟

سیگنال یک پیام بسیار ساده و کوچک است که یا کرنل یا یک پردازش دیگر، به یک پردازش می‌فرستد تا او را از یک رویداد مطلع کند یا از او بخواهد کاری انجام دهد. سیگنال‌ها با شماره یا نام شناخته می‌شوند:

| سیگنال | شماره | معنا | قابل نادیده‌گرفتن؟ |
|---|---|---|---|
| `SIGHUP` | 1 | معمولاً به معنای «تنظیماتت را دوباره بخوان» (استفاده رایج) | بله |
| `SIGINT` | 2 | وقفه (وقتی Ctrl+C می‌زنید) | بله |
| `SIGKILL` | 9 | خاتمه فوری و اجباری، بدون هیچ فرصتی برای پاکسازی | **خیر — هرگز** |
| `SIGTERM` | 15 | درخواست مودبانه برای خاتمه (پیش‌فرض دستور kill) | بله |
| `SIGSTOP` | 19 | توقف موقت اجرا | **خیر** |
| `SIGCONT` | 18 | ادامه اجرا بعد از STOP | بله |

### تفاوت حیاتی SIGTERM و SIGKILL

این یکی از مهم‌ترین نکات مفهومی این بخش است. وقتی `SIGTERM` به یک پردازش فرستاده می‌شود، آن پردازش **فرصت دارد** که خودش تصمیم بگیرد چگونه واکنش نشان دهد — می‌تواند فایل‌های باز را ذخیره کند، اتصالات شبکه را به‌درستی ببندد، و سپس خودش با آرامش خارج شود. این رفتار **Graceful Shutdown** نامیده می‌شود.

اما `SIGKILL` کاملاً متفاوت است: این سیگنال حتی به خود پردازش هم نمی‌رسد — **کرنل مستقیماً** آن پردازش را از جدول پردازش‌ها حذف می‌کند، بدون این‌که پردازش هیچ فرصتی برای واکنش داشته باشد. به همین دلیل، `SIGKILL` می‌تواند باعث از دست رفتن داده (مثلاً یک فایل نیمه‌نوشته‌شده) یا حالت ناسازگار (مثلاً یک تراکنش دیتابیس که نیمه‌کاره رها شده) شود.

```bash
kill -TERM 1234       # درخواست مودبانه خاتمه (پیش‌فرض)
kill 1234               # معادل بالا (SIGTERM پیش‌فرض است)
kill -KILL 1234        # اجبار فوری بدون فرصت پاکسازی
kill -9 1234             # معادل بالا (9 = شماره SIGKILL)
```

⚠️ **قانون طلایی:** همیشه ابتدا `SIGTERM` را امتحان کنید و چند ثانیه صبر کنید. فقط اگر پردازش پاسخ نداد (هنوز در حال اجرا بود)، به `SIGKILL` متوسل شوید. استفاده مستقیم و همیشگی از `kill -9` یک عادت بد رایج در بین مبتدیان است که می‌تواند مشکلات جدی (خصوصاً برای دیتابیس‌ها) ایجاد کند.

### ابزارهای ارسال سیگنال

```bash
kill 1234                          # ارسال SIGTERM به PID مشخص
kill -HUP 1234                      # ارسال SIGHUP (رایج برای "reload تنظیمات")
pkill -f "python.*myapp"             # کشتن بر اساس تطبیق نام کامل دستور (regex)
pkill -u alice                       # کشتن تمام پردازش‌های یک کاربر خاص
killall firefox                      # کشتن تمام پردازش‌هایی با این نام دقیق
```

### کنترل پردازش‌ها از ترمینال — jobs، bg، fg، nohup

وقتی یک دستور طولانی در ترمینال اجرا می‌کنید، چند راه برای کنترل آن دارید:

```bash
long-running-command &            # اجرا در پس‌زمینه (background) از ابتدا با &
# اگر دستور از قبل در حال اجراست و می‌خواهید آن را موقتاً متوقف کنید:
# Ctrl+Z (این سیگنال SIGTSTP می‌فرستد، پردازش را متوقف می‌کند)

jobs                                # لیست تمام کارهای (jobs) پس‌زمینه/متوقف‌شده این نشست ترمینال
bg %1                                # ادامه اجرای job شماره ۱ در پس‌زمینه
fg %1                                # آوردن job شماره ۱ به پیش‌زمینه (تعاملی دوباره)
```

یک نکته مهم: اگر یک دستور را در پس‌زمینه اجرا کرده باشید (`&`) و سپس ترمینال را ببندید، معمولاً یک `SIGHUP` به آن پردازش فرستاده می‌شود (چون "خانه" آن، یعنی نشست ترمینال، از بین رفته) که اغلب باعث خاتمه پردازش می‌شود. برای جلوگیری از این:

```bash
nohup long-running-command &
```
ا `nohup` (مخفف "no hang up") پردازش را طوری اجرا می‌کند که سیگنال `SIGHUP` را نادیده بگیرد، پس حتی با بسته شدن ترمینال، به اجرا ادامه می‌دهد. خروجی آن به‌طور پیش‌فرض در فایلی به نام `nohup.out` ذخیره می‌شود.

 در دنیای مدرن سرورها، معمولاً به‌جای `nohup` دستی، از **systemd service** یا ابزارهایی مثل `tmux`/`screen` (که یک نشست ترمینال کامل و مستقل می‌سازند) برای اجرای فرآیندهای طولانی‌مدت استفاده می‌شود، چون این‌ها کنترل و قابلیت مانیتورینگ بهتری فراهم می‌کنند.

## ۲.۴ اولویت‌بندی پردازش‌ها — nice و renice

### چرا نیاز به اولویت‌بندی داریم؟

فرض کنید سرور شما هم‌زمان یک وظیفه پس‌زمینه سنگین (مثل فشرده‌سازی یک backup بزرگ) و هم یک سرویس حیاتی (مثل وب‌سرور که باید سریع به کاربران پاسخ دهد) اجرا می‌کند. اگر Scheduler به‌طور مساوی به هر دو زمان CPU بدهد، وب‌سرور ممکن است کند شود چون منتظر می‌ماند تا نوبت CPU به او برسد.

ا **Niceness** (میزان «خوش‌اخلاقی») یک عدد است که به Scheduler می‌گوید یک پردازش چقدر باید نسبت به پردازش‌های دیگر «سخاوتمند» باشد در دادن اولویت CPU به بقیه. این عدد از **20-** (بالاترین اولویت، کمترین خوش‌اخلاقی — این پردازش خیلی «خودخواه» است و بیشترین سهم CPU را می‌خواهد) تا **19+** (پایین‌ترین اولویت، بیشترین خوش‌اخلاقی — این پردازش به بقیه اجازه می‌دهد جلو بیفتند) متغیر است. مقدار پیش‌فرض برای هر پردازش جدید، **۰** است.

```bash
nice -n 10 tar czf backup.tar.gz /data/
```
دستور `tar` با niceness برابر ۱۰ اجرا می‌شود — یعنی اولویت پایین‌تر از حالت عادی، پس CPU بیشتر در اختیار سایر پردازش‌های مهم‌تر (مثل وب‌سرور) باقی می‌ماند.

```bash
renice -n 15 -p 1234
```
ا `renice` niceness یک پردازش که **از قبل در حال اجراست** را تغییر می‌دهد (برخلاف `nice` که فقط هنگام شروع یک پردازش جدید استفاده می‌شود). `-p 1234` مشخص می‌کند این تغییر روی PID شماره ۱۲۳۴ اعمال شود.

⚠️ فقط کاربر root می‌تواند niceness یک پردازش را کاهش دهد (اولویت را بالا ببرد، یعنی به سمت -20 برود) یا niceness منفی برای یک پردازش جدید تنظیم کند؛ کاربران عادی فقط می‌توانند اولویت پردازش‌های خودشان را کاهش دهند (به سمت +19)، نه افزایش.

```bash
ps -eo pid,ni,comm | sort -k2 -n | head    # نمایش پردازش‌ها مرتب‌شده بر اساس niceness
top     # ستون NI در خروجی top نیز niceness هر پردازش را نشان می‌دهد
```

## ۲.۵ مدیریت حافظه — از حافظه فیزیکی تا Virtual Memory

### مشکل بنیادین: چند برنامه، یک حافظه فیزیکی محدود

فرض کنید سیستم شما ۸ گیگابایت RAM فیزیکی دارد، اما ۲۰ برنامه مختلف هم‌زمان در حال اجرا هستند که هرکدام فکر می‌کنند «صاحب» فضای حافظه خودشان هستند و می‌توانند از آدرس صفر تا آخرین آدرس ممکن استفاده کنند. اگر همه این برنامه‌ها مستقیماً به حافظه فیزیکی واقعی دسترسی داشتند، دو برنامه ممکن بود به‌طور تصادفی سعی کنند از یک آدرس فیزیکی یکسان استفاده کنند و داده همدیگر را خراب کنند.

### راه‌حل: Virtual Memory (حافظه مجازی)

کرنل به هر پردازش یک توهم می‌دهد: انگار او تنها برنامه در حال اجرا روی سیستم است و به تنهایی به کل فضای آدرس‌دهی (مثلاً در یک سیستم ۶۴ بیتی، مقداری بسیار بزرگ) دسترسی دارد. این فضای آدرس‌دهی که هر برنامه می‌بیند، **Virtual Memory (حافظه مجازی)** نامیده می‌شود و **کاملاً مجزا** از حافظه فیزیکی واقعی است.

کرنل (با کمک یک بخش سخت‌افزاری در CPU به نام **MMU — Memory Management Unit**) یک نگاشت (mapping) بین آدرس‌های مجازی هر برنامه و آدرس‌های فیزیکی واقعی RAM نگه می‌دارد. وقتی برنامه‌ای می‌خواهد از آدرس مجازی `0x1000` بخواند، MMU این آدرس را به آدرس فیزیکی واقعی (مثلاً `0x7A3B2000`) ترجمه می‌کند — این کار کاملاً پشت‌صحنه و نامرئی برای برنامه انجام می‌شود.

این طراحی دو مزیت بزرگ دارد:
۱. **ایزوله‌سازی امنیتی**: یک برنامه هرگز نمی‌تواند به حافظه فیزیکی برنامه دیگر دسترسی مستقیم داشته باشد، چون فقط آدرس‌های مجازی خودش را می‌بیند.
۲. **انعطاف در مدیریت حافظه**: کرنل می‌تواند حافظه را بین برنامه‌ها به‌طور پویا جابه‌جا کند، بدون این‌که برنامه‌ها متوجه شوند.

### ا Swap — وقتی RAM فیزیکی کافی نیست

اگر مجموع حافظه‌ای که همه برنامه‌ها درخواست کرده‌اند بیشتر از RAM فیزیکی واقعی باشد، کرنل می‌تواند بخش‌هایی از حافظه که مدتی است استفاده نشده‌اند را موقتاً روی دیسک (در یک فضای مخصوص به نام **Swap**) بنویسد و آن فضای RAM را برای داده‌ای که الان فعالانه استفاده می‌شود، آزاد کند. وقتی آن داده دوباره لازم شود، از دیسک به RAM بازگردانده می‌شود (این فرآیند را **Swapping** یا **Paging** می‌نامند).

⚠️ چون دیسک (حتی SSD) بسیار کندتر از RAM است، Swap شدید (زمانی که سیستم مدام در حال جابه‌جایی داده بین RAM و دیسک است) می‌تواند باعث کندی شدید سیستم شود — این حالت را **Thrashing** می‌نامند.

```bash
free -h
```
ستون `Swap` نشان می‌دهد چقدر از فضای Swap استفاده شده است. اگر این عدد به‌طور مداوم بالا برود، نشانه کمبود RAM فیزیکی است.

### ا NUMA — معماری حافظه در سرورهای چند-پردازنده‌ای

در سرورهای بزرگ با چند CPU فیزیکی (Socket)، هر CPU معمولاً به بخشی از RAM «نزدیک‌تر» است (فیزیکاً روی همان برد متصل است) و به بقیه RAM «دورتر» (باید از طریق یک لینک ارتباطی بین دو CPU عبور کند). این معماری را **NUMA (Non-Uniform Memory Access)** می‌نامند، چون سرعت دسترسی به حافظه یکسان نیست — دسترسی به حافظه محلی سریع‌تر از حافظه راه دور است.

```bash
numactl --hardware      # نمایش توپولوژی NUMA سیستم (چند node، هرکدام چقدر حافظه)
lscpu | grep NUMA         # خلاصه اطلاعات NUMA
```
برای برنامه‌های حساس به کارایی (مثل دیتابیس‌های بزرگ)، آگاهی از NUMA و اجرای عمدی یک پردازش روی هسته‌های نزدیک به حافظه‌اش می‌تواند تفاوت کارایی محسوسی ایجاد کند — این یک مبحث پیشرفته‌تر است که در آزمون LPIC-2 معمولاً فقط در سطح مفهومی (نه پیاده‌سازی عمیق) پرسیده می‌شود.

## ۲.۶ ماژول‌های کرنل — گسترش‌پذیری بدون کامپایل مجدد

### چرا ماژول‌ها وجود دارند؟

کرنل لینوکس باید بتواند با هزاران مدل مختلف سخت‌افزار (کارت‌های شبکه، کنترلرهای دیسک، کارت‌های گرافیک) کار کند. اگر درایور تمام این سخت‌افزارها همیشه به‌طور دائم در حافظه بارگذاری می‌شد، حافظه هدررفت زیادی داشت (چون سیستم شما فقط یک مدل کارت شبکه دارد، نه هزاران مدل مختلف).

راه‌حل، **ماژول‌های کرنل (Kernel Modules)** است: قطعات کد جداگانه که می‌توانند **به‌صورت پویا** (در حین اجرای سیستم، بدون نیاز به ریبوت) بارگذاری یا تخلیه شوند. وقتی کرنل سخت‌افزار جدیدی شناسایی می‌کند (یا کاربر دستی درخواست می‌کند)، فقط ماژول مربوط به همان سخت‌افزار خاص بارگذاری می‌شود.

### دستورات مدیریت ماژول‌ها

```bash
lsmod
```
لیست تمام ماژول‌هایی که **در حال حاضر** در حافظه بارگذاری شده‌اند را نشان می‌دهد، همراه با اندازه و تعداد ماژول‌های دیگری که به آن‌ها وابسته‌اند.

```bash
modinfo e1000e
```
اطلاعات کامل درباره یک ماژول خاص (بدون بارگذاری آن) نشان می‌دهد: نویسنده، توضیحات، پارامترهای قابل تنظیم، و مهم‌تر از همه، **وابستگی‌ها** (این ماژول به چه ماژول‌های دیگری نیاز دارد تا کار کند).

```bash
modprobe e1000e
```
ا `modprobe` هوشمندترین و توصیه‌شده‌ترین ابزار برای بارگذاری ماژول است: علاوه بر بارگذاری خود ماژول، **تمام وابستگی‌های آن را هم به‌طور خودکار پیدا و بارگذاری می‌کند**. این اطلاعات وابستگی از فایلی به نام `modules.dep` (که با دستور `depmod` ساخته می‌شود) خوانده می‌شود.

```bash
modprobe -r e1000e
```
ا  (remove) `-r` ماژول را تخلیه می‌کند — اما فقط اگر هیچ ماژول دیگری در حال حاضر به آن وابسته نباشد.

در مقابل، دو دستور سطح پایین‌تر وجود دارند که وابستگی‌ها را مدیریت **نمی‌کنند**:

```bash
insmod /lib/modules/$(uname -r)/kernel/drivers/net/ethernet/intel/e1000e/e1000e.ko
rmmod e1000e
```
ا `insmod` مستقیماً یک فایل ماژول مشخص (با مسیر کامل) را بارگذاری می‌کند، بدون بررسی یا بارگذاری خودکار وابستگی‌ها — اگر ماژول به چیز دیگری نیاز داشته باشد که بارگذاری نشده، `insmod` با خطا مواجه می‌شود. `rmmod` هم معادل مستقیم برای تخلیه است.

📌 **نکته کلیدی آزمون:** تقریباً همیشه باید از `modprobe` استفاده کنید، نه `insmod`/`rmmod`؛ این دو دستور آخر بیشتر برای دیباگ سطح پایین یا زمانی که ماژول خارج از مسیرهای استاندارد کرنل قرار دارد کاربرد دارند.

### پیکربندی دائمی ماژول‌ها

**بارگذاری خودکار یک ماژول در هر بوت:**
```bash
echo "vfio" > /etc/modules-load.d/vfio.conf
```
هر فایل در `/etc/modules-load.d/*.conf` شامل نام یک یا چند ماژول است که systemd در ابتدای بوت به‌طور خودکار بارگذاری می‌کند.

**تنظیم پارامترهای یک ماژول به‌طور دائم:**
```bash
echo "options e1000e InterruptThrottleRate=3000" > /etc/modprobe.d/e1000e.conf
```
هر بار که این ماژول (چه دستی چه خودکار) بارگذاری شود، این پارامتر همیشه اعمال می‌شود.

**مسدود کردن (blacklist) یک ماژول — جلوگیری از بارگذاری خودکار:**
```bash
echo "blacklist nouveau" > /etc/modprobe.d/blacklist-nouveau.conf
```
این رایج‌ترین کاربردش وقتی است که یک درایور جایگزین (مثلاً درایور اختصاصی NVIDIA به‌جای درایور متن‌باز `nouveau`) نصب می‌کنید و می‌خواهید مطمئن شوید کرنل به‌طور خودکار درایور اشتباه (قدیمی) را بارگذاری نمی‌کند.

## ۲.۷ تنظیمات Runtime کرنل با sysctl و /proc/sys

###ا  /proc — پنجره‌ای زنده به درون کرنل

ا `proc/` یک فایل‌سیستم بسیار خاص است — برخلاف فایل‌سیستم‌های عادی (مثل ext4) که داده واقعی روی دیسک ذخیره می‌کنند، `/proc` اصلاً روی دیسک وجود ندارد؛ این یک **فایل‌سیستم مجازی** است که کرنل آن را در لحظه (on-the-fly) از اطلاعات داخلی خودش می‌سازد. وقتی یک فایل داخل `/proc` را می‌خوانید، در واقع دارید مستقیماً از حافظه و ساختارهای داده کرنل اطلاعات می‌گیرید.

```bash
cat /proc/cpuinfo        # اطلاعات دقیق CPU
cat /proc/meminfo          # جزئیات کامل وضعیت حافظه
cat /proc/uptime            # مدت زمان روشن بودن سیستم
ls /proc/1234/                # اطلاعات پردازش با PID 1234 (وضعیت، فایل‌های باز، محیط)
```

### /proc/sys و sysctl — تنظیم رفتار کرنل بدون ریبوت

زیرشاخه خاصی از `/proc` به نام `/proc/sys/` علاوه بر خواندنی بودن، **قابل نوشتن** هم هست — یعنی می‌توانید مستقیماً با نوشتن یک مقدار جدید در این فایل‌ها، رفتار کرنل را در همان لحظه (بدون نیاز به ریبوت) تغییر دهید.

```bash
cat /proc/sys/net/ipv4/ip_forward
echo 1 > /proc/sys/net/ipv4/ip_forward
```
این مثال، قابلیت مسیریابی بسته‌های IP (تبدیل سرور به یک روتر) را در همان لحظه فعال می‌کند.

اما نوشتن مستقیم در `/proc/sys` کمی خام و مستعد خطا است. ابزار استاندارد و توصیه‌شده برای این کار، `sysctl` است که همان کار را با syntax تمیزتری انجام می‌دهد:

```bash
sysctl net.ipv4.ip_forward                 # خواندن (معادل cat از /proc/sys)
sysctl -w net.ipv4.ip_forward=1              # نوشتن (معادل echo)
sysctl -a                                     # نمایش تمام پارامترهای موجود (صدها خط)
```
📌 دقت کنید: نام پارامتر در `sysctl` از نقطه (`net.ipv4.ip_forward`) استفاده می‌کند، در حالی که مسیر معادل در `/proc/sys` از اسلش (`/proc/sys/net/ipv4/ip_forward`) استفاده می‌کند — این دو کاملاً معادل هم هستند، فقط نمادگذاری متفاوت است.

### دائمی کردن تغییرات sysctl

تغییراتی که با `sysctl -w` یا نوشتن مستقیم در `/proc/sys` انجام می‌شوند، **موقتی** هستند و با ریبوت از بین می‌روند (چون `/proc` اصلاً روی دیسک ذخیره نمی‌شود، هر بار از نو ساخته می‌شود). برای دائمی کردن:

```bash
echo "net.ipv4.ip_forward = 1" > /etc/sysctl.d/99-ip-forward.conf
sysctl -p /etc/sysctl.d/99-ip-forward.conf
```
فایل‌های داخل `/etc/sysctl.d/*.conf` در هر بوت به‌طور خودکار توسط systemd خوانده و اعمال می‌شوند. دستور `sysctl -p <file>` هم بلافاصله (بدون نیاز به ریبوت) همان فایل را می‌خواند و اعمال می‌کند.

✅ ا **Best Practice:** همیشه یک فایل جدید و مجزا در `/etc/sysctl.d/` برای تنظیمات سفارشی خودتان بسازید (مثلاً `99-custom-network.conf`)، به‌جای ویرایش مستقیم فایل عمومی `/etc/sysctl.conf`. این کار مدیریت، ردیابی تغییرات (با ابزارهایی مثل git)، و troubleshooting را بسیار ساده‌تر می‌کند.

## ۲.۸ کامپایل کرنل از سورس

### چرا امروزه به‌ندرت به این کار نیاز است، اما چرا هنوز مهم است بدانید

در دنیای واقعی امروز، تقریباً همیشه از کرنل‌های از پیش کامپایل‌شده که توسط توزیع (Debian, RHEL, ...) ارائه می‌شوند استفاده می‌کنید — این کرنل‌ها بسیار تست‌شده و برای اکثر سخت‌افزارهای رایج بهینه هستند. کامپایل دستی کرنل معمولاً فقط در موارد بسیار خاص لازم است: توسعه‌دهندگان کرنل، سیستم‌های embedded با سخت‌افزار بسیار غیرمعمول، یا نیاز به یک قابلیت آزمایشی که هنوز در نسخه‌های رسمی توزیع در دسترس نیست.

با این حال، LPIC-2 این موضوع را می‌پرسد چون فهمیدن مراحل کامپایل، درک عمیق‌تری از این‌که «کرنل واقعاً از چه ساخته شده» به شما می‌دهد.

### مراحل کامل کامپایل

**۱. دریافت سورس کد کرنل و استخراج آن**
```bash
wget https://cdn.kernel.org/pub/linux/kernel/v6.x/linux-6.6.tar.xz
tar xf linux-6.6.tar.xz
cd linux-6.6
```
سورس کد کامل کرنل لینوکس (میلیون‌ها خط کد C) از سایت رسمی kernel.org دانلود و استخراج می‌شود.

**۲. تعیین تنظیمات کرنل (Configuration) — کدام قابلیت‌ها کامپایل شوند**

کرنل لینوکس هزاران گزینه قابل تنظیم دارد (کدام درایورها، کدام فایل‌سیستم‌ها، کدام قابلیت‌های امنیتی باید داخل کرنل نهایی کامپایل شوند). این تنظیمات در یک فایل به نام `.config` ذخیره می‌شوند.

```bash
cp /boot/config-$(uname -r) .config     # شروع از تنظیمات کرنل فعلی سیستم (رایج‌ترین روش)
make oldconfig                             # به‌روزرسانی تنظیمات کپی‌شده برای نسخه سورس جدید؛ فقط برای گزینه‌های جدید سوال می‌پرسد
make menuconfig                             # رابط متنی تعاملی برای تغییر دستی تنظیمات (نیازمند کتابخانه ncurses)
```
ا `make menuconfig` یک رابط منوی متنی (شبیه رابط‌های قدیمی BIOS) باز می‌کند که می‌توانید با کلیدهای جهت‌نما هزاران گزینه را مرور و فعال/غیرفعال کنید.

**۳. کامپایل واقعی کرنل**
```bash
make -j$(nproc)
```
ا`make` فرآیند کامپایل را شروع می‌کند؛ `-j$(nproc)` به `make` می‌گوید از تمام هسته‌های CPU موجود به‌صورت موازی استفاده کند (کامپایل کامل کرنل می‌تواند از چند دقیقه تا بیش از یک ساعت طول بکشد، بسته به قدرت سیستم).

**۴. کامپایل و نصب ماژول‌ها**
```bash
make modules
make modules_install
```
بخش‌هایی از کرنل که به‌عنوان ماژول (نه built-in) تنظیم شده‌اند، جداگانه کامپایل و در مسیر `/lib/modules/<version>/` نصب می‌شوند.

**۵. نصب نهایی کرنل**
```bash
make install
```
این دستور فایل کرنل کامپایل‌شده را در `/boot/` کپی می‌کند، و در اکثر توزیع‌ها به‌طور خودکار initramfs جدید می‌سازد و GRUB را هم به‌روزرسانی می‌کند (اضافه کردن یک entry جدید برای این کرنل تازه کامپایل‌شده، در کنار کرنل‌های قبلی که همچنان به‌عنوان پشتیبان باقی می‌مانند).

### پاک‌سازی بین کامپایل‌ها

```bash
make clean          # فقط فایل‌های میانی کامپایل (object files) را پاک می‌کند، .config دست‌نخورده می‌ماند
make mrproper        # پاک‌سازی کامل، شامل خود فایل .config — بازگشت کامل به حالت اولیه سورس
```

### Kernel Rollback — بازگشت به نسخه قبلی در صورت مشکل

یکی از بزرگ‌ترین مزایای این‌که `make install` کرنل جدید را **در کنار** کرنل‌های قبلی نصب می‌کند (نه جایگزین کردن) این است که اگر کرنل جدید مشکلی داشت (مثلاً با سخت‌افزار خاصی سازگار نبود)، به‌سادگی می‌توانید از منوی GRUB، کرنل قبلی (که هنوز نصب و کاملاً سالم است) را انتخاب کنید — این را **Kernel Rollback** می‌نامند و یکی از دلایل مهمی است که چرا معمولاً نباید کرنل‌های قدیمی را زود حذف کنید.

```bash
# i لیست تمام کرنل‌های نصب‌شده روی سیستم
ls /boot/vmlinuz-*
dpkg --list | grep linux-image      # 🔵 لیست پکیج‌های کرنل نصب‌شده
rpm -qa | grep kernel                 # 🔴 معادل
```

## ۲.۹ ابزارهای بررسی سخت‌افزار و دستگاه‌ها

### دستورات پایه شناسایی سخت‌افزار

```bash
lspci                    # لیست تمام دستگاه‌های متصل به باس PCI (کارت گرافیک، کنترلر شبکه، ...)
lspci -v                  # با جزئیات بیشتر (شامل درایور در حال استفاده هرکدام)
lsusb                     # لیست دستگاه‌های متصل به USB
lsblk                     # لیست دیسک‌ها و پارتیشن‌های بلاکی، به‌صورت درختی
lscpu                     # اطلاعات کامل و خوانا از CPU (تعداد هسته، معماری، سرعت، کش)
```

### udev — سیستم مدیریت پویا دستگاه‌ها

وقتی یک دستگاه USB جدید (مثلاً یک فلش‌درایو) را وصل می‌کنید، کرنل این رویداد را شناسایی می‌کند اما خودش تصمیم نمی‌گیرد این دستگاه چه نامی در `/dev/` بگیرد یا چه اسکریپتی باید اجرا شود — این وظیفه به یک سیستم در فضای کاربر به نام **udev** سپرده شده است.

```bash
udevadm monitor
```
این دستور رویدادهای زنده udev را نمایش می‌دهد — اگر یک USB را در حین اجرای این دستور وصل کنید، بلافاصله رویداد شناسایی آن را می‌بینید.

```bash
udevadm info -a -n /dev/sda
```
اطلاعات کامل یک دستگاه خاص و تمام دستگاه‌های «والد» آن در سلسله‌مراتب سخت‌افزاری را نشان می‌دهد — این برای نوشتن **قوانین سفارشی udev** (مثلاً «هر بار که این فلش‌درایو خاص با این شماره سریال وصل شد، همیشه نامش را `/dev/mybackup` بگذار») ضروری است.

```
# /etc/udev/rules.d/99-custom-usb.rules
SUBSYSTEM=="block", ATTRS{serial}=="AB12CD34", SYMLINK+="mybackup"
```

```bash
udevadm control --reload      # بارگذاری مجدد قوانین بعد از تغییر فایل
udevadm trigger                 # اجرای مجدد قوانین برای دستگاه‌های از قبل متصل
```

## ۲.۱۰ خلاصه نکات کلیدی برای آزمون

- تفاوت Kernel Space (Ring 0، دسترسی کامل) و User Space (Ring 3، دسترسی محدود) و نقش System Call به‌عنوان تنها پل ارتباطی بین این دو
- تفاوت `fork()` (کپی کردن پردازش) و `exec()` (جایگزینی کد در حال اجرا)
- ا Zombie Process یعنی پردازشی که تمام شده اما پدرش هنوز `wait()` نکرده؛ راه‌حل واقعی، رفع مشکل در برنامه پدر است
- تفاوت حیاتی `SIGTERM` (مودبانه، قابل نادیده‌گرفتن توسط برنامه برای پاکسازی) و `SIGKILL` (فوری، اجباری، بدون فرصت پاکسازی)
- ا Niceness از -20 (بالاترین اولویت) تا +19 (پایین‌ترین اولویت)؛ فقط root می‌تواند اولویت را افزایش دهد
- تفاوت `modprobe` (هوشمند، حل خودکار وابستگی) با `insmod`/`rmmod` (مستقیم، بدون حل وابستگی)
- ا `/proc/sys` و `sysctl` هر دو یک چیز را نشان می‌دهند؛ تغییرات موقتی هستند مگر در `/etc/sysctl.d/*.conf` ذخیره شوند
- ترتیب کامپایل کرنل: تنظیمات (`.config` با `menuconfig`/`oldconfig`) → `make` → `make modules_install` → `make install`
- کرنل‌های قدیمی معمولاً کنار کرنل جدید نگه داشته می‌شوند تا امکان Rollback از طریق منوی GRUB وجود داشته باشد
